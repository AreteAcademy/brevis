Configuration

Chaque variable d'environnement, avec sa valeur par défaut, son format et ce qui se passe quand elle manque.

Toute la configuration vient de l'environnement, lu une seule fois au démarrage. Rien ne consulte l'environnement ensuite : un processus dont la configuration change en cours d'exécution est un processus dont personne ne peut reproduire le comportement.

Requis#

variable
BREVIS_DATABASE_URLPostgres. Manquante = erreur au démarrage dans les cinq sous-commandes qui utilisent la base

Processus#

variabledéfaut
BREVIS_ENVproductionlocal journalise en texte et laisse l'interface ouverte ; toute autre valeur, y compris l'absence de valeur, exige des identifiants et journalise en JSON. Définissez BREVIS_ENV=local pour le développement
BREVIS_HTTP_ADDR:8080adresse d'écoute
BREVIS_LOG_LEVELinfo
BREVIS_SHUTDOWN_TIMEOUT_SECONDS15entier ; une valeur non numérique est une erreur au démarrage
BREVIS_DB_MAX_CONNSdéfaut du pilote, max(4, CPUs)plafond du pool Postgres de chaque processus ; une valeur non numérique ou négative est une erreur au démarrage
BREVIS_CONSOLE_STATEMENT_TIMEOUT_SECONDS0 (désactivé)console (brevis serve) uniquement : Postgres interrompt toute requête de la console qui dure plus longtemps, afin qu'une requête de liste hors de contrôle ne garde pas une connexion. 30 est la valeur recommandée partout où le pool accepte les paramètres de démarrage ; désactivé par défaut, car un PgBouncer en mode transaction refuse sinon la connexion. Envoyé comme paramètre de démarrage de la connexion, donc un PgBouncer en mode transaction exige ignore_startup_parameters = statement_timeout
BREVIS_RETENTION_TRIM_DAYS0 (désactivé)purge planifiée optionnelle, exécutée par brevis scheduler : vide le log, les phases et la sortie des runs plus anciens que cette valeur. Même effet que brevis prune --trim-after. 0 = le scheduler ne purge jamais
BREVIS_RETENTION_PURGE_DAYS0 (jamais)avec la précédente, supprime aussi les runs plus anciens que cette valeur. Doit être au moins égale à la valeur de trim
BREVIS_RETENTION_INTERVAL_HOURS24fréquence d'exécution de la purge planifiée (une fois au démarrage, puis toutes les N heures)
BREVIS_BRAND_FILEbrand.yamlpersonnalisation de marque ; absent = valeur par défaut
BREVIS_UI_URL—base du lien du run dans les alertes
BREVIS_METRICS_ADDR—port des métriques Prometheus ; vide = non exposé. Voir Observabilité
BREVIS_SLACK_WEBHOOK—destination des alertes d'échec. Vide = personne n'est prévenu

Authentification#

variable
BREVIS_AUTH_USERutilisateur de l'interface
BREVIS_AUTH_PASSWORD_HASHhash pbkdf2-sha256$…, généré par brevis hash
BREVIS_AUTH_SECRET32 octets ou plus pour signer la session (openssl rand -base64 48)

Les trois vont ensemble, ou aucune.

variabledéfaut
BREVIS_AUTH_CLIENT_IP_HEADER—en-tête que votre proxy renseigne avec l'adresse du client, par ex. X-Forwarded-For. C'est la dernière entrée qui est utilisée (celle ajoutée par votre proxy). Vide = l'adresse de la connexion

La connexion est limitée par adresse client (IPv6 par son /64) : après trois échecs, l'adresse est verrouillée 2 secondes, durée qui double jusqu'à 15 minutes. Derrière un ingress ou un load balancer, définissez la variable (le chart Helm le fait quand api.ingress.enabled est actif ; surchargez avec auth.clientIPHeader) : sans elle, tous les clients partagent l'adresse du proxy, et une seule personne qui devine des mots de passe verrouillerait tout le monde. Dans ce cas, hors de BREVIS_ENV=local, le verrouillage est plafonné à 30 secondes et un avertissement est journalisé au démarrage. Ne définissez la variable que si l'en-tête est écrit par un proxy de confiance et ne peut pas être forgé par le client. Une seule vérification de mot de passe s'exécute à la fois par adresse : deux personnes derrière un même NAT qui se connectent à la même seconde peuvent donc voir brièvement un 429.

Une configuration à moitié faite est une erreur au démarrage

Celui qui a renseigné le nom d'utilisateur croit que la porte est fermée. L'interface déclenche des pipelines : un POST /workflows/<slug>/trigger exécute un dbt build qui écrit dans l'entrepôt. Ouverte sur Internet, c'est une télécommande pour l'entrepôt — et un avertissement dans le log ne défait pas cette croyance, car personne ne lit le log d'un processus qui fonctionne.

Hors de BREVIS_ENV=local, démarrer sans identifiants est refusé :

error: BREVIS_ENV=production requires a credential: set BREVIS_AUTH_USER,
BREVIS_AUTH_PASSWORD_HASH (generate one with `brevis hash`) and BREVIS_AUTH_SECRET

Les anciens noms fonctionnent toujours

Quatre variables ont été renommées le 2026-09-10, lorsque les derniers noms portugais ont quitté le côté opérateur du projet : BREVIS_AUTH_USUARIO, BREVIS_AUTH_SENHA_HASH, BREVIS_AUTH_SEGREDO et BREVIS_POD_MANTER_EM_FALHA. Une installation qui définit l'ancien nom continue de fonctionner et journalise un avertissement nommant le nouveau.

Ajoutez le nouveau nom, déployez, puis retirez l'ancien — le nouveau nom l'emporte quand les deux sont définis. Les anciens noms disparaîtront dans une version majeure.

Dans le SDK, BREVIS_SDK_LIMITE_INLINE est devenue BREVIS_SDK_INLINE_LIMIT selon la même règle.

Environnement des tâches#

variabledéfaut
BREVIS_TASK_ENVvidece que chaque step reçoit

Une tâche n'hérite pas de l'environnement de l'orchestrateur. La raison est concrète : le processus porte BREVIS_DATABASE_URL avec le nom d'utilisateur et le mot de passe Postgres, et un workflow est une commande arbitraire écrite par quelqu'un d'autre — hériter donnerait les identifiants de la base à chaque step de chaque pipeline.

Ce dont la tâche a besoin est déclaré :

bash
BREVIS_TASK_ENV=GOOGLE_PROJECT_ID,STAGE   # forwards these two from the process
BREVIS_TASK_ENV=STAGE=prod                # sets a literal
BREVIS_TASK_ENV='*'                       # forwards everything EXCEPT BREVIS_*

PATH et HOME sont toujours inclus — sans PATH, aucune commande ne se résout, et l'erreur serait un « not found » qui n'explique rien.

Un nom manquant ne devient pas une chaîne vide : GOOGLE_PROJECT_ID="" ferait échouer dbt avec un message pire qu'une variable manquante.

Kubernetes#

Des décisions d'installation, pas de workflow.

variabledéfautformat
BREVIS_PODSautoauto, on ou off ; toute autre valeur est une erreur au démarrage
BREVIS_POD_NAMESPACEcelui du cluster
BREVIS_POD_SERVICE_ACCOUNT—
BREVIS_POD_PULL_SECRETS—liste séparée par des virgules
BREVIS_POD_ENV_FROM_SECRETS—liste séparée par des virgules
BREVIS_POD_ENV_FROM_CONFIGMAPS—liste séparée par des virgules
BREVIS_POD_ALLOWED_SECRETS—liste séparée par des virgules
BREVIS_POD_CREDENTIAL_PATH—chemin monté dans le pod
BREVIS_POD_CREDENTIAL_PVC—PVC contenant les identifiants
BREVIS_POD_NODE_SELECTOR—key=value,other=value
BREVIS_POD_TOLERATIONS—key=value:effect,… ; uniquement l'opérateur Equal

Dans les listes, les entrées vides sont ignorées : a,,b est une faute de frappe, et un nom de secret vide ferait rejeter tout le pod par le serveur.

Tests#

variable
BREVIS_TEST_DATABASE_URLbase de données pour les tests d'intégration ; sans elle, ils sont sautés

Endpoints de santé#

GET /healthliveness — n'interroge pas la base de données
GET /readyreadiness — interroge, et nomme la dépendance qui a échoué

La séparation est voulue : une sonde de liveness qui dépend d'un service externe fait tuer le pod par Kubernetes quand la base vacille, au lieu de simplement le retirer du load balancer.

Un exemple complet#

bash
# required
export BREVIS_DATABASE_URL='postgres://brevis:secret@db:5432/brevis?sslmode=require'

# production requires credentials
export BREVIS_ENV=production
export BREVIS_AUTH_USER=operator
export BREVIS_AUTH_PASSWORD_HASH="$(brevis hash < password.txt)"
export BREVIS_AUTH_SECRET="$(openssl rand -base64 48)"

# what the tasks need, and nothing more
export BREVIS_TASK_ENV=GOOGLE_PROJECT_ID,STAGE,DBT_KEYFILE

# pods
export BREVIS_PODS=on
export BREVIS_POD_NAMESPACE=data
export BREVIS_POD_SERVICE_ACCOUNT=brevis-runner
export BREVIS_POD_ENV_FROM_SECRETS=bigquery-cred

# alerts
export BREVIS_SLACK_WEBHOOK='https://hooks.slack.com/services/...'
export BREVIS_UI_URL='https://brevis.example.com'
