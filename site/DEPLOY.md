# Deploying brevis.sh

The site is static HTML, generated by `build.py` and committed. Cloudflare Pages
serves it; there is no server-side anything.

## Cloudflare Pages, connected to Git

Six steps in the dashboard, once. After that every push to `master` publishes.

1. **Workers & Pages → Create → Pages → Connect to Git**, and pick
   `AreteAcademy/brevis`.
2. **Production branch**: `master`.
3. **Build settings**:

   | field | value |
   |---|---|
   | Framework preset | None |
   | Build command | `python3 build.py --dist` |
   | Build output directory | `dist` |
   | Root directory | `site` |

4. **Environment variables**: none. The generator reads no environment.
5. **Save and Deploy.** The first build takes about a minute, most of it the
   container starting.
6. **Custom domains → Set up a domain** → `brevis.sh`, then `www.brevis.sh` as a
   redirect to it. If the domain's DNS is already on Cloudflare, the record is
   created for you.

### Why a build command at all, when the HTML is committed

It is not to produce the HTML — that is already in the repo, and
`build.py --check` in CI proves it is current. It is to produce **`dist/`**,
which holds only what is served: no `build.py`, no `templates/`, no
`content/*.md`. The repository is public, so this is not about secrecy; it is
that a `.md` served next to the `.html` generated from it is a second indexable
copy of every page, and dead weight on the CDN.

If you would rather not run a build at all, set the output directory to `site`
and leave the command empty. It works, and you get those files on the CDN.

## What ships with the site

| file | |
|---|---|
| `_headers` | cache and security headers; Pages reads it verbatim |
| `_redirects` | `/github`, `/issues`, `/sdk` and the pre-`/docs` paths |
| `404.html` | Pages serves it automatically for an unmatched path |

`_headers` sets a CSP that allows exactly what the site uses: its own scripts,
one inline snippet (the `.js` class), the Google Fonts stylesheet, and the font
files. Nothing else — no analytics, no frames, no form posts. If you add
analytics later, that header is the file to change, and forgetting it means the
script is blocked silently in the browser console.

## Checking a deploy

```bash
curl -sI https://brevis.sh/            | grep -i 'cache-control\|content-type'
curl -sI https://brevis.sh/css/styles.css | grep -i cache-control   # immutable
curl -so /dev/null -w '%{http_code}\n' https://brevis.sh/docs/cli/   # 200
curl -so /dev/null -w '%{http_code}\n' https://brevis.sh/nothing     # 404
curl -sI https://brevis.sh/github      | grep -i location            # the repo
```

The one worth checking after every content change is `/sitemap.xml` — it lists
all 32 URLs, and a missing one means a page was generated but not linked.

## The other two paths

**Wrangler from CI.** If the deploy should come out of GitHub Actions instead,
it needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository
secrets and a step running
`npx wrangler pages deploy dist --project-name=brevis`. More moving parts, and
the reason to want it is usually wanting the deploy gated on something the CI
knows and Pages does not.

**Netlify and Vercel** still work — `netlify.toml` and `vercel.json` are in this
directory and were not removed. `_headers` and `_redirects` are Netlify's own
formats, which Cloudflare adopted, so those two files serve both.

## Preview deployments

Pages builds every pull request to its own URL. That is worth keeping: the
Lighthouse job in CI measures a local server, and a preview URL measures the
CDN, the real headers and the real font fetch.
