# Deploying brevis.sh

The site is static HTML, generated by `build.py` and committed. A Cloudflare
Worker serves it as static assets; there is no Worker script and no
server-side anything.

## Cloudflare Workers Builds, connected to Git

The Worker `brevis` is connected to `AreteAcademy/brevis` with root directory
`site` and production branch `master`. Every push to `master` deploys; every
other branch uploads a preview version.

What ships is decided by **`wrangler.jsonc`** in this directory, not by the
dashboard:

| field | value | why |
|---|---|---|
| `name` | `brevis` | the existing Worker; another name creates a second one |
| `build.command` | `python3 build.py --dist` | wrangler runs it before `deploy` and `versions upload` alike |
| `assets.directory` | `./dist` | only what `build.py --dist` copies is served |
| `assets.not_found_handling` | `404-page` | an unmatched path gets `404.html` with status 404 |

The dashboard keeps its defaults (deploy `npx wrangler deploy`, version
`npx wrangler versions upload`); its build command is redundant with
`build.command` and harmless. Environment variables: none, the generator reads
no environment. `brevis.sh` is a custom domain on the Worker.

Without `wrangler.jsonc`, `wrangler deploy` guesses a static site and uploads
all of `site/`, and `wrangler versions upload` guesses nothing and fails, which
is the red `Workers Builds` check every pull request used to get.

To see what a change would ship without deploying it:

```bash
npx wrangler versions upload --dry-run   # runs the build, reads dist/
```

### Why a build command at all, when the HTML is committed

It is not to produce the HTML — that is already in the repo, and
`build.py --check` in CI proves it is current. It is to produce **`dist/`**,
which holds only what is served: no `build.py`, no `templates/`, no
`content/*.md`. The repository is public, so this is not about secrecy; it is
that a `.md` served next to the `.html` generated from it is a second indexable
copy of every page, and dead weight on the CDN.

## What ships with the site

| file | |
|---|---|
| `_headers` | cache and security headers; Workers static assets read it verbatim |
| `_redirects` | `/github`, `/issues`, `/sdk` and the pre-`/docs` paths |
| `404.html` | served for an unmatched path (`not_found_handling`) |

`_headers` sets a CSP that allows exactly what the site uses: its own scripts,
one inline snippet (the `.js` class), the Google Fonts stylesheet, the font
files, and one `GET` to `api.github.com` (`js/stars.js`, the star count in the
header's button). Nothing else — no analytics, no frames, no form posts. If you
add analytics later, that header is the file to change, and forgetting it means
the script is blocked silently in the browser console.

## Checking a deploy

```bash
curl -sI https://brevis.sh/            | grep -i 'cache-control\|content-type'
curl -sI https://brevis.sh/css/styles.css | grep -i cache-control   # immutable
curl -so /dev/null -w '%{http_code}\n' https://brevis.sh/docs/cli/   # 200
curl -so /dev/null -w '%{http_code}\n' https://brevis.sh/nothing     # 404
curl -sI https://brevis.sh/github      | grep -i location            # the repo
```

The one worth checking after every content change is `/sitemap.xml` — it lists
all 32 URLs, and a missing one means a page was generated but not linked.

## The other two paths

**Wrangler from CI.** If the deploy should come out of GitHub Actions instead,
it needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository
secrets and a step running `npx wrangler deploy` in `site/`, which reads the
same `wrangler.jsonc`. More moving parts, and the reason to want it is usually
wanting the deploy gated on something the CI knows and Workers Builds does not.

**Netlify and Vercel** still work — `netlify.toml` and `vercel.json` are in this
directory and were not removed. `_headers` and `_redirects` are Netlify's own
formats, which Cloudflare adopted, so those two files serve both.

## Preview deployments

Workers Builds uploads every pull request as a preview version with its own
URL. That is worth keeping: the Lighthouse job in CI measures a local server,
and a preview URL measures the CDN, the real headers and the real font fetch.
