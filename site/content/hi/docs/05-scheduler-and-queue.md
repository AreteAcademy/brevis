brevis.sh run को **बनाने** और उसे **चलाने** को अलग रखता है। दो लूप साथ चलते हैं
और दोनों में से कोई भी दूसरे पर निर्भर नहीं।

```
scheduler                          queue
─────────                          ─────
reads the schedule
materialises the slot
creates the Run  ─────────────►  (pending in the database)
                                   claims it
                                   walks the graph
                                   executes each step
                                   records state and log
```

## अलग क्यों

जो एक ही लूप शेड्यूल भी करे और चलाए भी, उसमें एक बुरी बात है: जब चलाने वाला हिस्सा
अटकता है, शेड्यूलिंग भी उसके साथ रुक जाती है। अगले बारह घंटे के slot बस बनते ही नहीं,
और किसी को तब तक पता नहीं चलता जब तक कोई ऐसा डेटा न ढूँढे जो कभी पहुँचा ही नहीं।

दोनों अलग हों तो:

- **शेड्यूलर** बंद हो सकता है और कतार जो बन चुका है उसे खाली करती रहती है;
- **कतार** बंद हो सकती है और slot बनते रहते हैं, उसके लौटने पर चलाए जाने के लिए;
- **दोबारा प्रोसेस करना घड़ी पर निर्भर नहीं करता** — `backfill` बीते run उसी
  रास्ते से बनाता है जिससे cron बनाता।

## प्रोसेस

दोनों लूप एक ही कमांड में रहते हैं:

```bash
brevis scheduler --interval 5s --concurrency 4 --max-pods 10
```

| flag | डिफ़ॉल्ट | |
|---|---|---|
| `--interval` | `10s` | शेड्यूलर के चक्रों के बीच का अंतराल |
| `--concurrency` | `5` | एक साथ चलने वाले **run** |
| `--max-pods` | `5` | कुल मिलाकर एक साथ चलने वाले **steps** |

`--concurrency` और `--max-pods` जानबूझकर अलग चीज़ें गिनते हैं: अगर सीमा सिर्फ़ run पर होती,
तो तीन समानांतर steps वाले पाँच run पंद्रह pods बन जाते।

:::note `serve` schedules को नहीं बनाता
API प्रोसेस वही शेड्यूलर उठाती है, लेकिन **लूप के बिना** — वह सिर्फ़ इंटरफ़ेस से आने वाले
मैन्युअल ट्रिगर परोसने के लिए है, ताकि "शेड्यूलर run बनाता है" वाले नियम का मालिक एक
ही रहे। Schedules चलें, इसके लिए साथ में एक `brevis scheduler` चलना चाहिए।
:::

## परिभाषा का स्नैपशॉट

जब शेड्यूलर कोई run बनाता है, तो वह **workflow की परिभाषा को run के भीतर** रख देता है।
Execution उसी स्नैपशॉट को पढ़ता है, डिस्क पर पड़ी YAML को नहीं।

कारण ठोस है: ट्रिगर और execution के बीच किसी ने फ़ाइल बदलकर deploy कर दी हो सकती है।
स्नैपशॉट के बिना, 05:00 पर एक परिभाषा के साथ बना run 05:02 पर दूसरी परिभाषा के साथ चलता —
और लॉग के पास फ़र्क समझाने का कोई तरीका न होता।

## Retries

विफल run की **तीन बार** कोशिश होती है, और देरी हर बार **दोगुनी** होती है: डिफ़ॉल्ट के साथ वे
**0s, 30s और 1m30s** पर पड़ती हैं।

```bash
brevis scheduler --max-attempts 3 --retry-backoff 30s --retry-backoff-max 1h
```

| flag | डिफ़ॉल्ट | |
|---|---|---|
| `--max-attempts` | `3` | प्रति run प्रयास, पहले को मिलाकर |
| `--retry-backoff` | `30s` | पहली देरी, उसके बाद हर प्रयास पर दोगुनी |
| `--retry-backoff-max` | `1h` | उस देरी की ऊपरी सीमा |

प्रोसेस boot पर यह समय-सारणी छापती है, ताकि इसे दो संख्याओं से निकालना न पड़े:

```
scheduler and dispatcher are up  max_attempts=3 retry_backoff=30s retry_at="0s, 30s, 1m30s"
```

:::tip
**Rate-limit लगाने वाले vendor को ज़्यादा समय चाहिए।** इन pipelines के विफल होने का एक कारण
बाकी सबसे बड़ा है: अस्थायी upstream — ऐसी API जो "आपकी अनुरोध सीमा पूरी हो गई" कहकर 200 लौटाती है,
या warehouse quota की क्षणिक रुकावट। इन्हें साफ़ होने में करीब एक मिनट लगता है, और उससे पहले पूरा
हो जाने वाला retry ऐसा retry है जो कभी हुआ ही नहीं। `--retry-backoff 1m` प्रयासों को 0s, 1m और 3m पर रखता है।
:::

Retry प्रति **run** होता है, और सिर्फ़ उन steps को दोबारा चलाता है जो विफल हुए — जो `dbt_build` विफल हुआ
वह अपने ऊपर के सफल fetch को दोबारा नहीं चलाता।

प्रयास सहेजा जाता है, वह प्रोसेस की स्थिति नहीं है। worker को रीस्टार्ट करने से उस run के बारे में जो पहले
से पता था वह मिटता नहीं।

**Run** का प्रयास क्रमांक pod के नाम में जाता है। इसके बिना, retry run को शून्य से शुरू करता, पिछले प्रयास
के pod से उसी नाम पर टकराता और हमेशा के लिए `Pending` में अटका रहता।

## Backfill

पहले से प्रकाशित workflow के बीते slot बनाता है:

```bash
brevis backfill daily --from 2026-01-01 --to 2026-01-31
brevis backfill daily --from 2026-01-01 --to 2026-01-31 --param load_full=true
```

```
  31 run(s) de backfill enfileirados para daily (2026-01-01 a 2026-01-31)
  rode `brevis scheduler` para executa-los
```

यह **कतार में डालता है, चलाता नहीं।** चलाना `scheduler` का काम है — वही अलगाव फिर से।
`--to` पूरे दिन को शामिल करता है।

## Landing से शुरू होना

कोई workflow इसलिए चल सकता है कि डेटा आया, इसलिए नहीं कि घड़ी ने कहा:

```yaml
trigger:
  on_landed:
    - bigquery://acme-prod/bronze/orders
    - bigquery://acme-prod/bronze/*
  debounce: 5m
```

हर step पहले से घोषित करता है कि उसने क्या लिखा, उस pipe पर जो चरणों को ढोती है — वही `/data` को
भरता है। Workflow इनमें से किसी एक नाम की सदस्यता लेता है और तब शुरू होता है जब उस पर कुछ उतरता है।

अंत में `/*` पूरे dataset की सदस्यता लेता है। यह `auto_table` के लिए है, जो हर route के लिए एक तालिका
बनाता है: जिन तालिकाओं को किसी ने घोषित नहीं किया उनके लिए सिर्फ़ dataset का नाम ही लिया जा सकता है।
यह `bronze/orders` से मेल खाता है, `bronze_raw/orders` से नहीं।

### विंडो, और दस landing एक run क्यों हैं

`debounce` एक झोंके को समेट देता है। पाँच मिनट के भीतर उतरी दस तालिकाएँ **एक** run शुरू करती हैं,
दस नहीं, और run बताता है कि कौन-सी:

```
BREVIS_AUTO_LANDED=bigquery://acme-prod/bronze/orders,bigquery://acme-prod/bronze/items
```

सटीक सूची `BREVIS_AUTO_PARAMS` में JSON के रूप में भी होती है, जिसे तब पढ़ना चाहिए जब किसी target में
अल्पविराम हो सकता हो।

विंडो इस आधार पर कटती है कि **engine ने landing कब दर्ज की**, इस पर नहीं कि step ने उसका होना कब बताया।
जो step उस क्षण की रिपोर्ट करता है जब उसकी query शुरू हुई, वह कुछ सच और कुछ पुराना बता रहा होता है,
और एक बिगड़ी घड़ी वरना एक झोंके को दो run में बाँट देती।

`debounce` छोड़ दें तो हर landing एक run शुरू करती है।

### यह क्या नहीं करेगा

**कोई workflow अपने ही write से कभी शुरू नहीं होता।** Engine ऐसी landing को छोड़ देता है जिसका लेखक
सदस्यता लेने वाला workflow ही है, और कारण लॉग करता है — इसके बिना, जो workflow उसी तालिका को पढ़ता
और लिखता है वह हमेशा के लिए खुद को ट्रिगर करता रहता।

इसे **चलने के समय** मना किया जाता है, फ़ाइल जाँचते समय नहीं, और यह भूल नहीं बल्कि सीमा है:
`brevis validate` फ़ाइलें पढ़ता है और कोई फ़ाइल यह घोषित नहीं करती कि step क्या लिखता है। Warehouse
का target कनेक्शन तय करता है, YAML नहीं। इसलिए `validate` ऐसे workflow को पास कर देता है जो runtime पर
मना कर दिया जाएगा, हर बार, कारण लॉग में लिखकर।

**पहला चक्र कुछ शुरू नहीं करता।** ट्रिगर उस क्षण से गिनना शुरू करता है जब वह चालू होता है, शेड्यूल की तरह —
वरना एक को प्रकाशित करते ही catalog के पूरे इतिहास की हर landing के लिए एक run चल पड़ता।

## अलर्ट

```bash
export BREVIS_SLACK_WEBHOOK='https://hooks.slack.com/services/...'
export BREVIS_UI_URL='https://brevis.example.com'
```

Webhook के बिना, प्रोसेस boot पर चेतावनी देती है कि विफलताओं की रिपोर्ट नहीं होगी। जो इंस्टॉलेशन चुपचाप
विफल होता है, उसका पता आम तौर पर ग्राहक को चलता है, टीम को नहीं।

`BREVIS_UI_URL` अलर्ट के भीतर run का लिंक बनाता है — इसके बिना अलर्ट बताता है कि क्या विफल हुआ, पर पाठक
को run हाथ से ढूँढना पड़ता है।
