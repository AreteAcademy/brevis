Одна команда измеряет весь gateway:

```bash
BREVIS_BENCH_IMAGE=areteacademy/brevis-gateway:0.11.0 ./bench/run.sh
```

Она поднимает Postgres, запускает gateway, нагружает его с помощью [k6], **ждёт,
пока буфер опустеет**, снимает собственный `/metrics` gateway и записывает
`bench/results/REPORT.md`.

## Три свидетеля, и важнее всего третий

k6 знает, что увидел производитель. Gateway знает, что он сделал. Нагрузочный
тест, располагающий только первым, не отличит быстрый gateway от такого, что
отвечает `202` и теряет принятое.

Поэтому отчёт ставит их рядом — и считает строки в Postgres:

| свидетель | события |
|---|---:|
| k6 получил `accepted` | 5 431 000 |
| gateway насчитал принятых | 5 431 000 |
| строки в Postgres | 5 431 000 |
| записи в dead letter | 0 |

Первые два — арифметика самого gateway: одно из ответа, который он написал,
другое из счётчика, который он увеличил, — и ошибка, теряющая события, могла бы
сохранять их согласованность **друг с другом**. Только база данных не
поверила нам на слово.

**Запуск, в котором эти три числа расходятся, считается проваленным**, какими
бы хорошими ни были перцентили.

контейнере на том же ядре, `auto_table[columns]` с `write: append`:

|---|---:|
| принято событий | **5 431 000** (135 768/с) |
| отправлено тела | 1156,7 МиБ за 40 с |
| `503` (backpressure) | 0 |
| p50 / p95 / p99 | 5,9 мс / 16,0 мс / 22,7 мс |
| доставлено пакетов | 1087, ни один не захоронен |

## Пороги — это и есть суть

k6 завершается с ненулевым кодом, когда порог нарушен, поэтому это **шлагбаум**,
а не диаграмма:

| порог | почему |
|---|---|
| `p95 < 500ms` | путь приёма не должен зависеть от задержки sink. Запрос, ожидающий `COPY`, — это именно тот дефект, против которого существует асинхронный канал. |
| `http_req_failed < 1%` | `503` допустим; тайм-аут или 5xx — нет. |
| `events accepted > 1000` | набор порогов проходит и против gateway, который ничего не ответил. |

Они намеренно мягкие: тест работает на той машине, которую выдал CI. Они ловят
**порядок величины**, а именно так выглядит регрессия, а не процент.

**`503` не является сбоем.** Это отказ gateway принять событие, которое ему
некуда положить, и повторить его безопасно: `ingestion_id` — это
зафиксированная функция события, поэтому то же тело, отправленное повторно, —
та же запись. Если считать его ошибкой, backpressure выглядело бы как баг.

## Чего он не измеряет

- **Не BigQuery.** Место назначения — Postgres в контейнере. Квота load-задач
  хранилища, задержка фиксации и конкурентность DDL в этих цифрах отсутствуют и
  не могут присутствовать.
- **Не надёжность хранения.** `durability: memory` — единственный уровень,
  поэтому `202` означает *принято в RAM*. Измеряется, как быстро это
  происходит, но не то, что переживёт `SIGKILL`.
- **Не ваше оборудование.** Читайте это как форму и соотношение.

## Локальное облако по профилям

```bash
docker compose -f docker-compose.drivers.yml --profile gcp up -d
docker compose -f docker-compose.drivers.yml --profile all up -d
```

Один файл с профилями, а не по файлу на облако: два файла — это два имени
проекта, а `postgres` в обоих уже однажды заменил базу данных разработки
engine.

### floci покрывает BigQuery меньше, чем кажется

Измерено, а не предположено:

| | |
|---|---|
| создать датасет и таблицу | ✅ |
| `timePartitioning` и `clustering` сохраняются | ✅ — форма бага `0.9.1` |
| `PATCH` столбца | ✅ — эволюция `auto_table` |
| `insertAll` | ✅ |
| запросы | ✅, только при смонтированном `/var/run/docker.sock` |
| **load-задачи** | ❌ `Only QUERY jobs are supported by the floci BigQuery emulator` |

SDK пишет в BigQuery **только** через load-задачи. Поэтому floci проверяет
каждую строку `auto_table`, которая превращает payload в DDL, — и **ни одной
записи Brevis**. Это всё ещё та половина, у которой сегодня нет локального
теста, и она стоит того, чтобы её иметь. Но зелёный набор тестов против floci
не означает, что BigQuery работает.
