Engine — это один бинарный файл с подкомандами, а не несколько бинарных
файлов: API, планировщик и воркеры — роли одной системы, а один бинарный файл
означает одну версию, один образ и один путь сборки.

```
brevis [command] [flags]
```

| команда | база данных | учётные данные вне `local` | роль |
|---|---|---|---|
| [`serve`](#serve) | **да** | **обязательны** | API + интерфейс |
| [`scheduler`](#scheduler) | **да** | **обязательны** | оба цикла |
| [`migrate`](#migrate) | **да** | **обязательны** | схема |
| [`publish`](#publish) | **да** | **обязательны** | сохраняет workflow и расписание |
| [`backfill`](#backfill) | **да** | **обязательны** | повторно обрабатывает диапазон |
| [`cancel`](#cancel) | **да** | **обязательны** | останавливает запуск |
| [`run`](#run) | нет | — | запускает сразу, на самом экземпляре |
| [`validate`](#validate) | нет | — | проверяет YAML workflow |
| [`brand`](#brand) | нет | — | проверяет YAML брендинга |
| [`hash`](#hash) | нет | — | генерирует хеш пароля |
| [`version`](#version) | нет | — | версия, коммит, сборка |

Первые шесть загружают конфигурацию, которая **падает при старте** без
`BREVIS_DATABASE_URL`. Остальные пять — нет, поэтому `validate` работает в CI,
где Postgres нет.

Эти же шесть наследуют правило об учётных данных: при `BREVIS_ENV`, отличном от
`local`, запуск без трёх переменных аутентификации — **ошибка при старте**.

## serve

Поднимает HTTP API и интерфейс. Флагов нет — всё берётся из окружения.

```bash
brevis serve
```

Корректно завершается по `SIGINT`/`SIGTERM`, поэтому развёртывание не
обрывает запросы, находящиеся в обработке. Этот процесс **не материализует
расписания**: для этого рядом нужен `brevis scheduler`.

`CMD` образа `api` (distroless, без оболочки).

---

## scheduler

Оба цикла: планировщик материализует расписания в запуски, диспетчер берёт из
очереди и исполняет.

```bash
brevis scheduler --interval 5s --concurrency 4 --max-pods 10
```

| флаг | тип | по умолчанию | |
|---|---|---|---|
| `--interval` | duration | `10s` | интервал между циклами |
| `--concurrency` | int | `5` | одновременные **запуски** |
| `--max-pods` | int | `5` | одновременные **шаги** в сумме |

`CMD` образа `worker` (alpine с оболочкой, потому что шагам `run:` она нужна).

## alert

Доставляет алерты, записанные планировщиком. Третий процесс рядом с `serve` и
`scheduler`.

```bash
brevis alert --interval 1s --max-attempts 6
```

| флаг | тип | по умолчанию | |
|---|---|---|---|
| `--interval` | duration | `1s` | интервал между циклами доставки |
| `--max-attempts` | int | `6` | попыток до того, как алерт будет записан как недоставленный |

**Он существует из-за того, где записывается алерт, а не потому, что доставка
заслуживает отдельного процесса.** Планировщик записывает алерт в той же
транзакции, что и сбой, который его оправдывает: либо у запуска закончились
попытки и алерт существует, либо не произошло ни того, ни другого. Затем
что-то должно разбирать эту таблицу, и оно должно пережить как сбой Slack, так
и собственный перезапуск. Раньше сбойный webhook означал строку в журнале и
алерт, который попросту исчезал.

Он отказывается стартовать без настроенного канала (`BREVIS_SLACK_WEBHOOK`).
Процесс доставки, которому некуда доставлять, опустошает outbox в состояние
«недоставлено» так же быстро, как тот наполняется, а эти строки выглядят точно
так же, как отказ со стороны Slack.

Алерт, от которого он отказался, **сохраняется**: «поднят, не доставлен, 4
попытки, 403 от Slack» — важная строка, потому что это случай, когда кто-то
ждёт сообщения, которое не придёт.

`CMD` образа `worker`.

## report

Отправляет периодическую сводку о том, что выполнялось.

```bash
brevis report --window 168h              # sends it
brevis report --window 168h --dry-run    # prints it, sends nothing
```

| флаг | тип | по умолчанию | |
|---|---|---|---|
| `--window` | duration | `168h` | насколько далеко назад смотреть |
| `--dry-run` | bool | `false` | вывести вместо отправки |

**Команда**, а не цикл, и в этом разница между отчётом и алертом: она
запускается из CronJob, поэтому нет нового цикла, нового состояния и выбора
лидера — в кластере уже есть планировщик. `--dry-run` — способ, которым
начинают доверять еженедельному сообщению: читая, что оно сказало бы.

Она **не** проходит через outbox алертов. У них общий канал доставки и больше
ничего: потеря алерта — это сбой, о котором никто не узнает, а пропуск
сводки за одну неделю — это сводка за следующую.

Сообщение содержит запуски, успехи, сбои, пайплайны, чаще всего падавшие и
самые долгие, а также строки и байты, о которых сообщил SDK. Оно **не**
содержит CPU и память и не выводит для них нули — engine их не собирает, и
сообщение указывает, где они на самом деле находятся.

Пустое окно говорит об этом, а не сообщает 100%. Доля успеха из ничего — самое
успокаивающее число, которое может вывести отчёт, и наименее правдивое: пустая
неделя обычно означает, что планировщик не работал.

`deployments/kubernetes/report.yaml` запускает её еженедельно.

## migrate

```bash
brevis migrate up      # applies what is missing
brevis migrate down    # reverts the last one
brevis migrate status  # shows the state
```

Принимает ровно один аргумент. Миграции встроены в бинарный файл и применяются
отдельной подкомандой — **`serve` никогда не изменяет схему**.

## validate

Проверяет один или несколько файлов workflow. Принимает файл **или каталог**.

```bash
brevis validate examples/
```

```
  ok    daily_analytics              dag  5 steps, 5 dependencias  (manual)
  ok    hello                        dag  4 steps, 4 dependencias  (manual)
```

Она не обращается к базе данных и не запускает сервер, поэтому работает в
редакторе и в CI. Завершается с ненулевым кодом и подсчитывает число сбоев.

## run

Запускает workflow **сразу, на самом экземпляре**: без очереди, без базы
данных, без планировщика.

```bash
brevis run examples/hello.yaml
brevis run wf.yaml --param load_full=true --retries 3 --timeout 5m
```

| флаг | тип | по умолчанию | |
|---|---|---|---|
| `--param` | повторяемый | — | `key=value` для объявленного параметра |
| `--workdir` | string | каталог файла | рабочий каталог шагов |
| `--retries` | int | `1` | попыток на шаг (`1` = без повторов) |
| `--timeout` | duration | `0` | тайм-аут на шаг (`0` = без ограничения) |

`--param` без `=` — это **ошибка**, а не предупреждение: `--param load_full`,
с забытым значением, выполнился бы со значением по умолчанию — и оператор
считал бы, что значение применено.

:::warning Четыре ограничения
`run` работает только при `BREVIS_ENV=local`; шаг с `image:` выполняется на
самом экземпляре и сообщает об этом; реестра задач Go нет, поэтому `action:`
для незарегистрированной задачи падает с перечислением доступных; а `run` не
читает `BREVIS_HOSTS`, поэтому шаг с `host:` здесь вообще не может
выполниться — он падает с названием хоста, даже если переменная задана.
:::

## publish

Сохраняет workflow и их расписания в базе данных. Принимает файл или каталог.

```bash
brevis publish examples/hello.yaml
brevis publish workflows/ --project acme --prune
```

| флаг | тип | по умолчанию | |
|---|---|---|---|
| `--project` | string | `default` | slug проекта |
| `--prune` | bool | `false` | удаляет из проекта workflow, отсутствующие в списке |

С `--prune` история удалённых workflow сохраняется.

## backfill

Материализует прошлые слоты уже опубликованного workflow. Он **ставит в
очередь, но не исполняет.**

```bash
brevis backfill daily --from 2026-01-01 --to 2026-01-31 --param load_full=true
```

| флаг | | |
|---|---|---|
| `--from` | **обязателен** | дата начала, `YYYY-MM-DD` |
| `--to` | **обязателен** | дата окончания, `YYYY-MM-DD` |
| `--param` | | применяется к **каждому** слоту диапазона |

`--to` включает весь день: внутри конец становится `23:59:59` этой даты.

## cancel

Отменяет запуск, который ещё ожидает или выполняется. В ленте событий в
качестве автора отмены указан `cli`.

```bash
brevis cancel 3f1c9a52-6d0e-4b7a-9c41-2b8e5d7f0a13
```

| ответ | что произошло |
|---|---|
| `canceled` | запуск ждал в очереди; он покинул её и не будет выполнен |
| `cancel requested` | запуск выполняется; его диспетчер останавливает шаги в пределах `--cancel-poll` (2 с) |
| `already ended: <status>` | запуск уже завершился; ничего не меняется |

Отменённый запуск не повторяется. Несуществующий id — ошибка.

## gateway

Как gateway появляется в `/data`: его конфигурация, опубликованная как
осознанное действие — никогда не его трафик и никогда не во время выполнения.

```bash
gateway describe gateway.yaml > manifest.json   # the gateway's own binary
brevis gateway publish manifest.json
brevis gateway unpublish events_gateway
```

`publish` проверяет манифест целиком, прежде чем что-либо записать, называя
стрим и роль первой проблемы, и заменяет назначения этого gateway в одной
транзакции. `unpublish` удаляет выведенный из эксплуатации gateway и
завершается ошибкой, если gateway с таким именем не публиковался.

Как `brevis-sql-api` появляется в Данные → Endpoints: что каждый endpoint
принимает и читает, опубликовано как осознанное действие — никогда не его
трафик.

```bash
brevis-sql-api describe --config api.yaml --out manifest.json   # the API's own binary
brevis endpoints publish manifest.json
brevis endpoints unpublish metrics-api
```

`publish` проверяет манифест целиком, прежде чем что-либо записать, и заменяет
endpoints этого API в одной транзакции; имя, значение по умолчанию или
примечание, похожие на учётные данные, приводят к отказу во всём.

Отдельная команда, а не режим `brevis publish`, потому что у workflow и
gateway разная семантика наборов: `publish --prune` ни в коем случае не должен
затрагивать строки gateway.

## prune

Применяет политику хранения. Это **единственное**, что в Brevis что-либо
удаляет, и оно никогда не запускается само — его планирует оператор.

```bash
brevis prune --dry-run          # what would go, changing nothing
brevis prune
brevis prune --purge-after 0    # trim only, never delete a run
```

| флаг | по умолчанию | |
|---|---|---|
| `--trim-after` | `720h` | очищает журнал, фазы и опубликованный вывод |
| `--purge-after` | `8760h` | удаляет запуск целиком; `0` — никогда не удалять |

## brand

Проверяет файл брендинга, не запуская сервер.

```bash
brevis brand brand.yaml
```

```
  ok    Brevis · Orquestração
        logo      /assets/logo.svg  (simbolo embutido)
        destaque  #aa8450
        Powered by Brevis
```

Одно отличие в поведении от старта: **отсутствующий файл — это ошибка**. В
`serve` отсутствие означает «использовать идентичность по умолчанию»; тот, кто
попросил проверить путь, ожидает, что ему скажут, что такого пути нет.

## hash

Генерирует значение `BREVIS_AUTH_PASSWORD_HASH`.

```bash
brevis hash
```

Пароль читается из терминала **без эха**, никогда из аргумента: аргумент
виден в `ps` любого процесса и остаётся в истории оболочки. Пароли короче 12
символов отклоняются.

Хеш выводится один в **stdout**, а подписи — в **stderr**, поэтому
`brevis hash > hash.txt` сохраняет только то, что важно.

## version

```bash
brevis version
```

```
brevis 0.11.2
  commit  bb832ff
  build   2026-09-05T12:00:00Z
  go      go1.25.7 darwin/arm64
```

При сборке напрямую через `go build` выводится `brevis dev` без коммита и
даты — и отличить это от релизного артефакта важно, когда кто-то сообщает о
странном поведении.
