Workflow может объявлять **параметры запуска**: значения, которые меняются
между двумя запусками без изменения файла.

## Объявление

```yaml
params:
  - name: load_full
    type: boolean
    default: "false"

  - name: start_date
    type: string
    pattern: '^\d{4}-\d{2}-\d{2}$'

steps:
  - id: run
    run: dbt build --vars '{"load_full":"{{ .load_full }}"}' --select bronze+
```

| поле | | |
|---|---|---|
| `name` | **обязательно** | имя, используемое в шаблоне и в `--param` |
| `type` | | `string`, `boolean`, `integer` или `list|<type>` для нескольких значений |
| `default` | | используется, если запуск не передал значение |
| `pattern` | | регулярное выражение, которому должно соответствовать значение |
| `title` | | подпись, которую показывает форма, до 60 символов; иначе имя |
| `group` | | объединяет параметры в форме, до 60 символов |
| `warn` | | во что обходится значение, отличное от значения по умолчанию, показывается под полем, до 200 символов |
| `uses` | | ключ коннектора, к которому относится параметр (`bigquery`, `postgres`), для его логотипа |

Параметр **без `default`** обязателен: запуск, не передавший его, падает до
выполнения любого шага.

`title`, `group`, `warn` и `uses` определяют, как форма показывает параметр, и
**ни одно из них не меняет допустимые значения**. Каждое — одна строка; `uses`
— строчные буквы, цифры и `-`. Публикация отклоняет всё остальное с названием
параметра.

```yaml
params:
  - name: load_full
    type: boolean
    default: "false"
    title: Full load
    group: Load
    warn: reprocesses the whole table; it costs
    uses: bigquery
```

## Список значений

`list|<type>` объявляет параметр, несущий много значений: таблицы для загрузки,
слои для пересборки, окна для backfill:

```yaml
params:
  - name: tables
    type: list|string
    default: "users,orders"

  - name: layers
    type: list|string
    enum: [bronze, silver, gold]     # an enum restricts each ITEM
    default: "bronze"

  - name: days
    type: list|integer
    default: "1,7,30"
```

Элемент может быть `string`, `integer` или `boolean`. Каждый элемент проверяется
отдельно, поэтому `list|integer` со значением `1,x,30` падает с указанием
**элемента 2**, а не всего значения.

Везде это **одна строка через запятую**: в базе данных, в
`BREVIS_RUN_PARAMS` и в команде. Именно поэтому это работает в шаге без
каких-либо особых случаев —

```yaml
run: dbt build --select {{ .tables }}      # dbt build --select users,orders
```

— и именно поэтому запятая не может встречаться внутри элемента. Пустой элемент
и повторяющийся тоже отклоняются: повтор молча удваивает всё, что шаг делает на
каждый элемент.

### Как массив, в шаге

```go
for _, table := range p.Run.ParamList("tables") {
    load(table)
}
```

```python
from brevis import run

for table in run.param_list("tables"):
    load(table)
```

Обе возвращают `[]` для параметра, который никто не заполнил, а не список с
одной пустой строкой: итерация по «нечего делать» ничего делать не должна.
Элементы возвращаются как строки, включая `list|integer`, потому что шаг лучше
библиотеки знает, что делать с числом.

### В интерфейсе

Список с `enum` отображается как флажки, которым не нужен JavaScript и которые
браузер отправляет по одному значению на каждый отмеченный флажок. Без `enum`
это текстовое поле, элементы которого становятся удаляемыми метками, а при
выключенном JavaScript оно остаётся полем со значением `users,orders` — именно
то, чего ожидает сервер.

### В командной строке

```bash
brevis run wf.yaml --param tables=events,sessions --param days=1,30
```

:::note Более старый engine его не прочитает
Тип сохраняется вместе с workflow, а engine, выпущенный до этой функции,
отклоняет `list|string` при публикации как неизвестный тип. Обновите engine
перед публикацией workflow, использующего такой параметр.
:::

## Использование в команде

Значение попадает в `run` через шаблон, в двойных фигурных скобках с точкой:

```yaml
run: ./load.sh --since {{ .start_date }}
```

## Передача в командной строке

```bash
brevis run wf.yaml --param load_full=true
brevis run wf.yaml --param load_full=true --param start_date=2026-01-01
```

`--param` можно повторять. Ввод без `=` — это **ошибка**:

```
erro: --param "load_full": use chave=valor
```

Это сделано намеренно. `--param load_full`, с забытым значением, выполнился бы
со значением по умолчанию — и оператор считал бы, что backfill прошёл с тем
параметром, который он имел в виду.

## В backfill

Значения применяются к **каждому** слоту диапазона. Это центральный сценарий:
«переобработать весь январь с `load_full=true`».

```bash
brevis backfill daily --from 2026-01-01 --to 2026-01-31 --param load_full=true
```

## В интерфейсе

У workflow с `params` вместо простой кнопки запуска появляется **форма**. Поля
берутся из объявления, а `pattern` проверяется до отправки.

## В окружении шага

Параметры запуска также попадают в **окружение** каждого шага, с префиксом.
Это нужно, чтобы загрузчик, написанный с помощью [SDK](/docs/sdk/), мог их
видеть, не получая ничего в виде аргумента:

```go
Before: func(ctx context.Context, p *sdk.Pipeline) error {
    if p.Run.Params["load_full"] == "true" {
        p.Source.URL += "&full=1"
    }
    return nil
},
```

## Авто-параметры

Каждый запуск также несёт **авто-параметры**: значения, которые engine
вычисляет сам. Их никто не объявляет, они есть у каждого запуска, и они
показаны на экране запуска.

Важнее всего `adjusted_at`, и баг, который он устраняет, стоит назвать.
Загрузчик читает `now()`, вычитает своё окно и запрашивает у вендора последние
два часа. Для запуска, начавшегося вовремя, это верно. Для запуска, который
очередь задержала на сорок минут, это неверно на сорок минут — и эти сорок
минут принадлежат **ни одному запуску**, потому что следующий слот тоже читает
собственный `now()`. Ничего не падает; данных просто нет, и это обнаруживается
спустя недели.

Поэтому engine передаёт часы. Читайте `adjusted_at` там, где вы прочитали бы
`now()`:

| параметр | | |
|---|---|---|
| `adjusted_at` | всегда | часы, которые должен читать этот запуск: слот, если он есть, иначе время старта |
| `date` | всегда | `adjusted_at` в виде `YYYY-MM-DD`, UTC — партиция, папка, `WHERE` |
| `delay_seconds` | всегда | насколько эта попытка опоздала относительно своего слота; `0` при ручном запуске без слота |
| `previous_error` | всегда | предыдущий запуск не завершился успешно |
| `scheduled_at` | при наличии слота | слот, который запросил cron |
| `started_at` | | когда началась эта попытка; повторная попытка сдвигает его |
| `interval_start` | при наличии слота | **предыдущий** слот |
| `interval_end` | при наличии слота | этот слот, **исключая** его |
| `previous_success_at` | | слот последнего запуска, завершившегося успешно |

У запуска есть слот, когда его создало расписание, когда его создал backfill
или когда его запустили вручную **для прошлого слота**: поле `slot` триггера
(`2026-10-27T04:00:00Z`) повторно запускает этот слот с параметрами этого слота.
Слот, который cron никогда не запускает, отклоняется с указанием ближайшего
предшествующего.

**Все метки времени здесь в UTC**, записаны в RFC 3339 с `Z`, и экран запуска
тоже показывает их в UTC — поэтому страница и `$BREVIS_AUTO_ADJUSTED_AT` никогда
не расходятся. `date` — это **день по UTC**, который для workflow, чей слот
пересекает полночь UTC, не совпадает с локальным днём: `0 22 * * *` в
`America/Sao_Paulo` имеет `date` следующего дня. `ds` в Airflow ведёт себя так
же по той же причине — слот есть момент времени, а у момента времени есть один
день только после выбора часового пояса.

`interval_start` и `interval_end` определяются **cron**, а не историей: backfill
слота из марта даёт окно, которое было в марте, а не окно, которое сегодня
описывают запуски этого workflow. Пайплайн, запрашивающий `[start, end)`, никогда
не пересекается и не оставляет пробелов, как бы поздно он ни запускался и как
бы часто ни повторялся.

Это **снимок**, вычисляемый при старте запуска и сохраняемый в нём.
`previous_error` — факт о моменте, когда этот запуск начался; пересчёт завтра —
после того как предыдущий запуск был повторён и прошёл — отвечал бы на другой
вопрос под тем же именем.

### Как их читать

В shell-шаге — по одной переменной на значение, чтобы ничего не нужно было
разбирать:

```yaml
steps:
  - id: extract
    run: |
      curl "https://api.example.com/events?since=$BREVIS_AUTO_INTERVAL_START&until=$BREVIS_AUTO_INTERVAL_END" \
        > "/data/$BREVIS_AUTO_DATE.json"
```

Весь набор также лежит в `$BREVIS_AUTO_PARAMS` в виде одного JSON-объекта — для
шага, который предпочитает разобрать его один раз.

В Go [SDK](/docs/sdk/) читает их за вас:

```go
Before: func(ctx context.Context, p *sdk.Pipeline) error {
    start, end, ok := p.Run.Auto.Window()
    if !ok { // no schedule: fall back to a fixed window
        start, end = p.Run.Auto.Now().Add(-24*time.Hour), p.Run.Auto.Now()
    }
    p.Source.URL += "&from=" + start.Format(time.RFC3339) +
        "&to=" + end.Format(time.RFC3339)
    return nil
},
```

`Auto.Now()` — это часы, которые нужно читать вместо `time.Now()`. Вне engine —
загрузчик, запущенный вручную, — это *настенные* часы, поэтому для локальной
разработки не нужно делать никаких особых случаев.

В Python те же значения читает `pip install brevis`:

```python
from datetime import timedelta
from brevis import run

since, until = run.window() or (run.now() - timedelta(days=1), run.now())
df = fetch(since, until)
df.to_parquet(f"/data/{run.auto().date}.parquet")
```

`window()` возвращает `None`, если у workflow нет расписания, а не пару нулевых
значений времени: запрос с начала эпохи выбирает всё, и такой сбой не должен
быть тихим. `or` выше — это весь запасной вариант.

### В dlt читать вообще ничего не нужно

[dlt](https://dlthub.com) хранит собственный курсор в состоянии, которое пишет
в место назначения. Это состояние двигается только **вперёд**, что нормально,
пока вы не перезапускаете старый слот: курсор всё ещё указывает на сегодня,
поэтому backfill читает сегодняшнее окно, а собственный ответ dlt на это —
сбросить состояние.

Окно, которое передаёт Brevis, определяется cron, поэтому запуск за март даёт
мартовское окно, сколько бы раз он ни повторялся. dlt его примет — имена его
собственные, он читает их, прежде чем искать Airflow, и engine задаёт их при
каждом запуске по расписанию:

```python
@dlt.resource(primary_key="id")
def events(
    updated_at=dlt.sources.incremental(
        "updated_at",
        initial_value=datetime(1970, 1, 1, tzinfo=timezone.utc),
        allow_external_schedulers=True,   # this line is the whole integration
    )
):
    yield from api.events(since=updated_at.start_value, until=updated_at.end_value)
```

`allow_external_schedulers=True` — это вся интеграция. `$DLT_INTERVAL_START` и
`$DLT_INTERVAL_END` становятся `initial_value` и `end_value` в dlt, полуоткрытые
с обеих сторон: строка ровно на начале входит, строка ровно на конце — нет, и
именно поэтому последовательные слоты не оставляют пробелов и не пересекаются.

Инкрементальная загрузка с `end_value` **не трогает сохранённое состояние**.
Это важнее всего: повторный запуск одного слота идемпотентен, а backfill за март
не сдвигает курсор, от которого зависит ночной запуск.

Две вещи, которые нужно знать, чтобы это заработало:

- **Курсор должен быть datetime, а не строкой.** dlt не приводит `text`-курсор
  для сравнения и вообще отказывается подключаться к планировщику, выдавая
  `JoinSchedulerError`, который не очевидно говорит об этом. Преобразуйте его в
  ресурсе — `add_map` — или задайте тип `initial_value`, как выше.
- **Workflow без расписания ничего не передаёт**, и тогда dlt выбрасывает
  `ExternalSchedulerNotAvailable`, а не тихо откатывается к своему курсору.
  Если пайплайн должен работать в обоих режимах, оставьте
  `allow_external_schedulers` выключенным и передавайте окно сами из
  `run.window()`.

Объявление `tools: [dlt]` для шага — отдельная вещь, она лишь рисует метку на
графе — окно передаётся в любом случае.

## Снимок

Параметры сохраняются **в запуске**, а не читаются из workflow во время
исполнения. Запуск несёт вход, с которым его запустили, и журнал январского
запуска продолжает показывать январские значения, даже когда значение по
умолчанию изменилось.
