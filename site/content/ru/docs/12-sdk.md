Когда задача шага — **забрать данные и куда-то загрузить**, Go SDK даёт вам
весь загрузчик в несколько строк. Это отдельный модуль, версионируемый
независимо от engine.

```bash
go get github.com/AreteAcademy/brevis/sdk@latest
```

Требуется Go 1.23 или новее — SDK передаёт строки потоком в виде `iter.Seq2`.

:::warning Не используйте `v0.1.0`
В неё попал `go.mod`, фиксирующий несуществующую ревизию, а прокси модулей Go
неизменяем. Начинайте с `v0.1.1`.
:::

## Три шага

```go
import (
	"github.com/AreteAcademy/brevis/sdk"
	"github.com/AreteAcademy/brevis/sdk/from"
	"github.com/AreteAcademy/brevis/sdk/to/bigquery"
)

rows, err := sdk.Extract(ctx, sdk.Source{
	From: from.HTTP{URL: "https://api.example.com/v1/events"},
})

rows = sdk.Transform(rows, sdk.Accept("id", "created_at", "amount"))

res, err := sdk.Load(ctx, rows, sdk.Target{
	To:      bigquery.Table{Dataset: "bronze", Name: "events"},
	Columns: []string{"id", "created_at", "amount"},
})
```

`Extract` читает, `Transform` преобразует, `Load` записывает. Каждый принимает и
возвращает последовательность — ничто не материализуется в памяти целиком.

![Схема работы SDK: sdk.Extract читает из HTTP API с помощью from.HTTP, sdk.Transform оставляет принятые поля, а sdk.Load записывает строки в таблицу BigQuery. Три вызова выполняются внутри вашего собственного шага.](/assets/flow-sdk.svg)

## Драйвер — это значение, а не настройка

`from.HTTP` несёт всё, что нужно HTTP-источнику: URL, заголовки, повторные
попытки, пагинацию и то, что означает ответ. `from.Files` несёт путь и формат.
Ни одному не приходится уступать место полям другого, поэтому нет структуры
источника, собирающей сорок опций, из которых каждый драйвер читает шесть.

Он также определяет, **что вы компилируете**. Go отсекает зависимости по
импортируемому пакету, но никогда по используемому полю:

| что вы импортируете | пакеты | AWS | Google |
|---|---|---|---|
| `sdk` | 190 | нет | нет |
| `sdk` + `from` | 194 | нет | нет |
| `sdk` + `from` + `to` (файлы) | 195 | нет | нет |
| `sdk` + `to/bigquery` | 456 | нет | **да** |
| `sdk` + `from` + `store/s3` | 265 | **да** | нет |

Целый файловый пайплайн — чтение и запись — стоит 195 пакетов и вообще ни одного
облачного SDK. **Драйвер с SDK вендора за спиной живёт в собственном пакете**,
поэтому BigQuery — это `to/bigquery`, а хранилища объектов — `store/s3` и
`store/gcs`.

## Источники и места назначения

| источник | пакет |
|---|---|
| HTTP | `from.HTTP` |
| файлы (локальные, S3, GCS) | `from.Files` |
| Postgres | `from/postgres` |
| MySQL | `from/mysql` |
| несколько источников | `from.Many` |

| место назначения | пакет |
|---|---|
| файлы | `to.Files` |
| BigQuery | `to/bigquery` |
| Postgres | `to/postgres` |
| MySQL | `to/mysql` |
| Redshift | `to/redshift` |
| Pub/Sub | `to/pubsub` |

Backend определяется схемой пути, а `Store` **передаётся снаружи**, а не
выбирается внутри драйвера:

```go
from.Files{Path: "s3://bucket/day=1/*.ndjson", Store: s3.New(client)}
to.Files{Path: "gs://bucket/landing/", Store: gcs.New(client)}
```

Именно это не даёт программе с локальными файлами скомпилировать ни одной
строки кода AWS или Google.

### Публикация в топик

`to/pubsub` — единственное место назначения, которое не таблица, и оно ведёт
себя иначе, о чём стоит знать, прежде чем использовать его: **оно ничего не
добавляет к тому, что отправляет.**

```go
Target: sdk.Target{
    To: pubsub.Topic{
        Project: "acme-prod",
        Name:    "orders",

        // Nil is the default, and it means NO attributes at all.
        Attributes: func(e sdk.Envelope) map[string]string {
            row, ok := e.Payload.(map[string]any)
            if !ok {
                return nil
            }
            return map[string]string{"orderId": fmt.Sprint(row["order_id"])}
        },
    },
},
```

Подписчик получает ваш payload байт в байт плюс ровно те атрибуты, которые вы
назвали. Ничего больше — ни `ingestion_id`, ни `provider`, никакого конверта.

Это правило, а не минимализм. Таблицу создаёт пайплайн, который в неё пишет,
поэтому SDK вправе решать, каковы её столбцы. **Топик — нет**: он существует до
вашего пайплайна, его подписчики написаны раньше, и их фильтры написаны раньше.
Атрибут, добавленный самовольно, — это Brevis, редактирующий чужой контракт, и
подписчик узнал бы об этом в три часа ночи.

Из этого вытекают три вещи:

- **Он никогда не создаёт топик.** Пайплайн, который может создать топик, может
  создать не тот, и в отличие от таблицы с опечаткой этого никто не замечает —
  сообщения уходят куда-то, а подписчик, который должен был их получить,
  молчит.
- **`Schema`, `Dedup` и `PartitionBy` отклоняются** с названием опции. Они
  существуют для таблиц: `Schema` — это способ, которым место назначения создаёт
  таблицу, дедупликации нужна строка для замены, партиция — понятие таблицы.
  Ближайшее здесь — `OrderingKey`, но это другое: он группирует сообщения,
  которые должны *прийти* по порядку.
- **Сбой частичен.** Публикация не транзакционна, поэтому 48 000 сообщений,
  упавших на 31 000-м, *доставили* 31 000. Результат сообщает, что фактически
  ушло, а ошибка говорит, что повторный запуск — это повторная доставка:
  подписчик должен быть идемпотентным, а Pub/Sub в любом случае
  at-least-once.

Работающий пример на эмуляторе:
[`examples/13-pubsub`](https://github.com/AreteAcademy/brevis/tree/master/examples/13-pubsub).

## Весь загрузчик целиком

`sdk.Run` берёт на себя флаги, `-dry-run`, журналирование, повторные попытки,
пагинацию, происхождение данных, создание таблицы и код завершения. В файле
остаётся только то, что специфично для этого источника:

```go
package main

import (
	"time"

	"github.com/AreteAcademy/brevis/sdk"
	"github.com/AreteAcademy/brevis/sdk/from"
)

func main() {
	sdk.Run(sdk.Pipeline{
		Source: sdk.Source{
			From: from.HTTP{
				URL:     "https://api.example.com/v1/events",
				Timeout: 15 * time.Second,
			},
			Guard:  sdk.RejectIf("error"),
			Expand: sdk.ArrayAt("results"),
		},
		Target: sdk.Target{
			Provider: "example",
			Entity:   "events",
			Key:      sdk.Key("id"),
			When:     sdk.Field("created_at"),
		},
	})
}
```

```bash
go run ./fetcher -dry-run   # extracts, counts rows and errors, writes nothing
go run ./fetcher
```

## Контекст запуска

Когда загрузчик выполняется **как шаг workflow**, engine добавляет в окружение
то, чего иначе знать не мог: первый ли это запуск, с какими параметрами он был
отправлен, какой это запуск. SDK читает это в `Pipeline.Run`:

```go
Before: func(ctx context.Context, p *sdk.Pipeline) error {
	if p.Run.Params["load_full"] == "true" {
		p.Source.From = from.HTTP{URL: base + "?full=1"}
	}
	return nil
},
```

При ручном запуске `Run` возвращается обнулённым — читать его необязательно, и
игнорирование ничего не стоит.

Без истории ответ на вопрос «это первый запуск?» всегда **нет**: создание
таблицы без уверенности хуже, чем отказ от создания.

### Часы

`p.Run.Auto` — это то, что engine вычислил об этом запуске, — [авто-параметры](/docs/parameters/#авто-параметры).
`Auto.Now()` — часы, которые нужно читать вместо `time.Now()`: на запуске по
расписанию это слот, поэтому они не сдвигаются, когда запуск опаздывает, и не
сдвигаются, когда запуск повторяется через три часа.

```go
Before: func(ctx context.Context, p *sdk.Pipeline) error {
	start, end, ok := p.Run.Auto.Window()
	if !ok { // no schedule: fall back to a fixed window
		start, end = p.Run.Auto.Now().Add(-24*time.Hour), p.Run.Auto.Now()
	}
	p.Source.From = from.HTTP{URL: base +
		"?from=" + start.Format(time.RFC3339) +
		"&to=" + end.Format(time.RFC3339)}
	return nil
},
```

При ручном запуске `Auto.Now()` — *это* настенные часы, а `Window()` возвращает
`false`, поэтому для локальной разработки особых случаев не нужно.

## Не путать с клиентскими библиотеками

Этот SDK — механизм ETL на Go: драйверы, пагинация, происхождение данных,
создание таблиц. [Клиентские библиотеки](/docs/libraries/) — другое:
тонкие клиенты, передающие шагу контекст запуска и часы, сегодня для Python, а
позже для Node.js и Rust. Шагу на pandas или dbt нужны они, а не этот SDK.

## Параметры, которые строят пайплайн

`p.Run.Params` читается внутри пайплайна, что слишком поздно для значения,
которое определяет, **чем пайплайн является**: один источник на штат, одна
таблица на арендатора. `Pipeline.Flags` разбирается внутри `Run`, так что тоже
слишком поздно по той же причине.

```go
func main() {
	sdk.Run(pipeline(sdk.ParamList("ufs")))
}
```

`sdk.Param` и `sdk.ParamList` сначала читают окружение engine, затем
`-param name=value`:

```bash
./fetch-stations -param ufs=SP,RJ
```

Побеждает окружение: под управлением engine оно и есть значение, а флаг,
оставленный в манифесте, не должен переопределять то, что ввёл оператор. Без
engine остаётся флаг, что лучше, чем каждый раз писать `BREVIS_RUN_PARAMS` в
виде JSON.

## Структура приземления

Пайплайн может приземлить **ту же таблицу, что приземляет gateway** — те же
столбцы и тот же `brevis_ingestion_id` — поэтому выбор между ними становится
решением о развёртывании, а не о схеме. Команда может читать оба вместе и
переходить от одного к другому без миграции.

```go
const table = "landing.orders"

sdk.Run(sdk.Pipeline{
    Source:    sdk.Source{From: from.HTTP(/* ... */)},
    Transform: []sdk.Transformer{sdk.Landing(table, sdk.LandingKey("id"))},
    Target: sdk.Target{
        To:     postgres.Table{DSN: dsn, Name: table, CreateTable: true},
        Schema: sdk.LandingSchema(sdk.LandingOptions{}),
    },
})
```

`sdk.LandingSchema` — это девять столбцов: восемь принадлежат структуре и один —
производителю. `sdk.Landing` заполняет их и кладёт запись целиком в `data`.
Добавляйте в схему собственные столбцы, если хотите, или берите
`sdk.LandingControlColumns` и давайте полям записи отдельные столбцы.

### Две формы: запись целиком или по столбцу на поле

То, что выше, — это форма **document**: запись попадает в `data` как JSON, и
таблица одна и та же, что бы ни содержала запись. Добавьте
`sdk.LandingColumns()`, и у каждого поля записи появится собственный столбец:

```go
sdk.Landing(table, sdk.LandingKey("source_key"), sdk.LandingColumns())
```

Тогда таблица — это `sdk.LandingControlColumns` плюс ваши столбцы, а **не**
`sdk.LandingSchema`, который несёт `data`:

```go
Target{
    To: postgres.Table{DSN: dsn, Name: table, CreateTable: true},
    Schema: append(sdk.LandingControlColumns(sdk.LandingOptions{Keyed: true}),
        sdk.Column{Name: "source_key", Type: sdk.TypeString},
        sdk.Column{Name: "series", Type: sdk.TypeString},
        sdk.Column{Name: "data", Type: sdk.TypeString},
        sdk.Column{Name: "valor", Type: sdk.TypeString},
    ),
}
```

**Эти столбцы объявляете вы.** SDK никогда не выводит схему, и эта опция этого
не меняет: она определяет, как строится *строка*, но никогда — чем является
таблица. Gateway выводит схему, потому что его производитель — посторонний,
который присылает всё, что у него есть; здесь автор пайплайна знает форму и
записывает её в диффе, который кто-то просматривает.

Это та же форма, которую gateway приземляет как
[`shape: columns`](/docs/ingestion-sinks/#две-формы-один-контракт), тем же
кодом — те же столбцы, те же значения, тот же `brevis_ingestion_id`.

**Имя поля должно быть допустимым именем столбца**: буква или подчёркивание,
затем буквы, цифры и подчёркивания. Это правило BigQuery, самое узкое из четырёх
мест назначения, поэтому имя, проходящее здесь, работает везде. Запись с
`my-field` отклоняется по имени до того, как что-либо записано. У формы
document такого правила нет — дефис вполне допустим как ключ JSON.

**По умолчанию он не разворачивает вложенность.** Вложенный объект становится
ОДНИМ столбцом `JSON` под ключом, который его содержал: `customer` хранит
`{"id": 7, "uf": "SP"}`, а не `customer_id` и `customer_uf`. Массив — тоже
`JSON`. Запись, которой нужна одна строка *на элемент массива*, требует
`sdk.ArrayAt` в `Expand` источника — он выполняется до `Landing` и является
другой операцией с другим именем.
[`BREVIS_NORMALIZE_DATA`](#один-столбец-на-вложенное-поле) меняет первую половину
этого для всего развёртывания; массив остаётся `JSON` в любом случае:

```go
Source: sdk.Source{From: from.HTTP(/* ... */), Expand: sdk.ArrayAt("results")},
```

**`null` остаётся `NULL`**, никогда не `""`. Поле, присланное как null, и поле,
присланное пустым, — разные факты, и столбец потом не может их различить.

**`data` становится вашим.** В этой форме у структуры нет столбца с таким
именем, поэтому производитель с полем `data` — а именно его присылает серия
Bacen — получает собственный столбец с собственным значением. В форме
`document` это один ключ внутри JSON структуры.

### Префикс `brevis_` можно изменить

```
BREVIS_LANDING_PREFIX=acme
```

и восемь столбцов структуры становятся `acme_ingestion_id`, `acme_record_key` и
так далее. Если не задан, они такие, какими были всегда.

**Выбирайте его при создании таблицы, потому что последующая смена — это не
переименование.** SDK никогда не удаляет столбцы, поэтому поток, меняющий
префикс, не переименовывает восемь — он добавляет восемь и бросает восемь. Во
всех строках после этого в старом наборе стоят NULL, а

```sql
qualify row_number() over (partition by brevis_record_key
                           order by brevis_received_at desc) = 1
```

партиционирует по столбцу, в который уже ничего не пишется. Строки приходят,
дашборд замирает, и ничто ничего не логирует.

Поэтому таблица, уже несущая структуру под одним префиксом, **отклоняет**
загрузку, объявляющую другой, до извлечения, называя оба. Укажите новую
таблицу или сначала сами переименуйте восемь столбцов.

**Всё, что вы введёте, нормализуется**, так что ошибиться можно в одном
написании, а не в четырёх:

| вы задаёте | вы получаете |
|---|---|
| ничего или пусто | `brevis_` |
| `_NAME` | `name_` |
| `_NAME_` | `name_` |
| `NAME` | `name_` |

Обрезать `_` с обоих концов, привести к нижнему регистру, добавить ровно один.
Два значения отклоняются, а не угадываются: только подчёркивания, потому что
остался бы `ingestion_id` — именно тот столбец, который `sdk.IngestionID()`
пишет в каждом обычном пайплайне, — и всё, что не может начинать имя столбца.
**Процесс с непригодным значением не запускается**, что единственно честный
исход: альтернатива — таблицы, названные по префиксу, который вы заменяли.

**Он действует на ПРОЦЕСС, и в этом суть, а не ограничение.** Все потоки одного
gateway разделяют его, поэтому два sink не могут расходиться — как и схема,
объявляющая таблицу, и трансформер, который её заполняет.

**Зарезервированное правило движется вместе с ним.** При `acme_` производитель,
присылающий `acme_region`, отклоняется, потому что тот, кто может подделать
управляющий столбец, подделывает правдоподобный. А `brevis_region` становится
обычным полем.

`data` никогда не несёт префикс. Это столбец производителя, а не структуры.

### Один столбец на вложенное поле

```
BREVIS_NORMALIZE_DATA=true
```

и у полей вложенного объекта появляются собственные столбцы, как это делает
`json_normalize` в pandas — на один уровень:

```python
data = [
    {"id": 1, "name": {"first": "Coleen", "last": "Volk"}},
    {"name": {"given": "Mark", "family": "Regner"}},
    {"id": 2, "name": "Faye Raker"},
]
```

```
id  name_first  name_last  name_given  name_family  name
```

**Выбирайте до первой таблицы, потому что она не только ДОБАВЛЯЕТ столбцы.** Она
их переименовывает, а SDK никогда ни один не удаляет — поэтому старое имя
остаётся с уже лежащими в нём строками, а всё последующее приземляется в
новое, и запрос, который кто-то написал к нему, продолжает выполняться и
перестаёт видеть новые строки. Происходят два переименования:

- `userName` становится `username`, независимо от того, есть ли вложенность
- `name`, содержавший объекты, заменяется на `name_first` и `name_last`

Таблица, уже несущая любую из этих форм, **отклоняет** загрузку с этой опцией
до извлечения, называя оба столбца. Укажите новую таблицу или сначала сами
переименуйте столбцы.

**`name` может появиться и развёрнутым, и целым**, и пример выше это показывает:
третья запись несёт `name` как строку, поэтому в таблице есть `name_first`,
`name_last` И `name`. Поле, являющееся объектом в одной записи и скаляром в
другой, даёт оба.

**Один уровень, а массивы — это значения.** `{"a": {"b": {"c": 1}}}` — это `a_b`,
содержащий `{"c": 1}` — столбец `JSON`, а не `a_b_c`. `{"a": [1, 2]}` — это `a`,
тоже `JSON`. Записи, которой нужна одна строка на элемент массива, по-прежнему
нужен `sdk.ArrayAt`.

**Соединяется и приводится к нижнему регистру, без разбиения по camelCase.**
`userName` становится `username`, а не `user_name`, потому что у другого
прочтения нет согласованного ответа для аббревиатур — `HTTPStatus`, `userID`, —
и каждая библиотека расходится в этом с остальными.

**Коллизия отклоняется, а не разрешается.** `{"name_first": 1, "name":
{"first": 2}}` сделало бы один столбец из двух полей, а обход map в Go
случаен: если бы побеждало одно, тот же пакет давал бы в другом запуске другую
таблицу. Отказ называет оба.

**Зарезервированный префикс проверяется на столбце, а не на поле.** Производитель,
присылающий `{"brevis": {"stream": "x"}}`, иначе создал бы `brevis_stream` через
дверь, за которой проверка поля не следит. Он отклоняется с названием
`brevis.stream`, чтобы найти поле.

**Действует на ПРОЦЕСС**, как и префикс, и по той же причине: все потоки одного
gateway разделяют её, поэтому два sink не могут расходиться в отношении
таблицы, в которую могут писать оба. Применяется только к форме `columns` — при
`document` запись целиком попадает в один столбец `JSON`, и разворачивать
нечего.

### Текст, который уже является JSON

Столбец, объявленный как `sdk.TypeJSON`, получает JSON-**значение** — объект,
массив, число. В BigQuery строка кодируется целиком, поэтому Go `string` там
становится строковым литералом JSON, и столбец оказывается содержащим ТЕКСТ
вашего объекта, а не сам объект:

```sql
SELECT JSON_TYPE(payload) ...;            -- "string", not "object"
SELECT JSON_VALUE(payload, '$.a') ...;    -- NULL
```

Столбец правильного типа, а данные в нём недоступны, — худший из трёх исходов,
потому что ничего не падает. **Место назначения BigQuery отклоняет это** начиная
с `v0.74.0`, называя столбец.

Передавайте сам объект, когда он у вас есть. Когда то, что у вас есть, уже
является текстом JSON — столбец, прочитанный из другой базы данных, тело ответа,
которое вы не хотите заново разбирать, — скажите об этом:

```go
row["payload"] = sdk.JSONText(body)
```

Собственный `json.RawMessage` из `encoding/json` тоже работает и по той же
причине: оба записывают тот JSON, который держат, а не его строку в кавычках.

**Postgres и MySQL не затронуты и не отклоняют.** Их сервер разбирает строку в
столбец JSON и всегда так делал.

### Когда появляется поле, которого нет в таблице

Производитель добавляет поле, и загрузка останавливается, называя его: строка
несёт столбец, который никто не объявлял, а запись в место назначения, о нём не
упоминавшее, молча отбросила бы его. Этот отказ по умолчанию правилен — но в
таблице приземления это единственное изменение, которое не может сломать
читателя, и место назначения может его выполнить:

```go
postgres.Table{DSN: dsn, Name: table, Evolve: sdk.EvolveAdditiveFromPayload}
```

Тогда пакет **дополняет** ваше объявление: поле, которое он несёт, а объявление
нет, становится столбцом, `STRING`, если поле не объект и не массив, а в этом
случае `JSON`. Это то же правило и тот же код, которым gateway приземляет
`shape: columns`, поэтому оба дают одну и ту же таблицу.

Два других значения, и разница между ними в том, откуда берётся столбец:

| `Evolve` | добавляет |
|---|---|
| `sdk.EvolveNone` (по умолчанию) | ничего. Любое различие отклоняется, называя обе стороны |
| `sdk.EvolveAdditive` | столбец, который есть в вашем **объявлении**, но нет в таблице |
| `sdk.EvolveAdditiveFromPayload` | то же, плюс столбец, который несёт **пакет** |

**Только `ADD COLUMN`.** Столбец, исчезнувший из источника, перестаёт
записываться и остаётся в таблице; ничего не переименовывается, ничего не
удаляется, и ни один тип никогда не сужается. Это не пробел — таблица
приземления есть история, и единственное изменение, которое не может сломать
читающего её, — новый столбец, допускающий null.

**Оно дополняет объявление, но не заменяет его.** Если ничего не объявлено, оно
отклоняется до извлечения с названием таблицы: создание целой таблицы по
payload — другое решение, и SDK его не принимает. В структуре приземления вред
был бы конкретным — `brevis_received_at` получился бы текстом вместо метки
времени, а `brevis_loaded_at` вообще не путешествует в строке, так что замер
сквозной задержки попросту отсутствовал бы.

**SDK по-прежнему не выводит.** Тип берётся из ФОРМЫ поля, никогда из его
значения: `21129` и `8.89` оба объявляют `STRING`, поэтому в день, когда серия
опубликует целое число, ничего не изменится. Тип, считанный с первого пакета, —
это именно тот сбой, который призвано предотвратить это правило.

**И `null` ничего не решает — но остаётся в строке.** Это два разных вопроса, и
один ответ на оба стоил v0.77.0.

У null нет формы, поэтому **схеме** нечего читать: поле, пришедшее `null`, не
объявляет столбец, а столбец появляется с первой записи, несущей ЗНАЧЕНИЕ, с
формой этого значения. Иначе null стал бы `STRING` за неимением ответа, а первый
после него массив заставил бы место назначения отклонить весь пакет — без
миграции `STRING` в `JSON`, которая это исправила бы.

**Строка** несёт то, что прислал производитель, включая null. Иначе нельзя:
столбец, который вы ОБЪЯВИЛИ в `Target.Schema` и который пришёл пустым, должен
быть в строке, иначе проверка, сравнивающая объявление со строкой, читает цепочку,
перестав его выдавать, — и отклоняет загрузку. Именно это делала v0.77.0, и
именно это отменила 0.78.0.

Остальное решает место назначения: поле, равное null В КАЖДОЙ записи пакета и не
имеющее столбца в таблице, не записывается никуда и ничего не отклоняет. Null и
отсутствующее поле приземляются одним и тем же `NULL`, поэтому ничего не
теряется.

**Поле, меняющее форму, отклоняется, а не поглощается.** Если `valor` пришло
скаляром и сделало текстовый столбец, объект, пришедший позже, — смена рода, и
пакет останавливается — с собственным комментарием столбца в сообщении, чтобы
было видно, что никто его не объявлял. Переименуйте столбец или мигрируйте его
сами.

**В BigQuery два написания одного имени — один столбец.** BigQuery не различает
регистр столбцов: пакет с `nationalID` в одной записи и `nationalId` в другой
объявляет **один** столбец, а не два, и побеждает написание, первое в
отсортированном порядке, — `nationalID`, потому что `D` сортируется раньше `d`.
Не первое по приходу: повторённый тот же пакет не должен создавать столбец с
другим написанием. Объявление `createdat` для таблицы, в которой столбец
называется `createdAt`, — тоже тот же столбец, поэтому ничего не добавляется и
ничего не отклоняется.

**Одна запись, несущая оба написания, отклоняется с названием обоих.** У места
назначения один столбец, и одно из двух значений молча победило бы, поэтому
загрузка останавливается: переименуйте одно из них в `Transform` или отобразите
оба на одно поле. Две *записи*, каждая с одним написанием, допустимы — это
обычный трафик CDC, и именно его это правило призвано приземлять.

**Ничего не мигрируется.** Таблица, где уже есть два столбца, различающиеся
только регистром, сохраняет оба; ни один не переименовывается и не удаляется.

**Postgres и MySQL регистр не объединяют.** Там идентификатор в кавычках
различим, поэтому два написания — это два столбца, намеренно, и тот же
загрузчик, направленный на BigQuery, приземлит их в один.

**Каждый столбец, созданный пакетом, сообщает об этом в таблице.** Комментарий в
Postgres и MySQL, описание поля в BigQuery, с датой:

```
brevis: added from a batch on 2026-09-29; the type is the landing rule
(scalar text, object and array json), not a decision
```

Через полгода это единственное, что остаётся и отвечает на вопрос «когда
появился этот столбец и кто это решил». К тому времени строка журнала уже
ротирована.

**Это не режим.** `Target.Schema` по-прежнему — вы объявляете, чем является
таблица; это даёт вам уже существующую структуру вместо того, чтобы заставлять
вас её набирать. Ничто в SDK не ведёт себя иначе из-за того, что вы этим
воспользовались, а пайплайн, объявляющий собственную схему, не затрагивается.

**Пишите имя таблицы один раз.** Оно идёт в `Landing`, потому что это второй
слот id, и в место назначения, потому что туда идут строки. **Ничто не проверяет,
что они совпадают**: `Writer` знает собственную таблицу, но раскрывает её только
через `Describe`, то есть имя для журналов и ошибок, а id, построенный на нём,
привязал бы каждый уже записанный id к строке журнала. Если рассинхронизировать
их, строки приземлятся правильно, с id, выпущенными для таблицы, в которую никто
не писал. Они будут выглядеть нормально. Они не совпадут с id gateway.

**Три столбца равны `NULL`, и это честный ответ.** `brevis_stream` и
`brevis_gateway` называют то, чего у пайплайна нет, —
`brevis_gateway IS NULL` — способ отличить строку пайплайна от строки gateway.
`brevis_received_bytes` тоже `NULL`: у gateway он считает то, что пришло по сети,
включая конверт, а собственный JSON записи примерно на 30% меньше. Один столбец
с двумя значениями сделал бы сумму по строкам с обоих путей неверной на долю,
пришедшую с каждого. `length(data)` точно отвечает за версию пайплайна.

**Для слияния нужен `DedupKey`, а без него слияния нет вообще.** Каждый драйвер
сопоставляет по `ingestion_id`, если не сказано иное, а столбец идентичности
этой структуры — `brevis_ingestion_id`:

```go
Target{
    To:       postgres.Table{DSN: dsn, Name: table, CreateTable: true},
    Schema:   sdk.LandingSchema(sdk.LandingOptions{UniqueID: true, Keyed: true}),
    Dedup:    sdk.DedupMerge,
    DedupKey: sdk.LandingColumnID,
}
```

`UniqueID` ставит ограничение UNIQUE на id, а Postgres и MySQL оба отказываются
выполнять слияние без него — `ON CONFLICT` не с чем сопоставлять. `DedupKey`,
которого нет в вашей `Schema`, отклоняется до запуска чего-либо, потому что
слияние по столбцу, которого нет в таблице, ничего не сопоставляет, а слияние,
ничего не сопоставляющее, выглядит так же, как сопоставляющее всё, что должно.

**Зависит от места назначения, и сегодня MySQL не может.** В BigQuery нет
ограничений уникальности, и объявление отклоняется сразу. `string` в MySQL — это
`LONGTEXT`, а MySQL не индексирует `LONGTEXT` без длины, поэтому таблицу
приземления со слиянием там вообще нельзя *создать*:

```
Error 1170 (42000): BLOB/TEXT column 'brevis_ingestion_id' used in key
specification without a key length
```

В Postgres работает, потому что его `string` — это `TEXT`. В MySQL приземляйте
с `DedupNone` и разрешайте актуальную версию ниже по потоку, либо создайте
таблицу сами через `CreateSQL` со столбцом id заданной длины.

**Id адресуется по содержимому.** Одна и та же запись даёт один и тот же id с
любого пути, а изменённая запись — новый, и именно это делает повторный запуск
пустой операцией, а не дубликатом.
