Шесть мест назначения, и список намеренно явный: коннектор, который
*запланирован*, и коннектор, который *работает*, — разные вещи для того, кто
выбирает.

| sink | состояние | что такое запись | проверено на |
|---|---|---|---|
| `pubsub` | **работает** | одна публикация на пакет, атрибуты и ключ упорядочивания берутся из собственных полей события | эмуляторе |
| `postgres` | **работает** | `COPY FROM STDIN` или промежуточный `INSERT` в одной транзакции | настоящем Postgres |
| `mysql` | **работает** | многострочный `INSERT` в транзакции или `INSERT IGNORE` | настоящем MySQL |
| `files` | **работает** | объекты NDJSON в каталоге, `gs://` или `s3://` | файловой системе и S3 |
| `bigquery` | **работает** | строки загружаются или кладутся в промежуточную таблицу и `MERGE`-атся по `ingestion_id` | **только конфигурация — эмулятора не существует** |
| `redshift` | **работает** | пакет в S3, затем `COPY`, затем `MERGE` | **только конфигурация — эмулятора не существует** |

**Два из шести не проверены от начала до конца**, и таблица говорит об этом, а
не позволяет слову «работает» нести утверждение, которое никто не проверял. У
BigQuery и Redshift нет локального эмулятора, поэтому тестируются конфигурация,
отказы и драйвер под ними — что уже покрывает собственный набор тестов SDK.
Настоящее доказательство для каждого — первое использование в продакшене, и это
должен быть поток с невысокими ставками.

Неизвестный `type:` **отклоняется при старте** с перечислением того, что
содержит *этот бинарный файл*. Gateway, стартующий на sink, которого у него
нет, — это тот, что отбрасывает события по причине, которую никто не видит.

`gs://` и `s3://` — не отдельные коннекторы: `files` читает все три формы пути,
поэтому dead letter — это папка на ноутбуке и бакет в продакшене без изменений
здесь.

## Как записывает каждый

`write` **обязателен и никогда не имеет значения по умолчанию** для четырёх
мест назначения, пишущих в таблицу, потому что два режима действительно разные,
и только владелец таблицы знает, какой нужен:

| | `append` | `merge` |
|---|---|---|
| **postgres** | `COPY FROM STDIN` | `INSERT … ON CONFLICT (ingestion_id) DO NOTHING` |
| **mysql** | многострочный `INSERT` на блок | `INSERT IGNORE` |
| **bigquery** | строки загружаются (через GCS при превышении встроенного лимита) | `MERGE … WHEN NOT MATCHED THEN INSERT` |
| **redshift** | `COPY` из S3 | `COPY` в промежуточную таблицу, затем `MERGE` |

`merge` означает **одно и то же во всех четырёх**: идемпотентную вставку, и
**побеждает первая доставка**. Повторная доставка игнорируется, а не применяется
— что правильно для события, которое произошло один раз и не меняется, и
неправильно для строки, несущей изменяемое состояние.

Postgres и MySQL **требуют индекс `UNIQUE` по `ingestion_id`** для `merge` и
отклоняют без него, а не молча дописывают:

```sql
CREATE UNIQUE INDEX CONCURRENTLY ON landing.orders (ingestion_id);
```

Без индекса `ON CONFLICT` не с чем сопоставлять, и каждая повторная доставка
дублировалась бы в таблицу, чей владелец просил противоположного. Отказ — не
потерянный пакет: он повторяется, затем захороняется в dead letter с причиной и
командой `CREATE INDEX` в записи — пока кто-то создаёт индекс, никто не теряет
события.

**`upsert` отклоняется по имени.** `ON CONFLICT DO UPDATE`, где побеждает
*последняя* доставка, — это настоящий режим, который **не реализован**.
Принимать слово, а вести себя как `merge`, — именно тот сбой, который это поле
призвано предотвратить, поэтому конфигурация говорит об этом прямо.

## У каждого — то, что верно только для него

```yaml
# Postgres: schema-qualified name, and the table has to exist.
sink: {type: postgres, dsn_from: BREVIS_DSN, table: landing.clicks, write: merge}

# MySQL: no COPY, so throughput is an order below Postgres on the same
# hardware. Flush wider here.
sink: {type: mysql, dsn_from: BREVIS_DSN, table: landing.clicks, write: merge}

# BigQuery: no dsn_from. It authenticates with the pod's own credentials, which
# is what a workload identity is for. The name has no dots — the project and
# the dataset are their own fields.
sink: {type: bigquery, project: acme-prod, dataset: landing, table: clicks, write: merge}

# Redshift: two hops, not one. It is columnar, a row-by-row INSERT pays the cost
# of a block, and the only workable load is COPY from S3. So every batch becomes
# an object in the staging prefix and then a COPY — a stream flushing every
# second writes 86,400 objects a day. Flush much wider here.
sink:
  type: redshift
  dsn_from: BREVIS_RS_DSN
  table: landing.clicks
  staging: s3://acme-staging/gateway/
  iam_role: arn:aws:iam::123456789012:role/redshift-copy
  write: merge
```

`dsn_from` называет **переменную окружения**, содержащую строку подключения, а
не саму строку: DSN несёт пароль, а этот файл лежит в git. Это то же разделение,
которое делает `secrets:` в workflow.

`iam_role` — это роль, и драйвер **не примет ключ**: ключ в URL команды `COPY`
оказывается в журнале запросов кластера, который читают многие.

## Объявления столбцов нет

Gateway не отправляет список столбцов. Пайплайн объявляет собственный, потому
что у его строк одна форма, которую он контролирует; пакет gateway — это то,
что *N* клиентов прислали за одно окно сброса, и формам позволено различаться.

Драйвер определяет список по **самой таблице**, пересекая его с тем, что несёт
пакет, **до** обращения к серверу. Поле, которого в таблице нет, отклоняется с
сообщением, исправляющим ситуацию, а не падает посреди `COPY` с
`column "x" of relation "y" does not exist`; поле, которое пропустило одно
событие, записывается как `NULL`.

## Список импортов — это и есть выбор

Sinks **компилируются внутрь**, как и хуки, а бинарный файл регистрирует то, что
у него есть:

```go
func main() {
    sinks := gateway.NewSinks()
    sinks.MustRegister(postgres.Sink, postgres.New)
    sinks.MustRegister(files.Sink, files.New)
    gateway.Main(nil, gateway.WithSinks(sinks))
}
```

Компоновщик Go отсекает то, на что ничто не ссылается, поэтому бинарный файл,
который никогда не импортирует драйвер BigQuery, не несёт BigQuery — ни Arrow,
ни Storage Write API. Так `database/sql` работал всегда.

Это стоит того, как звучит:

| сборка | пакеты | бинарный файл |
|---|---|---|
| все шесть sinks, оба хранилища объектов, оба metastore | около 900 | 55,0 МБ |
| `postgres` + локальные `files` | около 240 | **10,2 МБ** |

Хранилища объектов — это **второй** реестр, потому что схема — это не место
назначения: `files` — это один sink, который пишет в каталог, в `gs://` и в
`s3://`, а сборка, пишущая только локально, не должна нести SDK AWS ради этого.

### Два опубликованных образа

| образ | содержит | pull (amd64) |
|---|---|---|
| `areteacademy/brevis-gateway:0.32.0` | шесть sinks, S3, GCS, Redis, memcached | 19,1 МБ |
| `areteacademy/brevis-gateway:0.32.0-slim` | `postgres`, локальные `files`, `auto_table` | **5,2 МБ** |

Оба из одной сборки одного дерева, поэтому два тега всегда указывают на один
коммит. `latest-slim` нет — `latest` уже тег, который никто не должен
разворачивать.

**Нужна другая пара?** `cmd/gateway-slim` — пятнадцать строк, а блок импортов
— вся его конфигурация. Скопируйте, измените импорты, соберите. Тот, кому нужен
хук, уже компилирует собственный бинарный файл, поэтому выбор sinks не стоит ему
ничего сверх этого.

### Отказ говорит, какую сборку вы держите

```
sink type "bigquery" is not one this binary carries (it has: files, postgres).
Sinks are compiled in, so this is a build that left it out rather than a
destination that does not exist.
```

Фиксированный список отправил бы этого человека искать ошибку конфигурации,
которой он не делал. То же верно для хранилища объектов: dead letter на
`s3://` в бинарном файле без backend S3 отклоняется **при старте** с названием
схемы, а не на первом пакете, который пришлось бы захоронить.

## Один маршрут, N таблиц, ничего не объявлено

```yaml
sink:
  type: auto_table
  shape: columns
  naming: {pattern: '^(app|svc)_[a-z0-9_]{2,40}$', allow: [app_, svc_], max_new_per_hour: 20}
  metastore: {type: redis, addr_from: BREVIS_METASTORE_ADDR, ttl: 60s}
  into: {type: bigquery, project: acme-prod, dataset: landing, write: merge}
```

`auto_table` **направляет, но не пишет**: пишет `into`, и у него нет `table` —
таблица берётся из каждого события. `into` с `table` отклоняется при старте,
потому что фиксированная таблица под маршрутизатором молча победила бы, и каждое
событие приземлялось бы в неё.

### Конверт

Тело — это **конверт**: управляющие поля сверху, запись внутри `data`.

```json
{
  "table_name": "app_orders",
  "description": "App orders",
  "operation": "INSERT",
  "unique_key": "id",
  "data": {
    "id": "A-1",
    "total": 150,
    "customer": {"id": 7, "uf": "SP"},
    "items": [{"sku": "X", "qty": 2}]
  }
}
```

| поле | | что это |
|---|---|---|
| `table_name` | **обязательно** | куда приземляется |
| `data` | **обязательно** | запись, и только она |
| `unique_key` | по умолчанию `id` | какое поле `data` идентифицирует запись — **обязательно при `merge`** |
| `operation` | по умолчанию `INSERT` | `INSERT`, `UPDATE` или `DELETE` |
| `description` | необязательно | **принимается, но пока не используется** — см. ниже |

`table_name`, стоявшее рядом с `total` и `customer`, было полем **транспорта**,
притворявшимся полем **записи**. Их разделение — то, как устроен каждый формат
CDC, — и именно оно делает возможным резервирование префикса, потому что теперь
есть одно место, в которое пишет только производитель.

### Ключ принадлежит `merge`, а не конверту

`unique_key` необязателен, и **обязателен** ли он, зависит от режима записи — ибо
два режима хотят разного:

| | |
|---|---|
| `write: merge` | **обязателен.** Режим существует, чтобы хранить одну строку на запись, а `brevis_record_key` — то, что значит «на запись»: `qualify`, определяющий текущую версию, партиционирует по нему. Таблица merge, полная строк без указания записи, — таблица, которую никто не может разрешить. |
| `write: append` | **необязателен.** Таблица append — это журнал, а запись журнала не обязана быть *о* какой-то записи: строка аудита, webhook, образец метрики. Требовать там `id` заставило бы производителей его выдумывать, что хуже, чем `NULL`, потому что выглядит настоящим. |

При `append` столбец создаётся допускающим null, и строка без ключа несёт
`NULL` — не `""`, это другой факт. А `brevis_ingestion_id` по-прежнему
существует: без ключа **ключом служит содержимое**, поэтому один и тот же
документ дважды — это один и тот же id.

**Название поля, которого нет в `data`, — ошибка в обоих режимах.** «Вы не
сказали» и «вы сказали то, чего нет» — разные ошибки, и проходит только первая:

```json
{"accepted":0,"rejected":["event 0: \"unique_key\" names \"pedido_id\" as this
 record's identity and \"data\".\"pedido_id\" is missing or empty. Drop
 \"unique_key\" to fall back to \"id\", or send the field"]}
```

**`description` читается, но сегодня никуда не попадает.** Оно есть в контракте
ради страницы приёма данных в консоли, которая не написана. Об этом сказано
здесь, потому что поле, принятое молча, — это поле, которое кто-то считает
сохраняемым.

### Восемь фиксированных столбцов плюс всё, что несёт запись

| столбец | | |
|---|---|---|
| `brevis_ingestion_id` | `STRING` | идентичность и ключ merge |
| `brevis_record_key` | `STRING` | `data[unique_key]` — о какой **записи** речь; `NULL` при `append` |
| `brevis_operation` | `STRING` | `INSERT`, `UPDATE` или `DELETE` |
| `brevis_received_at` | `TIMESTAMP` | момент прихода, по **нашим** часам — столбец партиции |
| `brevis_loaded_at` | `TIMESTAMP` | момент записи, проставленный **местом назначения** |
| `brevis_stream` | `STRING` | какой маршрут записал |
| `brevis_gateway` | `STRING` | какое развёртывание |
| `brevis_received_bytes` | `INT64` | какого размера событие **пришло**, включая конверт |

Эти восемь принадлежат **SDK**, а не этому sink: `sdk.LandingSchema` объявляет
их, а `sdk.LandingID` выпускает идентичность, так что пайплайн может приземлить
ту же таблицу с теми же id. Одно определение, потому что два разошлись бы. См.
[структуру приземления SDK](/docs/sdk/#структура-приземления).

**`brevis_` зарезервирован.** `data`, несущая любой ключ с этим префиксом,
отклоняется **по событию** — иначе производитель подделывает управляющее поле,
а подделанное `brevis_received_at` хуже отсутствующего, потому что выглядит
настоящим.

**`brevis_loaded_at` — это `DEFAULT` базы данных**, а не значение, которое
отправляет gateway. Gateway знает время **отправки**, место назначения знает
время **записи**, а разница между двумя столбцами — это настоящая сквозная
задержка, по каждой строке, без какой-либо инструментации.

**`brevis_received_at` — столбец партиции, а никогда не часы клиента**: у
производителя они могут быть неверными или отсутствовать, а столбец партиции,
контролируемый клиентом, — это клиент, способный писать в 2035 год.
Непартиционированная таблица приземления — это счёт за запросы, который только
растёт. Кластеризация идёт по `brevis_record_key`, потому что чтение истории одной
записи — то, что делает с такой таблицей каждый.

Одно объявление служит каждому месту назначения, потому что генератор DDL в SDK
переводит каждый тип: `STRING` становится `TEXT` в Postgres, `LONGTEXT` в MySQL
и `STRING` в BigQuery; `JSON` становится `JSONB`, `JSON` и `JSON`.

### Объём без инфраструктуры для измерения объёма

`brevis_received_bytes` **бесплатен**: gateway и так считает эти байты при
декодировании, чтобы управлять `buffer.flush.size`, и до сих пор число умирало
там. Измерение самой записи стоило бы `json.Marshal` на событие — 2,0 мкс против
3,1 мкс, которые уже тратит разбор, **на 67% больше на горячем пути**, — чтобы
уточнить число, чья задача — тренд и атрибуция.

Он отвечает на то, на что метрики **структурно не могут**. Каждая серия
`brevis_gateway_*` — по *потоку* и не несёт метки `table`, намеренно: при
`auto_table` один маршрут становится N таблицами, и эта метка — на выбор
производителя. Поэтому у вопроса «какая таблица растёт и с каких пор» нигде не
было ответа.

```sql
select date(brevis_received_at) day,
       count(*) events,
       sum(brevis_received_bytes)/1e9 gb
from app_orders
group by 1 order by 1 desc
```

Без столбца тот же вопрос означает сканирование всего столбца JSON —
`sum(length(to_json_string(data)))` — примерно **в пятьдесят раз больше
просканированных байтов**, каждый раз, когда кто-то спрашивает. Столбец окупается
на первом же запросе.

**Это входящий трафик, а не хранение.** Место назначения хранит строку
типизированной и сжатой: 400 байт JSON могут занимать 80 на диске. Сумма даёт то,
что *пришло*, а не то, за что выставляется счёт за хранение.

И **производитель не может его записать**. Gateway проставляет значение после
хука и перезаписывает всё, что нёс конверт, — клиент, приславший это поле,
сообщал бы собственный объём, и суммирование перестало бы что-либо значить.

### Серии объёма включаются по желанию

```bash
BREVIS_INGESTION_METRICS=true
```

```
brevis_gateway_ingested_bytes_total{stream,table}
brevis_gateway_ingested_events_total{stream,table}
```

**По умолчанию выключены**, и умолчание — это суть: `table` — метка, которую
выбирает *производитель*. Всё остальное в этом файле размечено тем, что
оператор написал в YAML, поэтому число серий известно до запуска процесса. Никто
не должен обнаружить счёт за метрики из-за обновления.

Значение, которое никто не может разобрать, читается как **выключено**, а не как
сбой: это наблюдаемость, и опечатка здесь не должна быть причиной, по которой
endpoint приёма данных не запускается.

Столбец есть в любом случае. Метрика покупает *сейчас*; столбец покупает *с каких
пор* и *кем*.

### Две формы, один контракт

`shape` определяет, что **запись** вносит в строку. Контракт производителя в
любом случае один и тот же — конверт никогда не меняется. Меняется то, как
выглядит таблица, а это решение оператора, а не производителя.

```yaml
shape: document   # the default
shape: columns
```

При **`document`** `data` целиком попадает в один столбец `JSON`:

```
 brevis_ingestion_id | brevis_record_key | … | data
 d7179bfe-…          | A-1               |   | {"id": "A-1", "total": 150, "customer": {…}}
```

После создания DDL никогда не выполняется. Новое поле — новый ключ: нет квоты на
изменение схемы, нет повторного открытия потока записи, нет гонки между
репликами — и оно доступно для запросов в день прихода. Именно туда пришёл рынок:
Fivetran, Airbyte и Snowpipe приземляют данные в сырой слой, который не может
упасть, и моделируют их ниже по потоку.

При **`columns`** у каждого поля записи появляется собственный столбец:

```
 id   | total | customer              | items
 A-1  | 150   | {"id": 7, "uf": "SP"} | [{"qty": 2, "sku": "X"}]
```

**Скаляры становятся `STRING`, объекты и массивы становятся `JSON`, и нигде нет
вывода типов.** `150` пришло числом и стало строкой `150`. Это выбор, а не
ограничение: поле, пришедшее сегодня целым, а завтра дробным, изменило бы тип
столбца без чьих-либо действий, а строка, которая больше не подходит, уходит в
dead letter. Типизация — это путь **повышения**, записанный в YAML и
проверенный в диффе.

**`null` не становится столбцом вообще.** У него нет формы, поэтому читать
нечего: поле появляется в таблице с первого события, несущего ЗНАЧЕНИЕ, с формой
этого значения. Событие, приславшее `null`, приземляет `NULL` точно так же, что
оно и означало, — а там, где столбец уже есть, потому что вы объявили его или
его создало другое событие, `null` записывается в него, а не опускается.

**И столбец `JSON` получает JSON-ЗНАЧЕНИЕ, а не строку с ним.** Это звучит как
деталь, а на деле разница между таблицей, к которой можно делать запросы, и
таблицей, которая только выглядит правильной:

```sql
SELECT JSON_TYPE(customer) FROM bronze.orders;     -- object
SELECT JSON_VALUE(customer, '$.uf') ...;           -- SP
```

Если `JSON_TYPE` отвечает `string`, а `JSON_VALUE` отвечает NULL, объект был
закодирован дважды — столбец хранит ТЕКСТ объекта, а не объект. Версии gateway
до **0.15.0** включительно делали так в BigQuery в **обеих** формах; о проверке
в одну строку и исправлении см. [журнал изменений gateway](https://github.com/AreteAcademy/brevis/blob/master/gateway/CHANGELOG.md).
Postgres и MySQL никогда не были затронуты: их сервер разбирает текст.

Имя поля должно соответствовать правилу BigQuery, самому узкому из четырёх.
Postgres принял бы почти что угодно в кавычках, и это ловушка: таблица там
создаётся и ломается в тот день, когда кто-то направит поток в BigQuery.

У обеих форм есть эквивалент в SDK, и это тот же код, а не соответствующий:
`sdk.Landing(table, sdk.LandingKey("id"))` приземляет `document`, а добавление
[`sdk.LandingColumns()`](/docs/sdk/#две-формы-запись-целиком-или-по-столбцу-на-поле)
приземляет `columns`. Те же столбцы, те же значения, тот же `brevis_ingestion_id`
— так что поток может переходить между gateway и пайплайном без миграции, и их
можно читать как одну таблицу.

Пайплайн может вырастить тот же столбец тем же способом: задайте
[`Evolve: sdk.EvolveAdditiveFromPayload`](/docs/sdk/#когда-появляется-поле-которого-нет-в-таблице)
на месте назначения, и поле, которое несёт пакет, станет столбцом по этому
правилу, через этот код.


**Префикс настраивается, и это одно решение для всего процесса.**
`BREVIS_LANDING_PREFIX=acme` делает их `acme_ingestion_id` и так далее — для
каждого потока в этом gateway, поэтому два sinks не могут расходиться в
отношении таблицы, в которую могут писать оба. Зарезервированное правило выше
движется вместе с ним: при `acme_` производитель, присылающий `acme_region`,
отклоняется, а `brevis_region` — обычное поле.

**Выбирайте его до создания первой таблицы.** Последующее изменение добавляет
восемь столбцов и бросает восемь — ничто не удаляет столбец — поэтому таблица,
уже несущая структуру под одним префиксом, отклоняет загрузку, объявляющую
другой. О нормализации и выходе см. [страницу SDK](/docs/sdk/#префикс-brevis-можно-изменить).

**Поля вложенного объекта могут получить собственные столбцы.**
`BREVIS_NORMALIZE_DATA=true` в процессе gateway разворачивает один уровень —
`{"name": {"first": "x"}}` приземляется как `name_first` — и каждый поток
разделяет её, поэтому два sinks не могут расходиться в отношении таблицы, в
которую могут писать оба. О том, что она переименовывает, — а это та половина,
которую нужно прочитать перед включением, — см. [страницу SDK](/docs/sdk/#один-столбец-на-вложенное-поле).

**В BigQuery `nationalID` и `nationalId` — один столбец.** BigQuery не различает
регистр столбцов, поэтому сброс, несущий одно написание в `DELETE`, а другое в
`INSERT`, создаёт **один** столбец — первый в отсортированном порядке — вместо
того, чтобы провалить `CREATE`. Одно событие, несущее оба, отклоняется с
названием обоих полей. Postgres и MySQL хранят их как два столбца, что для них
правильно. О том, какое написание побеждает и что не мигрируется, см. [страницу SDK](/docs/sdk/).

### `UPDATE` и `DELETE` записываются, но не применяются

`brevis_operation` — это столбец. Таблица приземления — это **история**:
`UPDATE`, применённый на месте, теряет предыдущую версию, а день, когда вам
понадобится эта версия, — это день, когда что-то сломалось. Определение
«текущей версии каждой записи» — задача модели ниже по потоку:

```sql
qualify row_number() over (partition by brevis_record_key
                           order by brevis_received_at desc) = 1
   and brevis_operation <> 'DELETE'
```

Так делают Debezium, Fivetran и Airbyte — и это значит, что CDC не стоит
**ничего** на пути записи: ни режима upsert, ни блокировки, ни удаления.

### В идентичности нет часов

```
brevis_ingestion_id = uuid5(auto_table | table | data[unique_key] | sha256(canonical(data)))
```

В формуле нет `occurred_at`, и это намеренно: приход стал **нашей**
ответственностью, а наши часы — это `time.Now()`, разные при каждой доставке.
Идентичность с ними внутри делала бы каждую повторную доставку новым событием, и
`merge` перестал бы что-либо поглощать.

```
same record, same content, twice  →  same id, merge absorbs
same record, content changed      →  a different id, both versions land
```

Оговорка задокументирована: два действительно разных события с идентичной до
байта `data` сливаются в одно. Для CDC это **правильно** — два одинаковых
обновления одной записи с одними и теми же значениями — один и тот же факт.

Отпечаток берётся по документу в **канонической** форме — ключи отсортированы
на каждом уровне, массивы оставлены в порядке, всё в кавычках. Go
рандомизирует обход map, поэтому наивный хеш различался бы между двумя
доставками одного события, а это именно то, чему он призван препятствовать.

### Таблица сама добавляет столбец

`data`, несущая поле, которого нет в таблице, заставляет столбец появиться.
**Только аддитивно**: ничего не удаляется, ничего не сужается.

В BigQuery это стало правдой только в **0.13.0**. До этого `auto_table`
объявляла `Evolve: additive` для каждого места назначения, а объявление читали
только драйверы Postgres и MySQL — поэтому здесь форма была заморожена при
создании, и ничто об этом не говорило.

> **При переходе с 0.11.0 или 0.12.0** таблицы, созданные до `0.11.0`, требуют
> разовой миграции, потому что восьмой фиксированный столбец попал в объявление,
> а не в таблицу:
>
> ```sql
> ALTER TABLE `<dataset>.<table>` ADD COLUMN IF NOT EXISTS brevis_received_bytes INT64
> ```
>
> Postgres и MySQL никогда не были затронуты.

Пакет, проигравший гонку `ALTER`, падает, и обычная повторная попытка канала это
разрешает — пакет, ожидающий DDL, и пакет, ожидающий воркера, — одно и то же,
поэтому второго буфера нет. Между репликами metastore держит односекундный
*debounce* на таблицу и форму, чтобы десять реплик, видящих одно и то же новое
поле, не превращались в десять `ALTER` против квоты BigQuery в пять операций
с метаданными на таблицу за десять секунд.

**Debounce, а не блокировка**: ничего не освобождается и аренда не продлевается.
Проигравшего *повторяют*, а не блокируют, и реплика, умершая с удерживаемым
debounce, стоит остальным секунды. Так поступает рынок — Delta Lake и Iceberg
фиксируют оптимистично и повторяют, Kafka Connect получает сериализацию из
упорядочивания партиций, Fivetran держит одного писателя на таблицу.

### Имя — это поверхность атаки

`auto_table` превращает строку в payload в DDL, поэтому каждое поле под
`naming` — это отказ:

- **`pattern`** по умолчанию `^[a-z][a-z0-9_]{2,48}$` — пересечение того, что
  Postgres, MySQL, BigQuery и Redshift принимают без кавычек. Имя, которое
  проходит, нигде не нуждается в кавычках и не может нести инъекцию.
- **`allow`** сужает дальше, по префиксу.
- **`max_new_per_hour`** (по умолчанию 20) ограничивает **создания** в скользящем
  часе, но не записи: таблица, которая уже существует, никогда не ограничивается
  по частоте. При `metastore: memory` бюджет живёт в процессе, и четыре реплики
  допускают в четыре раза больше; при `redis` или `memcached` они делят один
  счётчик.

Имя вне правил отклоняется **по событию**, в ответе, и каждое корректное
событие в том же запросе всё равно приземляется:

```json
{"accepted": 0, "rejected": ["event 0: the table name \"orders\" does not match ^(app|svc)_[a-z0-9_]{2,40}$"]}
```

По событию, а не по пакету, намеренно. Отказ во время записи провалил бы весь
пакет — одно неправильное событие одного производителя хоронило бы события
всех остальных производителей в том же окне сброса, и никому бы не сказали.

**`auto_table` отклоняется на endpoint без `listen.auth`**, в том числе при
`BREVIS_ENV=local`. Производитель, который может назвать таблицу, может её
создать, поэтому ему нужна аутентификация даже там, где обычному потоку она не
нужна. NetworkPolicy этого не покрывает: она ограничивает, кто достаёт до порта,
а не какое имя таблицы они запрашивают.

### Metastore — это кэш

Он существует, чтобы запись по событию не означала поиск по событию, и хранит
три вещи: какие таблицы существуют, *debounce* DDL и счётчик за
`max_new_per_hour`.

Это кэш, а **не** источник истины. Существует ли таблица, решает место
назначения, а *N* реплик, гоняющихся за её созданием, — обычный случай:
`AlreadyExists` — это успех, и кэш лишь снижает гонку. TTL — это то, как долго
он может быть **неправ**.

| backend | когда |
|---|---|
| `memory` | по умолчанию, ничего не требует. С **одной** репликой это правильный ответ |
| `redis` | обязателен `addr_from`. Claim — это `SETNX`, счётчик — `INCR` |
| `memcached` | обязателен `addr_from`. Claim — это `Add`, а истечение — с точностью до **секунды** |

**Redis быстрее для потока с ключом маршрутизации**, и разница стоит числа, а не
прилагательного. При триггере по таблице окно запрашивает один claim на
таблицу: Redis отвечает на 94 из них за один конвейерный круг, а любой другой
backend отвечает параллельно, ограничение 32. Измерено на backend, удалённом на
25 мс, — 94 claims:

| backend | по одному | как поставляется |
|---|---:|---:|
| `redis` | 2,589 с | **29,8 мс** |
| `memcached` | 2,577 с | **89,4 мс** |

Три волны против одного круга. Оба укладываются в 500 мс, отведённые claim,
поэтому memcached — более медленный выбор, но не отклонённый.

С несколькими репликами `memory` даёт каждой свой: debounce ничего не
debounce-ит, а `max_new_per_hour` ограничивает процесс. Это единственная причина,
по которой существуют два других.

**Metastore, который недоступен, не должен тянуть за собой запись.** `Get` с
ошибкой — это промах, claim с ошибкой ведёт себя как выигранный, счётчик с
ошибкой ослабляет лимит. Кэш, способный остановить приём данных, хуже, чем его
отсутствие.

**И «недоступен» включает «медленный».** Claim выполняется, пока удерживается
блокировка буфера, поэтому backend, отвечающий две секунды, — это две секунды, в
течение которых этот поток ничего не принимает. Каждый вызов ограничен **500
мс** и по истечении отказывает в открытом режиме. Redis подчиняется этому как
контексту вызывающего; `gomemcache` вообще не принимает контекст, поэтому
memcached подчиняется как таймауту сокета — одно и то же ограничение,
достигнутое двумя путями, потому что одному из двух клиентов нельзя сказать
остановиться.

**`ttl: 0` означает «никогда»**, а отсутствие значения по-прежнему даёт
минутное значение по умолчанию — три состояния, а не два.

Не часы восстанавливают после неверной записи. Запись, которую отклоняет место
назначения, вызывает `invalidate`, который сразу удаляет запись и позволяет
повторной попытке канала прийти на холодный кэш: таблица, удалённая вручную,
стоит **одной неудачной попытки**, а не минуты.

У истечения есть цена. `sinkFor` списывает `naming.max_new_per_hour`, когда не
**знает** таблицу, — поэтому промах списывает за таблицу, существующую уже
неделями, а pod, перезапустившийся через минуту после последнего события таблицы,
не получает ничего от общего backend, за который он платит. Для долгоживущих
таблиц ответ — `ttl: 0`.

> В `0.12.0` и `0.13.1` такая запись **не разбирается** — YAML читает голый ноль
> как int, и `0.13.2` — первая, принимающая оба варианта. В этих версиях пишите
> `ttl: 0s`.

`addr_from` называет **переменную окружения**, содержащую адрес, а не сам адрес:
он достаточно часто несёт пароль.

### У BigQuery есть нижняя граница сброса

**BigQuery допускает 1500 load-задач на таблицу в день.** Окно по умолчанию в
одну секунду — это 86 400, в 57 раз больше квоты, исчерпанной примерно за
двадцать пять минут. Для Pub/Sub это не проблема, и число пришло бы сюда *из*
конфигурации Pub/Sub.

Поэтому поток, пишущий в BigQuery напрямую или через маршрутизатор,
**отклоняется при загрузке** с окном меньше 60 с. Настоящий ответ — Storage
Write API, который не написан; пока его нет, конфигурация отклоняет окно,
которое не может выдержать, а не даёт первому же развёртыванию это обнаружить.

`auto_table` не может направлять в **Redshift**: этот драйвер не создаёт таблицы,
поэтому каждое новое имя провалилось бы при загрузке. Отклоняется по имени, при
старте.

## Чего пока не существует

`sqlite`, `dynamodb`, `kinesis`, `sqs`, `sns`, `kafka` и `rabbitmq`
запланированы, и ничего не написано. (`redis` и `memcached` существуют как
**metastore**, а это другое: кэш того, что известно о таблицах, но никогда не
место назначения.) Таблица в начале этой страницы указывает состояние каждого и
обновляется, когда состояние меняется, — но не раньше.
