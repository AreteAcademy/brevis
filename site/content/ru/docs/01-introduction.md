brevis.sh — это **рантайм оркестрации данных, написанный на Go**. Один бинарный
файл объединяет то, на что обычно уходит четыре инструмента: декларативные
преобразования, оркестрацию workflow, постоянную очередь, планировщик и
интерфейс для управления всем этим.

Проект распространяется с открытым исходным кодом под лицензией MIT и родился
в [Aretê Academy](https://areteacademy.com.br/).

## Проблема

Типичный стек данных сочетает инструмент преобразований, оркестратор, очередь
и интерфейс. Каждый компонент хорошо делает своё дело, но интеграция между
ними превращается в постоянную работу: четыре схемы версионирования, четыре
способа настройки, четыре места, куда смотреть при сбое.

Эта стоимость не видна на архитектурной схеме. Она проявляется во времени,
которое команда тратит на поддержку «клея» вместо работы над предметной
областью, которую знает только она.

## Предложение

Один артефакт с той подкомандой, которая нужна для роли:

```bash
brevis serve        # API + interface
brevis scheduler    # materialises schedules and drains the queue
brevis run wf.yaml  # runs now, no database
```

Workflow — это версионируемый YAML-файл. Ревью пайплайна превращается в ревью
диффа, а не в сеанс кликов мышью.

```yaml
name: ingest
schedule: "0 5 * * *"

steps:
  - id: bronze
    image: registry.example/dbt:1.10.3
    run: dbt build --select bronze+

  - id: notify
    image: ghcr.io/example/notify:0.3
    run: /notify --channel data
    depends_on: [bronze]
```

## Чем он отличается

**Каждый шаг работает в собственном pod, со своим образом.** Универсального
воркера, ждущего задач, нет: работа приносит с собой собственное окружение.
Шаг `dbt` запускается с образом dbt, а Go-загрузчик рядом с ним — с 5,8 МБ и
32Mi памяти, не наследуя размер самого тяжёлого соседа.

**Планировщик создаёт запуски, очередь их исполняет.** Два независимых цикла,
и это разделение сделано намеренно: один может упасть, не прерывая другой, а
повторная обработка прошлого месяца не зависит от часов.

**Валидации не нужна база данных.** `brevis validate` запускается в CI вместе
с тестами, поэтому ошибка в YAML ломает pull request, а не кластер.

## Три компонента, раздельных намеренно

| компонент | что это | версия |
|---|---|---|
| **engine** | `brevis`, бинарный файл, о котором эта страница: оркестрирует, планирует, исполняет и управляет | `0.15` |
| **SDK** | модуль Go для написания шага, который извлекает и загружает данные | `0.66` |
| **gateway** | HTTP-endpoint, принимающий данные, которые *приходят сами*, вместо того чтобы забирать их | `0.8` |

Версии независимы, потому что независима зрелость. Если присвоить gateway
версию `0.15.3` только потому, что там же живёт engine, это значило бы
заявить зрелость, которой у него нет, а опубликованную версию нельзя
отозвать.

Все три компонента связывает число: `ingestion_id`, зафиксированный UUID
v5 от `provider|entity|source_key|record_ts`. Строка, которую записывает
[gateway](/docs/ingestion/), и строка, которую записывает загрузчик на
[SDK](/docs/sdk/) для той же записи, — это *одна строка*, без сверки между
ними.

## Когда brevis.sh не подходит

Описывать то, чего инструмент не делает, экономит больше времени, чем
описывать то, что он делает:

- **Вы уже работаете с Airflow или Dagster и довольны.** Миграция стоит
  дороже, чем экономия от одного бинарного файла вместо нескольких.
- **Ваши workflow не про данные.** brevis.sh исходит из DAG преобразования и
  загрузки; вам лучше подойдёт оркестратор общего назначения.
- **Вам нужен каталог готовых операторов.** Здесь шаг — это образ и команда.
  Это просто, но ограниченно: сотен интеграций, которые можно подключить, нет.
- **Ваша команда не использует Kubernetes и не собирается.** Локальный режим
  работает, но архитектура рассчитана на pod.
