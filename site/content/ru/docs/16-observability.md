Brevis публикует метрики Prometheus на отдельном порту, из **обоих** процессов.

```
GET http://<pod>:9090/metrics
```

Порт задаётся через `BREVIS_METRICS_ADDR`. Он намеренно отделён от HTTP-порта:
метрики не проходят через аутентификацию интерфейса, а отдача обоих с одного
места заставила бы выбирать между аутентифицированным сбором и открытым
дашбордом.

## Два процесса, два эндпоинта

Именно здесь ошибается большинство установок, собирая только API.

| | отдаёт | сообщает |
|---|---|---|
| `brevis serve` | UI и HTTP API | глубина очереди |
| `brevis scheduler` | ничего по HTTP | глубина очереди, задержка захвата, слоты, сироты, запуски, шаги |

Исполняет планировщик, поэтому почти всё исходит от него. Дашборд, построенный
только на API, показывает растущую очередь и **ничего** о том, что её
разбирает.

## Метрики, которые публикует шаг

Помимо того, что измеряет engine, шаг может публиковать собственные: сколько
строк приземлилось, сколько отклонил вендор:

```python
from brevis import metrics
metrics.set("rows_loaded", 48213)
```

Они появляются в **том же** `/metrics` планировщика, с префиксом и метками,
которые добавляет engine:

```
brevis_step_rows_loaded{workflow="daily_sales",step="load"} 48213
```

Шаг не открывает порт: он пишет строку в stdout, а engine её фиксирует — pod,
живущий сорок секунд, нельзя опросить. См. [Python](/docs/python/).

## За чем следить

| сигнал | почему |
|---|---|
| глубина очереди растёт и не падает | планировщик умер или `--concurrency` мал для нагрузки |
| задержка захвата растёт | конкуренция за базу данных или очередь слишком велика для интервала |
| сироты > 0 | запуски, захваченные процессом, который умер, не завершив их |
| слоты не материализуются | цикл планировщика остановился, а вместе с ним — расписания |

Первые два сигнала сами по себе не отличают «высокую нагрузку» от «мёртвого
процесса», поэтому и важны слоты. Очередь растёт **при** создании слотов — это
нагрузка; очередь растёт **без** слотов — остановившийся цикл.

## Kubernetes

```yaml
env:
  - name: BREVIS_METRICS_ADDR
    value: ":9090"
ports:
  - name: metrics
    containerPort: 9090
```

С Prometheus Operator — по одному `PodMonitor` на роль, и именно на роль,
потому что у двух Deployment разные метки и они сообщают разные наборы.

## Чего намеренно нет

**Трассировок.** OpenTelemetry пока нет. Шаг выполняется как отдельный pod, а
то, что важно о нём знать — начало, конец, попытка, код завершения, журнал, —
уже есть в базе данных и на экране. Полезной была бы трассировка внутри
шага, а она принадлежит коду шага, а не оркестратору.

Это справедливо, пока единицей остаётся шаг. В тот день, когда шаг вызывает
другой сервис и вопрос становится «куда ушли эти 40 секунд», трассировка
начинает стоить своих затрат.
