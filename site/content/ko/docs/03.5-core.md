workflow 전체가 버전 관리되는 파일 하나이므로, 파이프라인을 리뷰한다는 것은 diff를 읽는 일이 됩니다. Core는 스케줄링하고, 큐에 넣고, 각 step을 자기만의 이미지로 시작하며, 데이터는 절대 만지지 않습니다.

![The Core flow: a scheduler and a queue, kept in Postgres, start one pod per step of the workflow — prepare, extract, validate and publish. Only control lines leave the Core. The data goes from an HTTP source into the extract pod, which runs the SDK, and from there to BigQuery; no data passes through the Core.](/assets/flow-core.svg)

## 하는 일

- **스케줄링합니다.** 스케줄러는 각 workflow의 스케줄을 읽고 run을 만듭니다. 스케줄러와 큐는 서로 독립된 두 루프이므로, 한쪽이 막혀도 다른 쪽은 멈추지 않습니다. 자세한 내용은 [스케줄러와 큐](/docs/scheduler-and-queue/)를 참고하세요.
- **큐에 넣습니다.** 큐는 Postgres에 있습니다. 실행하는 쪽이 대기 중인 run을 가져가 그래프를 따라가며 각 step의 상태를 기록합니다.
- **step마다 pod 하나를 시작합니다.** 각각 자기만의 이미지를 사용합니다. 자세한 내용은 [step당 pod 하나](/docs/pod-per-step/)를 참고하세요.
- **데이터는 절대 만지지 않습니다.** Core에서 나가는 것은 제어 라인뿐입니다. 데이터를 읽고 쓰는 것은 [SDK](/docs/sdk/)나 직접 작성한 코드를 사용하는 step입니다.

## 하나의 workflow, 처음부터 끝까지

workflow는 YAML 파일 하나입니다. 같은 step에 의존하는 두 step은 병렬로 실행됩니다.

```yaml
name: hello
type: dag
tags: [example]

steps:
  - id: prepare
    run: sh -c 'echo preparing; sleep 1'

  # The next two depend on the same step, so they run IN PARALLEL.
  - id: extract
    run: sh -c 'sleep 2; echo 42 extracted'
    depends_on: [prepare]

  - id: validate
    run: sh -c 'sleep 1; echo validated'
    depends_on: [prepare]

  - id: publish
    run: echo published
    depends_on: [extract, validate]
```

큐나 클러스터 없이 로컬에서 실행하려면 다음과 같이 합니다.

```bash
docker run --rm -v ./hello.yaml:/w/hello.yaml -w /w \
  brevissh/brevis:0.40.0-worker run hello.yaml
```

출력은 다음과 같습니다.

```text
workflow hello (dag, 4 steps) in .
  ▶ prepare
    prepare | preparing
  ✓ prepare
  ▶ validate
  ▶ extract
    validate | validated
  ✓ validate
    extract | 42 extracted
  ✓ extract
  ▶ publish
    publish | published
  ✓ publish

workflow hello finished
```

게시된 이미지에서 얻은 실제 출력입니다. brevis run은 큐 없이 로컬에서 실행하며, pod는 스케줄러가 시작합니다.
