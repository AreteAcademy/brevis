# Pod на шаг

> Почему каждый шаг выполняется в собственном pod и что это меняет в стоимости и изоляции.

*https://brevis.sh/ru/docs/pod-per-step/ · brevis.sh docs (ru)*

---

В Kubernetes **каждый шаг workflow становится pod** с образом, объявленным в
этом шаге. Универсального воркера, ждущего задач, нет: работа приносит с собой
собственное окружение.

![Схема: Core запускает по одному pod на каждый шаг — extract на Go, prepare на Python, load на Go и transform на dbt. Шаги передают друг другу контекст, а читает и записывает его SDK.](/assets/execution.svg)

```
scheduler                          cluster
─────────                          ───────
walks the graph
  for each ready step:
    builds the Pod  ───────────►  Pod: the step's image, the step's command
    follows status      ◄───────  Pending → Running → Succeeded/Failed
    follows the log     ◄───────  container stdout
    reads the exit code ◄───────  containerStatuses[0].terminated
    deletes the pod ───────────►  (gone)
```

## Что это меняет

Монолитный воркер вынуждает класть в образ всё, что может понадобиться любому
шагу. На практике:

| | единый образ | pod на шаг |
|---|---|---|
| шаг dbt | 1,9 ГБ · 1Gi RAM | 1,9 ГБ · 1Gi RAM |
| Go-загрузчик рядом с ним | **1,9 ГБ · 1Gi** | **12 МБ · 32Mi** |
| обновление версии dbt | пересобрать всё | одна строка в YAML этого workflow |
| шаг с утечкой памяти | роняет воркер и его соседей | падает один |

Третья строка наименее очевидна и обходится дороже всего изо дня в день: при
едином образе переход с dbt 1.10 на 1.11 в одном пайплайне навязывает его всем
остальным.

## Образы по ролям

Образы делятся по **ролям**, а не по проектам. Всё лишнее в образе скачивает
каждый узел, запускающий этот шаг:

| роль | размер | холодный старт |
|---|---|---|
| **Go** | **5,8 МБ** | 0,18 с |
| **Python** | **118 МБ** | 0,54 с |
| **dbt** | **620 МБ** | 3,3 с |

Раньше: единый образ на 1,87 ГБ для всего.

Для dbt `dbt parse` выполняется при сборке, а `target/partial_parse.msgpack`
поставляется в образе — **на 2,68 с меньше на каждый pod**, при каждом запуске.

## Где выполняется каждый шаг

Решение принимается один раз при старте и зависит от `BREVIS_PODS` и от
наличия кластера:

| `BREVIS_PODS` | с кластером | без кластера |
|---|---|---|
| `auto` (по умолчанию) | шаг с `image:` становится pod | всё как локальные процессы, с предупреждением в журнале |
| `on` | шаг с `image:` становится pod | **ошибка при старте** |
| `off` | всё как локальные процессы | всё как локальные процессы |

**Шаг с `host:` через всё это не проходит.** Он проверяется до pod и до
процесса и отправляется на уже работающую машину — `BREVIS_PODS` к нему не
применяется, и он никогда не откатывается к локальному процессу. Это
сделано намеренно: `image:` деградирует до локального исполнения с
предупреждением, потому что контейнер и процесс — это одна и та же команда в
двух обёртках, а хост — нет. Там находится лицензия, или GPU, или данные.

`auto` — значение по умолчанию, потому что один и тот же бинарный файл
работает в обоих местах: на ноутбуке сервисный аккаунт не смонтирован, и он
откатывается к локальным процессам; в кластере он есть, и начинается создание
pod.

`on` существует для развёртывания, которое **не должно** молча превратиться в
локальное исполнение. Там отсутствие кластера обязано быть ошибкой при старте.

:::warning `brevis run` не создаёт pod
Команда `run` собирает только исполнитель процессов. Шаг с `image:` выполняется
на самом экземпляре — и сообщает об этом. Молчание создало бы впечатление, что
шаг выполнился на объявленном образе, а такая ошибка обнаруживается лишь тогда,
когда результат уже неверен.
:::

## Идентичность и учётные данные

С какой идентичностью запускаются pod — это решение об **установке**, а не о
workflow: пайплайн не должен иметь возможности выбирать сервисный аккаунт, от
имени которого работает. Поэтому она берётся из окружения:

```bash
BREVIS_POD_NAMESPACE=data
BREVIS_POD_SERVICE_ACCOUNT=brevis-runner
BREVIS_POD_PULL_SECRETS=registry-cred
BREVIS_POD_ENV_FROM_SECRETS=bigquery-cred,api-tokens
```

В режиме pod окружение задачи берётся из Secrets кластера, а не из
`BREVIS_TASK_ENV`.

## Селектор узлов и tolerations

```bash
BREVIS_POD_NODE_SELECTOR='kubernetes.io/arch=arm64'
BREVIS_POD_TOLERATIONS='dedicated=data:NoSchedule'
```

В tolerations допускается только оператор `Equal`: `Exists` допускал бы
**любой** taint с этим ключом, что слишком широко для решения, приходящего из
переменной окружения.

Некорректный toleration **игнорируется**, а не вызывает ошибку при старте — pod
остаётся в `Pending`, что хорошо заметно, тогда как отказ от старта остановил
бы и те workflow, которым этот пул не нужен.

## Отладка сбоя

```bash
BREVIS_POD_KEEP_ON_FAILURE=true
```

Сохраняет упавший pod для `kubectl logs` и `kubectl describe`. В продакшене
оставляйте выключенным: остановленные pod расходуют квоту кластера.
