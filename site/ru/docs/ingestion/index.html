Документация

Приём данных

HTTP-endpoint, который приземляет данные — проверяет, идентифицирует, группирует в пакеты и доставляет. Собственный образ, собственная версия.

Gateway приёма данных — это HTTP-endpoint, который приземляет данные. Клиент отправляет POST, получает 202, а то, что пришло, становится записью в топике, в таблице или в бакете.

Это другой бинарный файл, другой модуль Go, другая версия и другой образ. Engine оркестрирует и никогда не касается данных клиентов; gateway не делает ничего другого. Нумерация независима намеренно: engine на 0.17, а gateway на 0.27, и это правдивое утверждение.

С gateway.yaml из раздела ниже и ключом, который он запрашивает в keys_from:

bash
docker run -p 8080:8080 -e BREVIS_INGEST_KEYS=dev-key \
  -v ./gateway.yaml:/etc/brevis/gateway.yaml:ro \
  areteacademy/brevis-gateway:0.32.0
text
2026/10/09 01:03:01 drain budget 30s; set terminationGracePeriodSeconds >= 40
2026/10/09 01:03:01 connections idle out after 1m30s and are recycled after 1m0s
2026/10/09 01:03:01 listening on :8080
2026/10/09 01:03:01 metrics on :9090/metrics

POST сразу возвращает 202:

bash
curl -X POST localhost:8080/v1/clicks -H 'Authorization: Bearer dev-key' \
  -d '{"event_id":"e-1","occurred_at":"2026-10-08T12:00:00Z","page":"/pricing"}'
text
{"accepted":1,"rejected":null}

Без учётных данных Google Cloud пакет повторяется и уходит в dead letter — см. Когда sink отказывает.

Образ -slim содержит только sinks auto_table, files и postgres; pubsub из этого примера и остальные есть в полном образе. Slim-образ с sink, которого в нём нет, отклоняется при старте с указанием причины.

Файл — это контракт#

Писать нечего, кроме хуков. Потоки, пути, форматы, идентичность, повторные попытки, место назначения и dead letter — всё в YAML, и каждое поле отклоняется, если его нельзя выполнить.

yaml
name: events_gateway

listen:
  addr: :8080
  max_body: 1MiB
  idle_timeout: 90s                  # the default; it cannot be turned off
  max_conn_age: 60s                  # off unless set — see below
  auth:
    type: bearer
    keys_from: BREVIS_INGEST_KEYS   # the NAME of the variable, never the keys

metrics:
  addr: :9090                        # its own port, never the ingest one

streams:
  - name: clicks
    path: /v1/clicks
    format: json                     # json | array | ndjson — declared, never sniffed

    identity:
      provider: web
      entity: click
      source_key: event_id
      record_ts: occurred_at

    buffer:
      flush: {every: 1s, records: 500}

    sink:
      type: pubsub
      project: acme-prod
      topic: clicks

    dead_letter:
      type: files
      path: /var/dead-letter/

format объявляется и никогда не угадывается: угадывание — это то, как пакет из тысячи записей превращается в одну строку, содержащую массив.

ingestion_id — в нём вся суть#

Каждая запись уходит с ingestion_id: зафиксированным UUID v5 от provider|entity|source_key|record_ts.

Это тот же id, который пакетный загрузчик вычисляет для той же записи. Строка, которую приземляет gateway, и строка, которую приземляет пайплайн на SDK, — это одна строка, без сверки между ними.

Два практических следствия:

  • Повторённый POST — та же запись. Клиент может отправить снова без опасений; место назначения с merge поглощает повтор, а не записывает вторую строку.
  • Формула зафиксирована. Все четыре поля обязательны, и пропуск одного даёт другой id, а не более слабый. Файл отклоняет неполную конфигурацию, а не принимает её.

Инструменты приёма данных отлично перемещают байты и не имеют мнения о том, чем является запись. Это мнение и добавляет gateway.

Запрос никогда не ждёт sink#

Он декодирует, запускает хук, вычисляет идентичность, добавляет в буфер и возвращает ответ. Это всё. Полный пакет уходит в пул воркеров, и публикация, COPY, повторные попытки и dead letter происходят уже там.

Это не косметика. Пока этого не было, запрос, оказавшийся тем, что заполнило пакет, выполнял доставку прямо в себе — так что один вызывающий на каждые flush.records платил полный круговой путь, а когда sink был недоступен, — полное окно повторных попыток. P99, форма которого зависит от того, кому не повезло, — это p99, на который никто не может реагировать.

yaml
buffer:
  flush:
    every: 1s         # age
    records: 500      # count
    size: 8MiB        # bytes — whichever is crossed FIRST sends the batch
    max_age: 30s      # and this one sends it REGARDLESS
  workers: 4          # batches delivered at once
  queue: 64           # full batches that may wait for a worker
  max_records: 10000  # events held in memory before the gateway says no
  max_bytes: 256MiB   # the same ceiling in bytes

Часы сброса принадлежат развёртыванию#

buffer.flush.every — это time.AfterFunc в каждой реплике. Поэтому число load-задач, получаемых таблицей, — функция числа реплик, а не трафика:

jobs / day / table  =  replicas × 86400 / every

В BigQuery при 1500 в день на таблицу две реплики при 60 с — это уже 192% квоты, которую нельзя увеличить, — ещё до того, как что-либо сделает HPA. И направление противоположно интуиции: gateway масштабируется по горизонтали ради HTTP-конкурентности, а sink хочет концентрации.

yaml
buffer:
  flush:
    every: 60s
    max_age: 300s
    claim: true

С claim реплика перед сбросом по таймеру берёт set-if-absent для потока и окна — а таймер просыпается на границе окна, так что все реплики запрашивают один и тот же ключ. Один сброс на окно, сколько бы ни было реплик. И это самонастраивается: реплика ждёт, только когда ей на самом деле кто-то конкурирует, поэтому уменьшение числа реплик возвращает меньшую задержку без правки конфигурации.

Измерено с двумя репликами и одним Redis, окна по 5 с: 8 load-задач стали 6, по одной на окно, с чередованием 3/3 — ни одного окна с двумя.

Нужен общий backend. С memory каждая реплика выигрывает собственный claim, и ничто не координируется. И он требует max_age, без которого конфигурация отклоняется: claim превращает every в цель, а цель без потолка — это задержка без границы.

Недоступное metastore всё равно сбрасывает. Потеря координации стоит load-задач; отказ сбрасывать удерживает данные. Проверено остановкой Redis посреди запуска: 40 из 40 событий приземлились, ничего не удержано.

outcome="unreachable" — единственный, ради которого стоит заводить алерт. К backend не удалось обратиться, поэтому claim отказал в открытом режиме: координация выключена, и load-задачи снова умножаются на число реплик — молча, потому что каждый сброс по-прежнему выглядит как сброс.

И claim даёт исключительность, а не справедливость: выигрывает тот, кто спросил первым. Реальный запуск с двумя репликами дал 4/1, а не поровну. max_age не даёт невезучей реплике голодать.

С claim: true и metastore: memory gateway предупреждает один раз при старте: каждая реплика выигрывает собственный claim, поэтому всё выглядит правильно, а ничто не координируется.

every — это цель; max_age — это обещание#

Три триггера выше определяют, когда пакет пытается уйти. max_age определяет, когда он уходит в любом случае.

Сегодня разница инертна, потому что ничто не откладывает цель. Она начинает иметь значение, когда часы сброса перестают быть пропроцессными: buffer.flush.every — это time.AfterFunc в каждой реплике, поэтому число load-задач, получаемых таблицей, — функция числа реплик, а не трафика — replicas × 86400 / every. В BigQuery при 1500 в день на таблицу две реплики при 60 с — это уже 192% квоты.

Когда реплика сможет уступить окно другой, она продолжит наполняться, а max_age не даст никому держать данные бесконечно в ожидании очереди.

Он также определяет слив: то, что буфер может удерживать в момент SIGTERM, ограничивается им, а terminationGracePeriodSeconds, который gateway выводит при старте, выводится из него.

Потолок ниже цели отклоняется при загрузке — это означало бы, что цель никогда не применяется.

Зачем нужен триггер по размеру#

Два других — счётчики, а счётчик не отличает 500 событий по 2 КБ от 500 по 2 МБ — 1 МБ против 1 ГБ, одно и то же число в файле. У max_records: 10000 та же слепота: 20 МБ или 20 ГБ, и ничто в YAML не могло бы сказать, что именно.

Производитель, начавший присылать весь документ вместо его id, роняет pod, а пока этого триггера не было, ни одно поле не могло выразить это ограничение.

Размер измеряется по тому, что пришло, — а не по весу события в памяти (map[string]any в несколько раз больше своего JSON) и не после хука, который его раздувает. Это приближение, и правильное: оно бесплатно при декодировании, меняется вместе с payload, а то, от чего оно защищает, — это запись, выросшая в десять раз.

В BigQuery size — это потолок, а не цель. Это место назначения допускает 1500 load-задач на таблицу в день, поэтому у every есть нижняя граница 60 секунд. Но граница управляет таймером: размер, срабатывающий каждые несколько секунд, проходит мимо неё и тратит ту же квоту. При загрузке ничто этого не отклоняет, потому что частота поступления там неизвестна. Вместо этого есть наблюдаемость:

brevis_gateway_flushes_total{stream,trigger}   trigger = time | records | size

Растущий trigger="size" в потоке BigQuery говорит вам, что пакетами управляет не окно.

Этот счётчик — по потоку, а квота — по таблице: с auto_table один маршрут становится многими таблицами, и 94 из них, сообщающие одно число, ничего не говорят ни об одной. За BREVIS_INGESTION_METRICS есть счётчик, называющий её:

brevis_gateway_table_flushes_total{stream,table,trigger}

Один сброс таблицы — это одна load-задача для неё, поэтому это серия, на которую стоит вешать алерт на 1200 из 1500 допускаемых BigQuery. Безусловная часть — строка при старте, которая говорит, во сколько обходится flush.every на таблицу в день, ещё до прихода первого события.

Он ограничен, а не fire-and-forget. Горутина на пакет превратила бы сбой sink в неограниченную память. Когда очередь и буфер заполнены, ответом служит 503 с Retry-After, а не 202 для события, которому некуда деваться. Принятое, но никогда не доставленное событие — единственный исход, которого этот сервис существует, чтобы не допускать.

И этот 503 безопасно повторять, как почти ни один сервис не может заявить: ingestion_id — это зафиксированная функция самого события, поэтому то же тело, отправленное повторно, — та же запись.

Соединение решает, какая реплика получит нагрузку#

За ClusterIP Service в Kubernetes kube-proxy выбирает backend один раз на TCP-соединение, а не на запрос. Большинство клиентов держат соединения живыми и используют их повторно, поэтому производитель с горсткой соединений шлёт всё на одну-две реплики, сколько бы их ни работало, — а реплика, добавленная HPA, не получает ничего, потому что никто на неё не дозванивается.

yaml
listen:
  idle_timeout: 90s     # closes a connection nobody came back to
  max_conn_age: 60s     # after this, the next response asks the client to redial

max_conn_age по умолчанию выключен, и это сделано намеренно: как долго клиент может держать одно соединение — это политика, и она меняет одно рукопожатие внутри кластера на соединение за возраст на распределение нагрузки. Сам запрос всегда обслуживается — заголовок добавляется к ответу, ничего не повторяется, и ни один пакет не теряется.

У idle_timeout есть значение по умолчанию, и его нельзя отключить. Работа без него — это файловый дескриптор на каждого брошенного клиента до перезапуска процесса. Задайте длинное, если вам нужно именно это; тогда это число, которое кто-то выбрал.

Они независимы: соединение встречает ту границу, которая наступит раньше, а до возраста соединение доходит, только будучи используемым, — то есть именно долгоживущий производитель, для перебалансировки которого возраст и существует.

Когда sink отказывает#

Пакет повторяется — по умолчанию четыре попытки примерно за семь секунд, с удвоением и джиттером, — а затем уходит в dead letter с причиной в каждой записи:

json
{
  "event_id": "dl-9",
  "ingestion_id": "84aaee4b-66af-5cc0-b97b-6856dec95b25",
  "_dead_letter_reason": "rpc error: code = NotFound desc = Topic not found",
  "_dead_letter_sink": "pubsub:acme-prod/clicks",
  "_dead_letter_at": "2026-09-25T02:02:32Z"
}

Причина путешествует в записи, а не только в журнале, потому что тот, кто позже найдёт этот файл, имеет события, а не журнал, — и почему это здесь — его первый вопрос.

Поток без dead_letter отклоняется при загрузке. Молчание по умолчанию перенесло бы решение туда, где его никто не принимает, а отклонённый пакет, остающийся лишь строкой журнала, — это тихая потеря данных.

Хук — это Go, скомпилированный внутрь#

go
hooks := gateway.NewHooks()
hooks.MustRegister("enrich_clicks", enrichClicks)
gateway.Main(hooks, gateway.WithSinks(sinks))

func enrichClicks(e map[string]any) (map[string]any, error) {
    host, _ := e["host"].(string)
    e["tenant"] = strings.Split(host, ".")[0]
    return e, nil     // returning nil DROPS the event, on purpose
}

YAML называет хук; он его не несёт. Измерено до выбора: функция Go стоит 93 нс/оп против 959 у Starlark и 1281 у yaegi, без добавления чего-либо в бинарный файл — а plugin.Open вообще не вариант, потому что при CGO_ENABLED=0, как собирается здесь каждый артефакт, он возвращает plugin: not implemented.

Чего это стоит, сказано там, где кто-то прочтёт: добавление хука — это пересборка и развёртывание, а не изменение конфигурации. Это правильный компромисс, пока хуки пишут те, кто выпускает бинарный файл, и неправильный в тот день, когда клиенту нужно изменить один без релиза.

Ошибка в хуке отправляет это событие по пути dead letter и никогда не роняет пакет рядом с ним. Так же и паника: она перехватывается на каждое событие, потому что одна неправильная запись не должна ронять процесс, обслуживающий все остальные потоки.

Когда событие слишком велико#

yaml
oversize:
  larger_than: 256KiB
  archive: {type: files, path: gs://acme-oversize/clicks/}
  hook: strip_heavy_clicks

Событие записывается в archive целиком, а уменьшенная версия продолжает путь в поток, неся ссылку назад:

json
{
  "event_id": "big-1",
  "ingestion_id": "bd8ac083-9796-50f5-bab6-77a4e2e57ad0",
  "_oversize": true,
  "_oversize_archive": "files:gs://acme-oversize/clicks/",
  "_oversize_bytes": 2149
}

Это шаблон Claim Check, и он лучше простого 413, потому что 413 теряет событие, а слишком большой payload обычно самый интересный из всех: это запрос с приложенным документом целиком, тот случай, который стоит отлаживать.

larger_than измеряет одно событие после хука. listen.max_body — другое: он ограничивает весь запрос и отклоняет с 413 до того, как разобран хоть один байт.

Что он считает#

Одиннадцать серий Prometheus на собственном порту — никогда не на порту приёма, и это правило здесь важнее, чем в engine: порт приёма публичен по построению, туда клиенты шлют POST, поэтому /metrics на нём опубликовал бы каждое имя потока, путь и место назначения тому, кто найдёт путь. Указание одного и того же адреса для обоих отклоняется при загрузке.

brevis_gateway_events_received_total{stream,format}     counter
brevis_gateway_events_rejected_total{stream,reason}     counter  per event, after decode
brevis_gateway_requests_refused_total{stream,reason}    counter  per request: unauthorized|body_too_large|malformed|empty|saturated
brevis_gateway_batches_total{stream,sink,outcome}       counter  delivered|retried|buried
brevis_gateway_reconciled_total{stream,sink}            counter  landed after the send window; also delivered
brevis_gateway_flushes_total{stream,trigger}            counter  time|records|size
brevis_gateway_flush_windows_total{stream,outcome}      counter  won|yielded|ceiling|unreachable
brevis_gateway_ingested_bytes_total{stream,table}        counter  opt-in
brevis_gateway_ingested_events_total{stream,table}      counter  opt-in
brevis_gateway_table_flushes_total{stream,table,trigger} counter  opt-in
process_start_time_seconds                              gauge    unprefixed, on purpose
brevis_gateway_saturated_total{stream}                  counter  the 503s
brevis_gateway_delivery_seconds{stream,sink}            histogram
brevis_gateway_buffer_records{stream}                   gauge
brevis_gateway_queue_batches{stream}                    gauge

process_start_time_seconds не имеет префикса brevis_, и это сделано намеренно: коллекторы ищут именно это имя. Оно говорит, когда запустился процесс, а без него коллектор, выполняющий корректировку по времени старта, — приёмник Prometheus для OpenTelemetry, на котором построен Google Managed Prometheus, — привязывает каждую накопительную серию к её первому опросу и тратит значение этого опроса как базовое. В результате каждый счётчик читается заниженным: дельты верны, а итоги нет.

Последние три — те, о которых никто не просит до первого инцидента. saturated_total — единственное число, которое говорит, что клиенту велели отступить; buffer_records относительно buffer.max_records — единственное, которое это предсказывает.

reason — закрытое множество и никогда не текст ошибки: строка ошибки несёт имя таблицы, столбец, иногда строку, и один неправильный клиент порождал бы новую серию на каждый запрос. Текст остаётся в dead letter, в записи.

202, а не 200#

Gateway принял события. С durability: memory — единственным реализованным уровнем — это всё, что он может честно заявить. Уровень, заслуживающий 200, — это тот, который уже записал их, и его не существует.

disk отклоняется по имени, а не принимается и обрабатывается как memory: тот, кто пишет disk, считает, что его события переживут сбой, а согласиться, не выполнив, — это именно тот сбой, который это поле призвано предотвратить.

То, что находится в буфере при завершении, доставляется, а не отбрасывается — тем же путём, каким идёт полный пакет, с повторными попытками и захоронением.

Чего он не делает#

  • Он не появляется в консоли. Он не делит базу данных с интерфейсом engine, поэтому страницы /ingestion нет — и эволюция схемы, которую выполняет auto_table, там тоже не видна. Это следующий шаг, и он не написан.
  • Поток с table не эволюционирует схему. Когда вы называете таблицу, контракт — это таблица: поле, которого в ней нет, отклоняется с сообщением, исправляющим ситуацию, а не изменяет таблицу, которую кто-то проверял. Собственное добавление столбца — то, что делает auto_table, и в этом разница между ними.
  • Поток с table не создаёт ни таблицу, ни индекс. Сервис, создающий таблицы, превращает опечатку во вторую таблицу, которую никто не читает, — поэтому создание происходит только при auto_table, где naming ограничивает, какие имена могут существовать, а listen.auth обязателен.
  • У опубликованного образа нет хуков, и это честный артефакт для дизайна со скомпилированными хуками: он обслуживает потоки, не объявляющие hook:.

Один маршрут, N таблиц#

auto_table направляет каждое событие в таблицу, которую называет конверт, создаёт эту таблицу, если её нет, и добавляет столбец, когда появляется новое поле:

json
{"table_name": "app_orders", "operation": "INSERT", "unique_key": "id",
 "data": {"id": "A-1", "total": 150, "customer": {"id": 7, "uf": "SP"}}}

Управляющие поля сверху, запись внутри data и семь служебных столбцов brevis_* в каждой таблице. Один маршрут, N таблиц, ничего не объявлено.
