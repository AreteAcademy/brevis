SQL

Обычные .sql-файлы превращаются в таблицы и представления в порядке зависимостей — как шаг workflow или сами по себе.

Никаких шаблонов: модель — это файл, который остаётся валидным SQL, а порядок определяется чтением самого SQL. Postgres и BigQuery, с одним и тем же набором тестов на соответствие.

Шесть команд#

командачто делает
brevis-sql compileразбирает каждую модель и разрешает каждое ребро, ни к чему не подключаясь
brevis-sql graphвыводит выведенные рёбра, чтобы неверное было видно, а не обнаруживалось
brevis-sql buildсоздаёт или заменяет каждую модель в порядке зависимостей
brevis-sql testвыполняет тесты каждой модели; каждый — это SELECT, который ничего не должен находить
brevis-sql serveотвечает на предпросмотры и запросы только для чтения по HTTP, так что консоли не нужны учётные данные хранилища
brevis-sql generation bumpзаписывает, что таблица была пересобрана, так что кэшированные ответы brevis-sql-api над ней устаревают — build --generations-from делает это для каждой собираемой модели

--select orders+ сужает любую из них до одной модели и всего, что ниже по графу.

brevis-sql serve — чтение хранилища без учётных данных#

Экраны Данные и SQL в консоли показывают, что приземлилось и что в этом находится. Ни один из них не обращается к хранилищу: они спрашивают этот сервис, который работает рядом и хранит учётные данные, которых engine намеренно не держит.

bash
brevis-sql serve --connections brevis.yaml --addr 127.0.0.1:8088

Потолок — это не бюджет: --max-bytes ограничивает один запрос, а --budget — сумму на подключение в час, проверяемую по оценке стоимости, поэтому отказ наступает до того, как деньги потрачены. Он ограничивает только хранилища, сообщающие байты, то есть BigQuery, но не Postgres; баннер при старте говорит, какая политика действует, включая её отсутствие.

Доступно только то, что объявлено в файле, и по умолчанию ничто из этого не является записью: каждая инструкция классифицируется до выполнения, чтение, которое просканировало бы больше --max-bytes, оценивается и отклоняется до того, как оно что-либо стоило, а само хранилище просят отклонять записи. Строка аудита содержит хеш инструкции и никогда не саму инструкцию.

Ему больше не нужен собственный сервисный аккаунт. brevis-sql build создаёт таблицы, поэтому его роль может писать, а сервис, отвергавший любую такую роль, означал второй аккаунт, который нужно создавать, хранить и ротировать. Роль больше не единственное, что держит границу: Postgres выполняет каждую инструкцию внутри транзакции, открытой как READ ONLY — где SELECT nextval('s'), запись, которую не видит ни один классификатор, отклоняется самим Postgres, — а BigQuery сообщает, какого рода инструкция, при пробном запуске, который её оценивает, так что CREATE TABLE или EXPORT DATA отклоняются по собственному вердикту хранилища. Хранилище, которое не может предложить ни того ни другого, всё равно отклоняет учётные данные, способные писать.

Вне BREVIS_ENV=local требуется токен, и без него сервис не запустится.

Хранилище для разработки, которое можно менять#

bash
BREVIS_SQL_SERVE_WRITES=warehouse_dev

Оно называет подключения. Один сервис достаёт до нескольких хранилищ, и разблокировка того, с которым вы разрабатываете, не должна разблокировать соседнее. На именованном подключении все уровни защиты отключаются, и сервис становится ровно настолько мощным, насколько мощны его учётные данные: потолок строк ограничивает экран, потолок байт ограничивает деньги, и ни один из них не ограничивает то, что инструкция изменяет.

Токен требуется везде, где это задано, и BREVIS_ENV=local не исключение. Баннер при старте называет каждое разблокированное подключение, консоль рисует баннер над редактором, а в метриках появляется brevis_sql_writable_connection. В продакшене оставляйте незаданным; ни один манифест в этом репозитории его не задаёт.

Токены можно именовать: BREVIS_SQL_SERVE_TOKEN_CONSOLE=… объявляет вызывающего с именем console, и каждая строка аудита, порождённая этим носителем, содержит "caller":"console". Идентичность — это учётные данные, а не заголовок, который заполняет вызывающий, поэтому журнал не может сказать того, чего не держал владелец токена. Отклонённый токен тоже оставляет строку, и никогда не записывает, что было предъявлено.

Модель — это файл, остающийся валидным SQL#

Конфигурация — это блочный комментарий в начале, поэтому файл открывается в редакторе с подсветкой, выполняется вручную в консоли, а psql -f его исполняет.

sql
/* brevis
materialized: table
tests:
  - not_null: [order_id]
  - unique: [order_id]
  - relationships: {column: customer_id, to: staging.stg_customers, field: customer_id}
*/
select * from staging.stg_orders

Никаких шаблонов. models/<schema>/<name>.sql — это <schema>.<name>, а зависимости определяются чтением SQL, а не вызовом функции, который вам пришлось бы писать. brevis-sql graph выводит то, что было выведено; depends_on: в заголовке — явное переопределение для редкого промаха.

От compile до test#

Две модели: представление, очищающее raw.orders, и зависящая от него таблица.

models/staging/stg_orders.sql:

sql
/* brevis
materialized: view
*/
select order_id, customer_id, amount, ordered_at
from raw.orders
where amount is not null

models/marts/orders.sql:

sql
/* brevis
materialized: table
tests:
  - not_null: [customer_id]
  - unique: [customer_id]
*/
select customer_id, count(*) as orders, sum(amount) as revenue
from staging.stg_orders
group by customer_id

Когда тест падает#

Если в raw.orders есть заказ без клиента, build проходит, а тест not_null — нет. Сбой называет модель, столбец, число строк и запрос — именно его вы вставляете в консоль и продолжаете сужать:

text
FAIL  marts.orders                   not_null         customer_id          1 row(s)
      SELECT COUNT(*) FROM (SELECT customer_id FROM marts.orders WHERE customer_id IS NULL) AS v
brevis-sql: 1 of 2 tests failed

Процесс завершается с кодом 1, и шаг workflow падает вместе с ним.

Тесты — это SELECT, возвращающие нарушающие строки#

not_null, unique, accepted_values, relationships. Ноль строк — это успех, и больше нечего интерпретировать.

Он сообщает, что записал#

Каждая материализованная модель выводит строку @brevis:, которую engine Brevis уже читает, поэтому она появляется в /data рядом со всем остальным (см. вывод build выше). Представление сообщает об отсутствии числа строк, а не о нуле: в нём их нет, а ноль там неотличим от таблицы, которая действительно пуста.

Два хранилища, один набор тестов#

PostgreSQL и BigQuery (--dialect bigquery), и оба прогоняют один и тот же набор тестов — написанный, пока была единственная реализация, чтобы вторая не могла тихо разойтись.

BigQuery аутентифицируется через Application Default Credentials: при workload identity это собственная идентичность pod, а --dsn-from называет переменную, содержащую id проекта.

13 МБ#

Distroless, nonroot, без оболочки. Официальный клиент BigQuery — это 31 МБ и 526 пакетов в пустом бинарном файле, поэтому здесь используется обращение к BigQuery через его REST endpoint — около 200 строк, с тестом на каждый способ, которым оно могло бы тихо ошибиться. Проверка в репозитории отклоняет этот клиент по имени, так что решение переживает плановое обновление зависимостей.

Проверено на dbt#

jaffle-shop, собранный этим образом на тех же исходных данных, что использовал dbt:

результат
строки и md5 каждой строки, по моделямидентичны, 13 из 13
столбцы и типы, по моделямидентичны, 13 из 13
13 моделей, первая сборка1,56 с

Чего он не делает#

Совместимости с dbt нет, и это решение, а не пробел. Около трети моделей реального проекта dbt не используют ничего, кроме ref, source и config; остальные используют макросы, а пакеты — это шаблонизация по замыслу. Половина совместимости, которую никто не может предсказать, хуже, чем её отсутствие.
