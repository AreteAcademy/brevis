Документация

Workflows

Полный формат YAML — шаги, зависимости, образы, ресурсы и расписание.

Workflow — это YAML-файл. Он объявляет что запускать, в каком порядке и в каком окружении — и ничего сверх этого.

Минимальная структура#

yaml
name: hello
steps:
  - id: only
    run: echo done

name идентифицирует workflow в базе данных и в интерфейсе. steps — список шагов, у каждого из которых есть уникальный id и run.

description — для чего он нужен#

Необязательное, произвольное и не читаемое ничем в engine:

yaml
name: daily-orders
description: >
  Pulls yesterday's orders from the vendor and lands them in bronze.
  Runs at 04:00 because the vendor closes its books at 03:30.
steps:
  - id: extract
    run: python fetch.py

Оно появляется в верхней части экрана workflow, над счётчиками и расписанием. Граф уже говорит, что поток делает; это единственное место, которое говорит, зачем он существует, а именно это нужно тому, кто открывает его впервые в три часа ночи.

У workflow без описания там ничего не показывается — не пустой блок, который выглядит как что-то, что не загрузилось.

Порядок: chain или dag#

yaml
type: chain   # order is the file's order
type: dag     # order comes from depends_on

chain — это синтаксический сахар: парсер превращает последовательность в рёбра, а engine знает только DAG. Используйте dag, когда порядок не линейный:

yaml
type: dag

steps:
  - id: prepare
    run: ./prepare.sh

  # Siblings: they depend on the same step, so they run in parallel.
  - id: extract
    run: ./extract.sh
    depends_on: [prepare]

  - id: validate
    run: ./validate.sh
    depends_on: [prepare]

  - id: publish
    run: ./publish.sh
    depends_on: [extract, validate]

Раннер обходит граф по уровням: всё внутри уровня выполняется параллельно, а следующий уровень начинается только после полного завершения предыдущего.

Сбой останавливает весь уровень

Раннер останавливается на первом сбое в уровне, не запуская следующий. Продолжение после ошибки дало бы частичный результат, выглядящий законченным.

Расписание#

yaml
schedule: "0 5 * * *"   # five-field cron
concurrency: 1

Без schedule workflow ручной: он запускается только триггером в интерфейсе, командой brevis run или backfill.

concurrency: 1 ограничивает одновременные запуски одного и того же workflow — именно это не даёт */15 пересечься с самим собой, если один запуск идёт дольше пятнадцати минут.

Два разных workflow, пишущих в одни и те же таблицы, нуждаются в группе. Ежедневный и */15, оба собирающие одни и те же модели dbt, объявляют каждый:

yaml
concurrency:
  group: jaffle_models   # the shared resource, named the same in both files
  limit: 1               # optional; a group without one means 1

Запуски каждого workflow группы учитываются в одном лимите, что бы их ни запустило — расписание, приземление, backfill или щелчок. Запуск, обнаруживший группу заполненной, ждёт в очереди; он не пропускается и не падает. Третий workflow, пишущий в те же таблицы, присоединяется, назвав группу. Пока он ждёт, страница запуска сообщает об этом: какая группа, её лимит и какие запуски занимают слоты.

  • Все участники объявляют один и тот же лимит. validate и publish отклоняют группу, объявленную с 1 в одном файле и с 3 в другом, в том числе относительно участников, которые уже опубликованы.
  • Группа сериализует запуски Brevis. dbt run, который кто-то запускает на своей машине, не находится в этой очереди и падает так же.

Образ и ресурсы#

yaml
image: us-central1-docker.pkg.dev/example/apps/dbt:1.10.3
resources:
  cpu: 200m
  memory: 1Gi
  limits: {memory: 2Gi}

Объявленные вверху, они — значение по умолчанию для каждого шага. Каждый шаг может переопределить своё:

yaml
steps:
  - id: bronze
    run: dbt build --select bronze+          # inherits the top-level image

  - id: notify
    image: ghcr.io/example/notify:0.3        # another runtime
    shell: false                             # distroless has no shell
    run: /notify --channel data
    resources: {cpu: 25m, memory: 32Mi, limits: {memory: 64Mi}}
    depends_on: [bronze]

Именно поэтому Go-загрузчик стоит 12 МБ и 32Mi рядом с dbt build на 1,9 ГБ, а не оба платят размер большего. См. Pod на шаг.

Запуск шага только когда есть что делать#

python
# in extract
context.set(has_rows=len(rows) > 0)
yaml
  - id: transform
    run: ./transform.sh
    depends_on: [extract]
    unless_empty: extract.has_rows

unless_empty называет ключ, а не выражение. Шаг решает и публикует ответ; engine читает один ключ и спрашивает, пуст ли он.

считается пустымсчитается заполненным
false, 0, "", null, [], {}всё остальное

"false" как строка — заполнено. Шаг, опубликовавший эти пять символов, опубликовал нечто, а угадывание, что имелся в виду логический тип, — это то, как у правила появляются мнения, которых автор не видит. Публикуйте настоящий boolean.

Почему не выражение#

Соблазнительный вариант — when: "{{ context.extract.rows > 0 }}". Мини-язык выражений — это большое обязательство: парсер, система типов, чтобы сказать, что значит > над JSON any, вопрос безопасности, потому что выражение приходит из YAML, написанного кем-то другим, и сообщения об ошибках, указывающие внутрь строки. У каждого оркестратора, где он есть, трекер ошибок полон такого.

Здесь решение живёт на языке, на котором его автор уже пишет, там, где до него может дотянуться его собственный тестовый фреймворк.

Отсутствующий ключ — это сбой, а не пустое значение#

Если ключа нет, шаг падает, и сообщение называет его рядом с тем, что издатель на самом деле записал:

step "transform" reads `extract.has_row`, and "extract" published "has_rows" but not "has_row"

Альтернатива — читать отсутствующий ключ как «пусто, значит пропустить» — превращает опечатку в шаг, который молча и навсегда перестаёт выполняться, и нигде нет объяснения почему. Это худший исход, который может быть у этой функции.

Ключ всегда квалифицирован шагом, который его публикует, и этот шаг должен быть одним из тех, от которых зависит данный. Оба условия проверяются при публикации: шаг, привязанный к ключу, который он никогда не увидит, пропускался бы вечно, а узнать об этом, когда ночной запуск перестал выполняться, слишком поздно.

Запуск шага один раз на элемент#

python
# in extract
context.set(partitions=["2026-01", "2026-02", "2026-03"])
yaml
  - id: load
    run: ./load.sh "$BREVIS_MAP_VALUE"
    depends_on: [extract]
    for_each: extract.partitions

Шаг выполняется один раз на элемент, у каждого — своя строка, своя повторная попытка и свой код завершения. Граф показывает один узел с [3], а не три узла.

переменная
BREVIS_MAP_INDEX0, 1, 2 …
BREVIS_MAP_VALUEэлемент

JSON-строка приходит без кавычек, поэтому for_each по ["2026-01"] передаёт оболочке 2026-01, а не "2026-01". Всё остальное — число, объект, список — приходит как свой JSON.

Ни одной из этих переменных нет у не размноженного шага. Переменная, которая есть всегда и всегда пуста, приучает того, кто читает окружение, её игнорировать.

Форма DAG не меняется#

Размноженный шаг — по-прежнему один узел с одним набором рёбер. Меняется лишь число строк под ним, поэтому раскладка прежняя, а [3] подсчитывается по этим строкам при чтении — ничего не хранится, поэтому нечего синхронизировать, и неверный счёт не переживёт исправленный запрос.

Пока экземпляры ещё выполняются, карточка показывает [2/3].

Один упавший экземпляр роняет шаг#

Три партиции загружаются, а одна нет — это шаг, не выполнивший свою работу, и шаги ниже это видят. Узел, ставший зелёным потому, что большая часть сработала, — это значок, который лжёт.

Повторная попытка переделывает только упавшие экземпляры. Восемнадцать партиций, которые отработали, не перезагружаются из-за того, что сломались две.

Пустой список — это skipped, а не успех#

Шаг, ничего не сделавший, потому что делать было нечего, не преуспел в этом. Зелёный узел над нулём экземпляров — именно то, на чём кто-нибудь построит дашборд.

Значение, которое не является списком, приводит к сбою, как и отсутствующий ключ — та же политика, что у unless_empty:, и по той же причине: опечатка, молча породившая ноль экземпляров, навсегда отключила бы шаг.

Разветвление ограничено, и ограничение унаследовано#

Список передаётся в контексте, а у контекста потолок в 4096 байт, идущий от kubelet. Workflow не может запросить десять тысяч pod, не найдя сначала способ сказать об этом в четырёх килобайтах. Это ограничение, которое стоит сохранить, а не обходить.

Что публикует размноженный шаг#

Его вывод записывается в строку каждого экземпляра и не виден шагам ниже. Четыре экземпляра, публикующие под именем одного шага, — это четыре значения для одного ключа, и у context.String("load.bucket") нет ответа, который не был бы догадкой. Шаг сообщает об этом в своём журнале, а не отбрасывает тихо.

Группировка шагов на графе#

yaml
steps:
  - id: extract_orders
    group: sales_data_reporting
    run: ./extract.sh
  - id: load_orders
    group: sales_data_reporting
    depends_on: [extract_orders]
    run: ./load.sh

Шаги рисуются внутри именованного блока, который сворачивается — TaskGroup из Airflow, для случая, когда DAG становится настолько большим, что перестаёт читаться.

Только визуально. TaskGroup в Airflow также добавляют префикс к id внутри себя, так что extract становится sales.extract. Здесь этого нет: префикс изменил бы каждый depends_on, каждый ключ контекста и каждую записанную строку в существующем workflow ради функции, вся ценность которой в том, что большой граф читается лучше. Пространство имён можно добавить позже — это строгое дополнение к существующему.

Группа — это метка, а не контейнер. Шаги сохраняют свои глобальные id, группа может охватывать несколько уровней, и ничто в исполнении не меняется.

Щелчок по имени группы сворачивает её: её шаги исчезают, а стрелки, пересекавшие границу, указывают на блок.

Повторное использование другого workflow#

yaml
# nightly.yaml
steps:
  - id: prepare
    run: ./prepare.sh

  - id: mlops
    uses: ml_training       # another workflow in the same publish
    depends_on: [prepare]

  - id: report
    run: ./report.sh
    depends_on: [mlops]

При публикации шаги ml_training занимают место этого шага с префиксом из его id, а узел uses исчезает:

prepare → mlops.train → mlops.evaluate → report

Они приходят как одна сворачиваемая группа, так что граф показывает то, что сказал файл.

Раскрывается при публикации, а не запускается во время выполнения. Шаг, запускавший дочерний запуск и ждавший его, — это дизайн, из-за которого Airflow попадал в взаимную блокировку, а у этого engine тот же ингредиент: потолок pod — это семафор на процесс, так что родитель, держащий слот и ожидающий дочерний запуск, которому нужны слоты из того же пула, зависает — и только под нагрузкой, то есть в продакшене. Один запуск, один граф, один пул.

Чем приходится жертвовать — дочерний запуск со своим id и своей историей.

Правила#

дочерний workflow должен быть в той же публикацииа не просто уже опубликован
стрелкивходящие в шаг становятся входящими в каждый из корней дочернего; исходящие из него — исходящими из каждого из его листьев
image, env, secrets, resources дочернегоматериализуются на каждом шаге, так что он выполняется в том, что сказал его собственный файл
ключи unless_empty / for_each дочернегоперемещаются вместе с префиксом
вложенностьразворачивается, в глубину
циклотклоняется при публикации с указанием цепочки

Та же публикация, а не «уже опубликован» — самое важное. Раскрытие, читающее базу данных, заставило бы brevis validate — который намеренно не обращается к базе — отвечать на другой вопрос, чем brevis publish, и файл, прошедший CI, был бы файлом, провалившим развёртывание.

Дочерний workflow по-прежнему можно опубликовать отдельно: раскрытие копирует, а не потребляет. Шаг не может одновременно иметь uses: и объявлять run:, action: или marker: — это файл, говорящий две вещи.

Как сказать, что означает стрелка#

Зависимость может нести метку, показываемую на стрелке на графе.

yaml
steps:
  - id: determine_load_type
    run: ./decide.sh

  - id: load_full
    run: ./full.sh
    depends_on:
      - {step: determine_load_type, label: additional data}

  - id: load_delta
    run: ./delta.sh
    depends_on:
      - step: determine_load_type
        label: changed existing data

Простая форма — depends_on: [extract] — продолжает работать и остаётся обычной. Большинству зависимостей нечего сказать, а метка на каждой стрелке — шум.

Метки оправдывают себя на ветвлении: две стрелки, выходящие из одного шага без подписей, — это схема, чтобы прочитать которую нужно открывать исходник, а граф существует именно для того, чтобы этого избегать.

Шаг, который ничего не делает#

yaml
steps:
  - id: start
    marker: true

  - id: end
    marker: true
    depends_on: [load_full, load_delta, report]

marker: true — это шаг без команды. Он ничего не запускает, мгновенно завершается успешно и появляется на графе.

Это не украшение. end, зависящий от каждой ветки, превращает вопрос всё ли завершилось? в один узел вместо шести стрелок, за которыми нужно следить, — и он ведёт себя как любой другой шаг, так что end под упавшей веткой пропускается, а не зеленеет.

Шаг без run: и без marker: true по-прежнему отклоняется. Эти два случая не должны сливаться в один: пустая команда почти всегда ошибка, а marker: true — способ сказать, что так и задумано. Маркер, который к тому же объявляет run:, тоже отклоняется — это файл, говорящий две вещи.

Запуск шага только когда что-то упало#

По умолчанию шаг выполняется, когда всё до него сработало. when: меняет это.

yaml
steps:
  - id: extract
    run: python fetch.py

  - id: notify_failure
    run: ./notify.sh
    depends_on: [extract]
    when: any_failed          # runs precisely when extract did not make it

  - id: cleanup
    run: ./cleanup.sh
    depends_on: [extract, transform]
    when: all_done            # runs either way
правило
all_successпо умолчанию. Всё, от чего зависит этот шаг, завершилось успешно — его собственные зависимости, как в Airflow
any_failedхотя бы один шаг, от которого зависит этот, упал
all_doneвсё, от чего зависит этот шаг, завершилось, как бы ни закончилось

Неизвестное правило отклоняется при публикации с указанием допустимых. Иначе нельзя: when: on_failure, прочитанное как «по умолчанию», выполнялось бы при успехе — наоборот тому, что написано, и это обнаружилось бы в ту ночь, когда это имело значение.

Шаг, который не выполняется, — это skipped#

Это отдельное состояние, нарисованное собственным цветом, и оно несёт причину: extract был failed. Раньше у шага ниже сбоя вообще не было записи, и экран показывал его ожидающим вечно.

skipped — не сбой и не успех. Шаг, у которого сломался предшественник, не упал — ему просто не дали шанса, — а назвать его успехом значит солгать, и эта ложь дойдёт до статуса самого запуска.

Правило запуска решает, какие шаги выполняются. Оно не решает исход запуска: notify_failure, доставивший своё сообщение, не означает, что пайплайн сработал, и запуск остаётся упавшим.

all_success локален, как в Airflow#

Правило спрашивает о собственных зависимостях шага и больше ни о чём. Сбой в несвязанной ветке не останавливает этот:

extract_orders ──✕                 (failed)
extract_users  ──✓── transform_users ──✓     keeps going

Ветка ниже сбоя всё равно останавливается — то, что all_success локален, не значит, что его нет.

Раньше этот engine прерывал весь граф при первом сбое. У этого была причина: продолжение после ошибки давало частичный результат, выглядящий законченным, и пайплайн опаздывал на 28 дней, а никто не замечал.

Что заменяет эту защиту, и это не ничто:

  • запуск всё равно падает с той же ошибкой;
  • граф показывает упавший шаг красным, а каждый пропущенный — своим цветом, и каждый говорит, какой шаг его остановил;
  • алерт всё равно уходит, когда запуск сдаётся.

Частичный результат больше не выглядит законченным, потому что запуск говорит, что это не так.

От чего отказались, прямо: несвязанная ветка теперь записывает свои данные в запуске, упавшем в другом месте.

Повторная попытка перезапускает только упавшее#

Повторная попытка запуска не переделывает весь граф. Шаг, уже успешно выполнившийся в более ранней попытке того же запуска, сохраняет свой результат и не выполняется снова — так же ведёт себя очищенный запуск DAG в Airflow.

attempt 1   extract ✓    load ✕    report (skipped)
attempt 2   extract –    load ✓    report ✓            extract is not re-run

Он сохраняет свою исходную строку: его длительность, журнал и опубликованное им принадлежат первой попытке, потому что именно тогда была выполнена работа. Шаг ниже по-прежнему читает то, что тот опубликовал — контекст запуска хранится, а не перестраивается.

Важное различие: речь о более ранних попытках этого запуска. Шаг, успешный в запуске вчерашнего дня, сегодня выполняется как обычно. (Существует и тот другой вопрос — он говорит SDK, первый ли это раз для шага; см. BREVIS_RUN_FIRST.)

Пропущенный шаг не считается урегулированным: он не выполнялся, и повторная попытка решает о нём заново, исходя из исходов новой попытки.

Объявление о сбоях шага#

Каждый сбой уже объявляется: при настроенном webhook запуск, который сдаётся, отправляет одно сообщение, без блока, повторяемого в каждом файле. on_error нужен шагу, которому нужно собственное.

yaml
steps:
  - id: fetch_observations
    run: python fetch.py
    on_error:
      type: SLACK
поле
typeобязательноSLACK. Неизвестное значение отклоняется при публикации с указанием допустимых
whengive_upattempt объявляет о каждой неудачной попытке, а не только о последней

Приходят два сообщения вместо одного, и в этом смысл: алерт уровня запуска говорит id_verification упал — то, что нужно владельцу пайплайна; алерт уровня шага говорит fetch_observations упал — то, что нужно владельцу этой интеграции.

Поля webhook или url нет, и не будет. Адресат — это учётные данные: тот, кто ими владеет, пишет в канал так, как если бы он был платформой, а файл workflow пишет человек, которому не обязательно разрешено выбирать, куда идут алерты компании. Файл говорит будет ли и как; установка говорит куда — через BREVIS_SLACK_WEBHOOK.

when: give_up — значение по умолчанию из-за того, чья это ночь. Шаг, дважды падающий и проходящий с третьей попытки, при другом значении по умолчанию отправил бы два сообщения, и второе пришло бы после того, как проблема исчезла.

О шаге, который не падал, никогда не объявляется. В workflow, где ломается одна ветка, владельца другой ветки не будят.

Доставка — работа brevis alert: алерт записывается в той же транзакции, что и сбой, поэтому сбой Slack задерживает его, а не теряет.

Теги#

yaml
tags: [analytics, dbt, daily]

Они используются для фильтрации в интерфейсе. На исполнение они не влияют.

Валидация#

Валидации не нужна база данных, поэтому она запускается в CI вместе с тестами:

bash
brevis validate workflows/
  ok    daily_analytics              dag  5 steps, 5 dependencias  (manual)
  ok    daily-report                 chain  3 steps, 2 dependencias  cron 0 2 * * *

Принимает файл или каталог. В каталоге она сопоставляет *.y*ml и сортирует — два запуска дают один и тот же журнал, а разница между двумя развёртываниями не превращается в шум.

Публикация#

bash
brevis publish workflows/
brevis publish workflows/ --project acme --prune

--prune удаляет из проекта workflow, отсутствующие в опубликованном списке, сохраняя их историю. Это не значение по умолчанию по практической причине: publish one-file.yaml не должен удалять остальные сорок восемь только потому, что они не названы в командной строке.
