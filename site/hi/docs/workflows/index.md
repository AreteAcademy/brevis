# Workflows

> पूरा YAML फ़ॉर्मेट — steps, निर्भरताएँ, images, संसाधन और शेड्यूल।

*https://brevis.sh/hi/docs/workflows/ · brevis.sh docs (hi)*

---

Workflow एक YAML फ़ाइल है। वह घोषित करती है कि **क्या चलाना है**, **किस क्रम में** और **किस runtime के साथ** —
और इससे आगे कुछ नहीं।

## न्यूनतम संरचना

```yaml
name: hello
steps:
  - id: only
    run: echo done
```

`name` डेटाबेस में और इंटरफ़ेस में workflow की पहचान है। `steps` steps की सूची है, हर एक की अनूठी `id` और एक `run` के साथ।

### `description` — यह किसलिए है

वैकल्पिक, मुक्त-रूप, और engine में कुछ इसे नहीं पढ़ता:

```yaml
name: daily-orders
description: >
  Pulls yesterday's orders from the vendor and lands them in bronze.
  Runs at 04:00 because the vendor closes its books at 03:30.
steps:
  - id: extract
    run: python fetch.py
```

यह workflow की स्क्रीन के शीर्ष पर दिखता है, गिनतियों और शेड्यूल के ऊपर। ग्राफ़ पहले से बताता है कि प्रवाह **क्या करता है**; यही अकेली जगह है जो बताती है कि वह क्यों मौजूद है, और रात के तीन बजे पहली बार उसे खोलने वाले को असल में यही चाहिए।

जिस workflow में यह नहीं होता वहाँ कुछ नहीं दिखता — खाली block नहीं, जो ऐसा पढ़ा जाता है जैसे कुछ लोड होने में विफल रहा।

## क्रम: chain या dag

```yaml
type: chain   # order is the file's order
type: dag     # order comes from depends_on
```

`chain` सिंटैक्टिक शुगर है: parser क्रम को edges में बदल देता है, और **engine सिर्फ़ DAG जानता है**। क्रम सीधा न हो तो `dag` इस्तेमाल करें:

```yaml
type: dag

steps:
  - id: prepare
    run: ./prepare.sh

  # Siblings: they depend on the same step, so they run in parallel.
  - id: extract
    run: ./extract.sh
    depends_on: [prepare]

  - id: validate
    run: ./validate.sh
    depends_on: [prepare]

  - id: publish
    run: ./publish.sh
    depends_on: [extract, validate]
```

Runner ग्राफ़ पर **स्तरों के हिसाब से** चलता है: एक स्तर के भीतर सब कुछ समानांतर चलता है, और अगला स्तर तभी शुरू होता है जब पिछला पूरी तरह बंद हो जाए।

:::warning एक विफलता पूरे स्तर को रोक देती है
Runner स्तर में **पहली** विफलता पर रुक जाता है, अगला स्तर शुरू किए बिना। त्रुटि के बाद चलते रहना ऐसा आंशिक नतीजा बनाता जो पूरा दिखता है।
:::

## शेड्यूल

```yaml
schedule: "0 5 * * *"   # five-field cron
concurrency: 1
```

`schedule` के बिना workflow मैन्युअल है: वह सिर्फ़ इंटरफ़ेस के ट्रिगर, `brevis run` या `backfill` से चलता है।

`concurrency: 1` उसी workflow के एक साथ चलने वाले run को सीमित करता है — यही `*/15` को खुद से ओवरलैप होने से रोकता है जब कोई run पंद्रह मिनट से आगे चला जाए।

एक ही तालिकाएँ लिखने वाले दो **अलग** workflows को **समूह** चाहिए। एक daily और एक `*/15`, जो दोनों वही dbt मॉडल बनाते हैं, दोनों यह घोषित करते हैं:

```yaml
concurrency:
  group: jaffle_models   # the shared resource, named the same in both files
  limit: 1               # optional; a group without one means 1
```

समूह के हर workflow के run एक सीमा के विरुद्ध गिने जाते हैं, उन्हें जिसने भी शुरू किया हो — शेड्यूल, landing, backfill या क्लिक। जिस run को समूह भरा मिले वह **कतार में प्रतीक्षा करता है**; वह छोड़ा नहीं जाता और विफल नहीं होता। वही तालिकाएँ लिखने वाला तीसरा workflow समूह का नाम लेकर जुड़ता है। प्रतीक्षा के दौरान run का पेज यह बताता है: कौन-सा समूह, उसकी सीमा, और कौन-से run slots थामे हैं।

- हर सदस्य **वही सीमा** घोषित करता है। `validate` और `publish` ऐसे समूह को मना करते हैं जो एक फ़ाइल में 1 और दूसरी में 3 के साथ घोषित हो, पहले से प्रकाशित सदस्यों के विरुद्ध भी।
- समूह **Brevis के run** को क्रमबद्ध करता है। कोई अपनी मशीन पर `dbt run` शुरू करे तो वह इस कतार में नहीं है, और उसी तरह विफल होता है।

## Image और संसाधन

```yaml
image: us-central1-docker.pkg.dev/example/apps/dbt:1.10.3
resources:
  cpu: 200m
  memory: 1Gi
  limits: {memory: 2Gi}
```

शीर्ष पर घोषित होने पर वे **हर step का डिफ़ॉल्ट** हैं। हर step अपना खुद का override कर सकता है:

```yaml
steps:
  - id: bronze
    run: dbt build --select bronze+          # inherits the top-level image

  - id: notify
    image: ghcr.io/example/notify:0.3        # another runtime
    shell: false                             # distroless has no shell
    run: /notify --channel data
    resources: {cpu: 25m, memory: 32Mi, limits: {memory: 64Mi}}
    depends_on: [bronze]
```

इसी से Go fetcher 1.9 GB के `dbt build` के बगल में 12 MB और 32Mi का पड़ता है, दोनों के बड़े वाले का आकार चुकाने के बजाय। देखें
[हर step के लिए एक pod](/hi/docs/pod-per-step/index.md)।

## Step के फ़ील्ड

| फ़ील्ड | | |
|---|---|---|
| `id` | **ज़रूरी** | workflow में अनूठी; ग्राफ़ और लॉग में दिखने वाला नाम |
| `run` | | कमांड |
| `image` | | step की image; इसके बिना, शीर्ष वाली विरासत में मिलती है |
| `host` | | कमांड को ऐसी मशीन पर भेजें जिसे engine **नहीं** सँभालता — `image` का विकल्प, साथी कभी नहीं। देखें [Kubernetes गाइड में `host:`](https://github.com/AreteAcademy/brevis/blob/master/docs/KUBERNETES.md#a-third-place-a-step-can-run-host) |
| `shell` | `true` | `false` बिना shell के चलाता है — distroless पर ज़रूरी |
| `depends_on` | | `id` की सूची जो पहले खत्म होनी चाहिए; प्रविष्टि `{step, label}` हो सकती है |
| `marker` | `false` | बिना कमांड का step, `start` या `end` के लिए |
| `resources` | | उस step के लिए `cpu`, `memory` और `limits` |
| `runtime`, `tools` | | step की भाषा और टूल — देखें [Step runtime](/hi/docs/runtime/index.md) |
| `when` | `all_success` | अपनी निर्भरताओं की किस स्थिति में यह step चलता है — नीचे देखें |
| `unless_empty` | | वह संदर्भ key जो तय करती है कि करने को कुछ है या नहीं — नीचे देखें |
| `for_each` | | सूची रखने वाली संदर्भ key; step हर तत्व के लिए एक बार चलता है — नीचे देखें |
| `group` | | इस step को नामित, सिकुड़ने वाले बॉक्स के भीतर बनाता है — नीचे देखें |
| `uses` | | दूसरा workflow जिसके steps इसकी जगह लेते हैं — नीचे देखें |
| `on_error` | | इस step की विफलताओं की घोषणा करता है — नीचे देखें |

## Step को सिर्फ़ तब चलाना जब करने को कुछ हो

```python
# in extract
context.set(has_rows=len(rows) > 0)
```

```yaml
  - id: transform
    run: ./transform.sh
    depends_on: [extract]
    unless_empty: extract.has_rows
```

`unless_empty` **key** का नाम लेता है, एक्सप्रेशन का नहीं। Step फ़ैसला करता है और जवाब प्रकाशित करता है; engine एक key पढ़ता है और पूछता है कि वह खाली है या नहीं।

| खाली गिना जाता है | मौजूद गिना जाता है |
|---|---|
| `false`, `0`, `""`, `null`, `[]`, `{}` | बाकी सब कुछ |

**string** के रूप में `"false"` मौजूद है। जिस step ने वे पाँच अक्षर प्रकाशित किए, उसने कुछ प्रकाशित किया, और यह अंदाज़ा लगाना कि उसका मतलब boolean था ही वह तरीका है जिससे कोई नियम ऐसी राय रखने लगता है जो उसका लेखक देख नहीं सकता। असली boolean प्रकाशित करें।

### एक्सप्रेशन क्यों नहीं

लुभावना डिज़ाइन `when: "{{ context.extract.rows > 0 }}"` है। छोटी एक्सप्रेशन भाषा बड़ी प्रतिबद्धता है: एक parser, यह बताने के लिए टाइप सिस्टम कि JSON `any` में `>` का क्या अर्थ है, एक सुरक्षा कहानी क्योंकि एक्सप्रेशन किसी और की लिखी YAML से निकलता है, और ऐसे त्रुटि संदेश जो string के भीतर इशारा करते हैं। जिस भी ऑर्केस्ट्रेटर में यह है, उसके bug tracker में इसी से भरा पड़ा है।

यहाँ फ़ैसला उसी भाषा में रहता है जो उसका लेखक पहले से लिखता है, जहाँ उसका अपना टेस्ट फ्रेमवर्क पहुँच सकता है।

### गायब key विफलता है, खाली मान नहीं

Key न हो तो step **विफल** होता है और संदेश उसका नाम बताता है, साथ में यह भी कि प्रकाशक ने असल में क्या लिखा:

```
step "transform" reads `extract.has_row`, and "extract" published "has_rows" but not "has_row"
```

विकल्प — गायब key को "खाली, इसलिए छोड़ दो" पढ़ना — टाइपो को ऐसे step में बदल देता है जो चुपचाप और हमेशा के लिए चलना बंद कर दे, और कहीं कुछ न बताए कि क्यों। इस फ़ीचर का यह सबसे बुरा नतीजा है।

Key हमेशा उस step से योग्य होती है जो उसे प्रकाशित करता है, और वह step ऐसा होना चाहिए जिस पर यह निर्भर हो। दोनों **publish** पर मना किए जाते हैं: जो step उस key पर टिका है जिसे वह कभी नहीं देख सकता, वह हमेशा छोड़ा जाता, और जब रात का run चलना बंद हो तब यह पता चलना देर है।

## Step को हर तत्व के लिए एक बार चलाना

```python
# in extract
context.set(partitions=["2026-01", "2026-02", "2026-03"])
```

```yaml
  - id: load
    run: ./load.sh "$BREVIS_MAP_VALUE"
    depends_on: [extract]
    for_each: extract.partitions
```

Step हर तत्व के लिए एक बार चलता है, हर एक की अपनी पंक्ति, retry और exit code के साथ। ग्राफ़ **`[3]` वाला एक नोड** दिखाता है, तीन नोड नहीं।

| वेरिएबल | |
|---|---|
| `BREVIS_MAP_INDEX` | `0`, `1`, `2` … |
| `BREVIS_MAP_VALUE` | तत्व |

JSON string **बिना अपने उद्धरण चिह्नों के** आती है, इसलिए `["2026-01"]` पर `for_each` shell को `2026-01` देता है, `"2026-01"` नहीं। बाकी सब कुछ — संख्या, ऑब्जेक्ट, सूची — अपने JSON के रूप में आता है।

Mapped न होने वाले step पर दोनों में से कोई वेरिएबल नहीं होता। जो हमेशा मौजूद और हमेशा खाली हो, वह environment पढ़ने वाले को उसे अनदेखा करना सिखाता है।

### DAG का आकार नहीं बदलता

Mapped step अब भी एक नोड है, edges के एक ही सेट के साथ। उसके नीचे सिर्फ़ पंक्तियों की संख्या बदलती है, इसलिए लेआउट वही है जो हमेशा था और `[3]` पढ़ने के समय उन पंक्तियों से गिना जाता है — कुछ सहेजा नहीं जाता, इसलिए कुछ तालमेल में रखना नहीं पड़ता और गलत गिनती ठीक की गई query से ज़्यादा नहीं जी सकती।

जब तक इंस्टेंस चल रहे हैं, कार्ड `[2/3]` पढ़ता है।

### एक विफल इंस्टेंस step को विफल करता है

तीन partitions लोड हों और एक न हो, तो वह step अपना काम नहीं कर पाया, और उसके नीचे के steps यह देखते हैं। जो नोड इसलिए हरा हो जाए कि ज़्यादातर चला, वह झूठ बोलने वाला बैज है।

**Retry सिर्फ़ उन इंस्टेंस को दोबारा करता है जो विफल हुए।** अठारह partitions जो चले, दो के टूटने पर दोबारा लोड नहीं होते।

### खाली सूची `skipped` है, सफलता नहीं

जिस step ने कुछ नहीं किया क्योंकि करने को कुछ नहीं था, वह उसे करने में सफल नहीं हुआ। शून्य इंस्टेंस के ऊपर हरा नोड ठीक वही चीज़ है जिस पर कोई डैशबोर्ड बना बैठता है।

**सूची न होने वाला** मान विफल होता है, और गायब key भी — वही नीति जो `unless_empty:` की है, उसी कारण से: चुपचाप शून्य इंस्टेंस बनाने वाला टाइपो step को हमेशा के लिए बंद कर देता।

### Fan-out सीमित है, और सीमा विरासत में मिलती है

सूची संदर्भ में चलती है, और संदर्भ की 4096 बाइट की सीमा kubelet से आती है। Workflow दस हज़ार pods नहीं माँग सकता जब तक पहले चार किलोबाइट में उसे कहने का तरीका न खोज ले। यह रखने लायक सीमा है, घूमकर निकलने लायक नहीं।

### Mapped step क्या प्रकाशित करता है

उसका आउटपुट हर इंस्टेंस की पंक्ति पर दर्ज होता है और नीचे के steps को **नहीं** दिखता। एक step के नाम के नीचे प्रकाशित करते चार इंस्टेंस एक key के चार मान हैं, और `context.String("load.bucket")` का कोई जवाब अनुमान के सिवा कुछ नहीं। Step इसे चुपचाप गिराने के बजाय अपने लॉग में बता देता है।

## ग्राफ़ पर steps को समूहित करना

```yaml
steps:
  - id: extract_orders
    group: sales_data_reporting
    run: ./extract.sh
  - id: load_orders
    group: sales_data_reporting
    depends_on: [extract_orders]
    run: ./load.sh
```

Steps नामित बॉक्स के भीतर बनते हैं जो सिकुड़ता है — Airflow का TaskGroup, उस स्थिति के लिए जब DAG इतना बड़ा हो जाए कि पढ़ने लायक न रहे।

**सिर्फ़ दृश्य।** Airflow के TaskGroups उनके भीतर की ids पर *उपसर्ग* भी लगाते हैं, इसलिए `extract` `sales.extract` बन जाता है। यह ऐसा नहीं करता: उपसर्ग मौजूदा workflow के हर `depends_on`, हर संदर्भ key और हर दर्ज पंक्ति को बदल देता, ऐसे फ़ीचर के लिए जिसका पूरा मूल्य यह है कि बड़ा ग्राफ़ बेहतर पढ़ा जाता है। Namespacing बाद में जोड़ी जा सकती है — यह इसमें सख़्त जोड़ है।

समूह **लेबल** है, कंटेनर नहीं। Steps अपनी वैश्विक ids रखते हैं, समूह स्तरों में फैल सकता है, और execution के बारे में कुछ नहीं बदलता।

समूह के नाम पर क्लिक करने से वह सिकुड़ता है: उसके steps गायब हो जाते हैं और सीमा पार करने वाले तीर बॉक्स की ओर इशारा करते हैं।

## दूसरे workflow का दोबारा इस्तेमाल

```yaml
# nightly.yaml
steps:
  - id: prepare
    run: ./prepare.sh

  - id: mlops
    uses: ml_training       # another workflow in the same publish
    depends_on: [prepare]

  - id: report
    run: ./report.sh
    depends_on: [mlops]
```

**Publish** पर, `ml_training` के steps उस step की जगह लेते हैं, उसकी id के उपसर्ग के साथ, और `uses` नोड गायब हो जाता है:

```
prepare → mlops.train → mlops.evaluate → report
```

वे एक सिकुड़ने वाले समूह के रूप में आते हैं, इसलिए ग्राफ़ वही दिखाता है जो फ़ाइल ने कहा।

**Publish पर फैलाया जाता है, run के समय नहीं चलाया जाता।** जो step child *run* ट्रिगर करके इंतज़ार करे, वही डिज़ाइन है जिसने Airflow को deadlock किया, और इस engine में भी वही सामग्री है: pod की सीमा प्रति-प्रोसेस semaphore है, इसलिए slot थामे बैठा parent उस child के इंतज़ार में जिसे उसी pool से slots चाहिए, अटक जाता है — और सिर्फ़ भार में, यानी production में। एक run, एक ग्राफ़, एक pool।

जो यह छोड़ता है वह अपनी id और अपने इतिहास वाला child run है।

### नियम

| | |
|---|---|
| child **उसी publish** में होना चाहिए | सिर्फ़ पहले से प्रकाशित होना काफ़ी नहीं |
| तीर | step में आने वाले तीर child के हर **root** में आने वाले तीर बन जाते हैं; उससे बाहर जाने वाले, उसके हर **leaf** से बाहर |
| child के `image`, `env`, `secrets`, `resources` | हर step पर materialise होते हैं, ताकि वह उसमें चले जो उसकी अपनी फ़ाइल ने कहा |
| child की `unless_empty` / `for_each` keys | उपसर्ग के साथ चलती हैं |
| nesting | समतल की जाती है, गहराई-प्रथम |
| चक्र | publish पर मना, श्रृंखला का नाम बताते हुए |

**उसी publish में, और "पहले से प्रकाशित" नहीं, यह ज़रूरी वाली बात है।** डेटाबेस पढ़ने वाला विस्तार `brevis validate` — जो जानबूझकर कोई डेटाबेस नहीं छूता — को `brevis publish` से अलग सवाल का जवाब देने वाला बना देता, और जो फ़ाइल CI में पास हुई वही deploy में विफल होती।

Child अब भी अपने आप प्रकाशित हो सकता है: विस्तार **नकल** करता है, खपत नहीं। Step `uses:` भी और `run:`, `action:` या `marker:` भी घोषित नहीं कर सकता — यह फ़ाइल का दो बातें कहना है।

## तीर का मतलब बताना

निर्भरता लेबल ढो सकती है, जो ग्राफ़ में तीर पर दिखता है।

```yaml
steps:
  - id: determine_load_type
    run: ./decide.sh

  - id: load_full
    run: ./full.sh
    depends_on:
      - {step: determine_load_type, label: additional data}

  - id: load_delta
    run: ./delta.sh
    depends_on:
      - step: determine_load_type
        label: changed existing data
```

सादा रूप — `depends_on: [extract]` — काम करता रहता है और सामान्य बना रहता है। ज़्यादातर निर्भरताओं के पास कहने को कुछ नहीं होता, और हर तीर पर लेबल शोर है।

लेबल अपनी जगह **शाखा** पर कमाते हैं: एक ही step से निकलते दो तीर जिन पर कुछ लिखा नहीं, ऐसा डायग्राम है जिसे पढ़ने के लिए स्रोत खोलना पड़ता है, और ग्राफ़ ठीक इसी से बचने के लिए है।

## ऐसा step जो कुछ नहीं करता

```yaml
steps:
  - id: start
    marker: true

  - id: end
    marker: true
    depends_on: [load_full, load_delta, report]
```

`marker: true` बिना कमांड का step है। वह कुछ नहीं चलाता, तुरंत सफल होता है, और ग्राफ़ पर दिखता है।

यह सजावट नहीं है। हर शाखा पर निर्भर `end` *क्या पूरा काम खत्म हुआ?* को छह तीरों के पीछे चलने के बजाय एक नोड बना देता है — और वह किसी भी दूसरे step की तरह व्यवहार करता है, इसलिए विफल शाखा के नीचे का `end` **skipped** होता है, हरा नहीं।

**जिस step में न `run:` है और न `marker: true`, वह अब भी मना है।** दोनों मामले एक में नहीं सिमटने चाहिए: खाली कमांड लगभग हमेशा गलती है, और `marker: true` वह तरीका है जिससे कोई कहता है कि उसका यही मतलब था। जो marker `run:` भी घोषित करे वह भी मना है — यह फ़ाइल का दो बातें कहना है।

## Step को सिर्फ़ तब चलाना जब कुछ विफल हुआ हो

डिफ़ॉल्ट रूप से step तब चलता है जब उससे पहले सब कुछ चला। `when:` इसे बदलता है।

```yaml
steps:
  - id: extract
    run: python fetch.py

  - id: notify_failure
    run: ./notify.sh
    depends_on: [extract]
    when: any_failed          # runs precisely when extract did not make it

  - id: cleanup
    run: ./cleanup.sh
    depends_on: [extract, transform]
    when: all_done            # runs either way
```

| नियम | |
|---|---|
| `all_success` | डिफ़ॉल्ट। जिन पर यह step निर्भर है वे सब सफल हुए — इसकी **अपनी** निर्भरताएँ, जैसे Airflow में |
| `any_failed` | जिन steps पर यह निर्भर है उनमें से कम से कम एक विफल हुआ |
| `all_done` | जिन पर यह step निर्भर है वे सब खत्म हो चुके, चाहे जैसे भी खत्म हुए |

अज्ञात नियम publish पर मना किया जाता है, यह बताते हुए कि क्या मान्य है। ऐसा होना ही चाहिए: `when: on_failure` जिसे "डिफ़ॉल्ट" पढ़ लिया जाए वह **सफलता** पर चलता — जो वह कहता है उसका उलटा, उस रात पता चलता जब मायने रखता।

### जो step नहीं चलता वह `skipped` है

यह अपनी अलग स्थिति है, अपने रंग में बनी, और कारण साथ ढोती है: *`extract` विफल था*। इससे पहले, विफलता के नीचे के step का कोई रिकॉर्ड ही नहीं था और स्क्रीन उसे हमेशा के लिए pending दिखाती थी।

`skipped` न विफलता है न सफलता। जिस step का upstream टूटा वह विफल नहीं हुआ — उसे मौका ही नहीं मिला — और उसे सफलता कहना झूठ है जो run की अपनी स्थिति तक पहुँचता है।

Trigger नियम तय करता है कि कौन-से steps **चलें**। वह run का नतीजा तय नहीं करता: `notify_failure` जिसने अपना संदेश पहुँचा दिया, उसका मतलब यह नहीं कि pipeline चली, और run अब भी विफल है।

### `all_success` स्थानीय है, जैसे Airflow में

नियम step की **अपनी** निर्भरताओं के बारे में पूछता है और कुछ नहीं। असंबंधित शाखा की विफलता इसे नहीं रोकती:

```
extract_orders ──✕                 (failed)
extract_users  ──✓── transform_users ──✓     keeps going
```

विफलता के **नीचे** की शाखा अब भी रुकती है — `all_success` के स्थानीय होने का मतलब उसका गायब होना नहीं है।

यह engine पहली विफलता पर पूरा ग्राफ़ रोक देता था। इसका कारण था: त्रुटि के बाद चलते रहना ऐसा आंशिक नतीजा बनाता था जो पूरा दिखता है, और एक pipeline किसी के ध्यान दिए बिना 28 दिन देर से चली।

**इस सुरक्षा की जगह जो आता है**, और वह कुछ नहीं नहीं है:

- run अब भी उसी त्रुटि के साथ **विफल** होता है;
- ग्राफ़ विफल step को लाल में और हर skipped को अपने रंग में दिखाता है, हर एक बताता है कि किस step ने उसे रोका;
- run के हार मानने पर अलर्ट अब भी जाता है।

आंशिक नतीजा अब पूरा नहीं दिखता, क्योंकि run कहता है कि वह नहीं है।

**जो छोड़ा गया है**, सीधे कहें तो: कहीं और विफल हुए run पर असंबंधित शाखा अब अपना डेटा लिखती है।

### Retry सिर्फ़ वही दोबारा चलाता है जो विफल हुआ

Run का retry पूरा ग्राफ़ दोबारा नहीं करता। जो step **उसी run** के पहले प्रयास में पहले ही सफल हो चुका है, वह अपना नतीजा रखता है और दोबारा नहीं चलता — जैसे Airflow में cleared DAG run व्यवहार करता है।

```
attempt 1   extract ✓    load ✕    report (skipped)
attempt 2   extract –    load ✓    report ✓            extract is not re-run
```

वह अपनी मूल पंक्ति रखता है: उसकी अवधि, उसका लॉग और जो उसने प्रकाशित किया वे पहले प्रयास के हैं, क्योंकि काम तब हुआ। **उसके नीचे का step अब भी वही पढ़ता है जो उसने प्रकाशित किया** — run का संदर्भ सहेजा गया है, दोबारा नहीं बनाया गया।

मायने रखने वाला फ़र्क: यह **इस run के** पहले प्रयासों के बारे में है। जो step *कल के* run में सफल हुआ वह आज सामान्य रूप से चलता है। (वह दूसरा सवाल भी मौजूद है, और वही SDK को बताता है कि यह step का पहली बार है या नहीं — देखें `BREVIS_RUN_FIRST`।)

जो step **skipped** हुआ वह निपटा हुआ नहीं है: वह कभी चला नहीं, और retry नए प्रयास के नतीजों के साथ उसके बारे में दोबारा फ़ैसला करता है।

## Step की विफलताओं की घोषणा

हर विफलता की घोषणा पहले से होती है: webhook कॉन्फ़िगर हो तो हार मानने वाला run एक संदेश भेजता है, किसी फ़ाइल में कोई block दोहराए बिना। `on_error` उस step के लिए है जिसे अपना चाहिए।

```yaml
steps:
  - id: fetch_observations
    run: python fetch.py
    on_error:
      type: SLACK
```

| फ़ील्ड | | |
|---|---|---|
| `type` | **ज़रूरी** | `SLACK`। अज्ञात मान publish पर मना, यह बताते हुए कि क्या मान्य है |
| `when` | `give_up` | `attempt` हर विफल प्रयास की घोषणा करता है, सिर्फ़ आखिरी की नहीं |

एक के बजाय दो संदेश आते हैं, और यही मुद्दा है: run-स्तर का अलर्ट कहता है *`id_verification` विफल हुआ*, जो pipeline के मालिक को चाहिए; step-स्तर का कहता है *`fetch_observations` विफल हुआ*, जो उस इंटीग्रेशन के मालिक को चाहिए।

**कोई `webhook` या `url` फ़ील्ड नहीं है, और न होगा।** गंतव्य क्रेडेंशियल है — जिसके पास है वह चैनल में ऐसे पोस्ट करता है जैसे प्लैटफ़ॉर्म हो — और workflow फ़ाइल उस व्यक्ति की लिखी है जिसे ज़रूरी नहीं कि कंपनी के अलर्ट कहाँ जाएँ यह चुनने की अनुमति हो। फ़ाइल कहती है **क्या** और **कैसे**; इंस्टॉलेशन कहता है **कहाँ**, `BREVIS_SLACK_WEBHOOK` के ज़रिए।

**`when: give_up` डिफ़ॉल्ट इसलिए है कि रात किसकी है।** जो step दो बार विफल होकर तीसरी कोशिश में पास हो, वह दूसरे डिफ़ॉल्ट के तहत दो संदेश भेजता, और दूसरा तब पहुँचता जब समस्या जा चुकी होती।

**जो step विफल नहीं हुआ उसकी घोषणा कभी नहीं होती।** जिस workflow में एक शाखा टूटती है, वहाँ दूसरी शाखा के मालिक को नहीं जगाया जाता।

डिलीवरी `brevis alert` का काम है — अलर्ट उसी लेनदेन में दर्ज होता है जिसमें विफलता, इसलिए Slack की गड़बड़ी उसे खोने के बजाय देर करती है।

## Tags

```yaml
tags: [analytics, dbt, daily]
```

ये इंटरफ़ेस में फ़िल्टर करते हैं। ये execution पर असर नहीं डालते।

## Validation

Validation को डेटाबेस नहीं चाहिए, इसलिए यह CI में टेस्ट के साथ चलता है:

```bash
brevis validate workflows/
```

```
  ok    daily_analytics              dag  5 steps, 5 dependencias  (manual)
  ok    daily-report                 chain  3 steps, 2 dependencias  cron 0 2 * * *
```

यह फ़ाइल या डायरेक्टरी लेता है। डायरेक्टरी में यह `*.y*ml` से मेल खाता है और क्रमबद्ध करता है — दो run एक ही लॉग बनाते हैं, और दो deploys के बीच का फ़र्क शोर नहीं बनता।

## Publish करना

```bash
brevis publish workflows/
brevis publish workflows/ --project acme --prune
```

`--prune` प्रकाशित सूची में अनुपस्थित workflows को प्रोजेक्ट से हटाता है, उनका इतिहास सुरक्षित रखते हुए। यह डिफ़ॉल्ट **नहीं** है, व्यावहारिक कारण से: `publish one-file.yaml` बाकी अड़तालीस को सिर्फ़ इसलिए नहीं हटा सकता कि कमांड लाइन पर उनका नाम नहीं था।
