Core areteacademy/brevis

Um arquivo YAML, um pod por etapa.

O workflow inteiro é um arquivo versionável: revisar um pipeline vira revisar um diff. O Core agenda, enfileira e sobe cada etapa com a própria imagem — e nunca toca o dado.

hello.yaml
name: hello
type: dag
tags: [example]

steps:
  - id: prepare
    run: sh -c 'echo preparing; sleep 1'

  # The next two depend on the same step, so they run IN PARALLEL.
  - id: extract
    run: sh -c 'sleep 2; echo 42 extracted'
    depends_on: [prepare]

  - id: validate
    run: sh -c 'sleep 1; echo validated'
    depends_on: [prepare]

  - id: publish
    run: echo published
    depends_on: [extract, validate]
shell
$ docker run --rm -v ./hello.yaml:/w/hello.yaml -w /w \
  areteacademy/brevis:0.17.1-worker run hello.yaml
workflow hello (dag, 4 steps) in .
  ▶ prepare
    prepare | preparing
  ✓ prepare
  ▶ validate
  ▶ extract
    validate | validated
  ✓ validate
    extract | 42 extracted
  ✓ extract
  ▶ publish
    publish | published
  ✓ publish

workflow hello finished

A saída real, com a imagem publicada. brevis run executa local, sem fila; quem sobe pods é o scheduler.

SDK brevis/sdk

Um fetcher inteiro em três chamadas.

Extract lê, Transform reformata, Load escreve. Cada um recebe e devolve uma sequência — nada é materializado em memória de uma vez.

shell
$ go get github.com/AreteAcademy/brevis/sdk@latest
main.go
rows, err := sdk.Extract(ctx, sdk.Source{
	From: from.HTTP{URL: "https://api.example.com/v1/events"},
})

rows = sdk.Transform(rows, sdk.Accept("id", "created_at", "amount"))

res, err := sdk.Load(ctx, rows, sdk.Target{
	To:      bigquery.Table{Dataset: "bronze", Name: "events"},
	Columns: []string{"id", "created_at", "amount"},
})

Requer Go 1.23 ou mais novo.

Gateway areteacademy/brevis-gateway

Um endpoint que pousa o dado que chega.

O cliente faz POST e recebe 202 na hora; o lote vai para o destino depois, num worker. Sem banco próprio, e configurado inteiro em YAML.

gateway.yaml
name: events_gateway

listen:
  addr: :8080
  auth:
    type: bearer
    keys_from: BREVIS_INGEST_KEYS

streams:
  - name: clicks
    path: /v1/clicks
    format: json
    identity:
      provider: web
      entity: click
      source_key: event_id
      record_ts: occurred_at
    sink:
      type: files
      path: /var/landed/
    dead_letter:
      type: files
      path: /var/landed/dead-letter/
shell
$ docker run -p 8080:8080 -e BREVIS_INGEST_KEYS=dev-key \
  -v ./gateway.yaml:/etc/brevis/gateway.yaml:ro -v ./landed:/var/landed \
  areteacademy/brevis-gateway:0.26.1-slim

$ curl -X POST localhost:8080/v1/clicks -H 'Authorization: Bearer dev-key' \
  -d '{"event_id":"e-1","occurred_at":"2026-10-08T12:00:00Z","page":"/pricing"}'
{"accepted":1,"rejected":null}  202

A resposta real, com a imagem publicada. Sem a chave, 401.

SQL areteacademy/brevis-sql novo · 0.1

Arquivos .sql comuns, construídos na ordem certa.

Sem template: um modelo é um arquivo que continua SQL válido, e a ordem vem da leitura do próprio SQL. Postgres e BigQuery, com a mesma suíte de conformidade.

models/staging/stg_orders.sql
/* brevis
materialized: view
*/
select order_id, customer_id, amount, ordered_at
from raw.orders
where amount is not null
models/marts/orders.sql
/* brevis
materialized: table
tests:
  - not_null: [customer_id]
  - unique: [customer_id]
*/
select customer_id, count(*) as orders, sum(amount) as revenue
from staging.stg_orders
group by customer_id
shell
$ docker run --rm -v ./project:/project:ro areteacademy/brevis-sql:0.1.0 \
  compile --project /project
2 models, 2 to build, 0 function(s)
  staging.stg_orders                 view  0 test(s)
  marts.orders                       table 2 test(s)

$ docker run --rm -v ./project:/project:ro areteacademy/brevis-sql:0.1.0 \
  graph --project /project
staging.stg_orders
  └─ raw.orders (source)
marts.orders
  ├─ staging.stg_orders

a mesma linha

Busque ou receba: a linha é a mesma.

Um pedido que o SDK busca e um pedido que chega ao Gateway pousam na mesma tabela, com o mesmo brevis_ingestion_id. Escolher entre os dois vira decisão de deploy, não de schema.

pelo SDKmain.go
sdk.Execute(ctx, &sdk.Pipeline{
	Source:    sdk.Source{From: from.Files{Path: "order.json"}},
	Transform: []sdk.Transformer{sdk.Landing("app_orders", sdk.LandingKey("id"))},
	Target: sdk.Target{
		To:     postgres.Table{DSN: dsn, Name: "app_orders"},
		Schema: sdk.LandingSchema(sdk.LandingOptions{}),
	},
}, nil)
pelo Gatewayshell

como executa

Um pod por passo. Cada um com a sua imagem.

O core lê o workflow e sobe um pod por passo. Extrair em Go, preparar em Python, transformar em dbt — cada passo com a imagem, os limites e o runtime que ele declarou. Nenhum passo herda o peso do vizinho.

01

O trabalho traz o runtime

Um passo é uma imagem e um comando. Trocar a versão do dbt é uma linha no YAML daquele workflow, não um rebuild de tudo.

02

Contexto entre passos

Um passo publica uma marca d'água ou um caminho; o seguinte lê. Duas variáveis de ambiente, sem API e sem porta.

03

Falha com limite

Um passo que vaza memória morre sozinho. Sem worker genérico, não há vizinho para derrubar.

o console

O que está rodando, e o que vai rodar.

A interface vem no binário — não é um serviço à parte para instalar e manter. Taxa de sucesso, duração média, a fila, o histórico de tentativas e a agenda das próximas execuções.

localhost:8080
  • Visão geral com métricas e gráficos
  • Lista de workflows com busca, filtros, pausa e disparo
  • Histórico de execuções, com a tentativa de cada uma
  • A DAG de um run ao vivo, e os auto params que o engine calculou para ele
  • Projetos, para dois times não colidirem no mesmo nome
  • Fontes e bundles servidos do binário — funciona sem internet

Kubernetes + Helm

O chart do repositório: migrações como hook, uma imagem por papel e RBAC mínimo para os pods de etapa.

$ helm install brevis ./deployments/helm/brevis \
    --namespace data --create-namespace \
    --set database.url="postgres://…" \
    --set auth.user=admin \
    --set auth.passwordHash="$(brevis hash)" \
    --set auth.secret="$(openssl rand -base64 48)"

de brevitate vitae

Não é que temos pouco tempo. É que perdemos muito dele.

A máxima de Sêneca guia a pergunta por trás do brevis.sh: quais complexidades realmente merecem o tempo de uma equipe? Cada workflow executa em pods isolados para que falhas, versões e dependências tenham limites claros.

01

imagem por etapa

Cada passo declara o runtime de que precisa. Trocar a versão de um não obriga a mexer nos outros.

02

logs por execução

A saída pertence ao run que a produziu. Investigar uma falha não é reconstruir um contexto perdido.

03

retries persistentes

A tentativa sobrevive ao processo. Uma reinicialização não apaga o que já se sabia sobre o trabalho.

04

isolamento de dependências

O que uma etapa carrega não vaza para as vizinhas. Limite claro é o que torna a falha legível.

O brevis.sh é realmente 100% open source?
