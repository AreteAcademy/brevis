ドキュメント

Workflows

YAML 形式の全体 — ステップ、依存関係、イメージ、リソース、スケジュール。

ワークフローは YAML ファイルです。何を実行するか、どの順序で、 どのランタイムでを宣言し、それ以外は何も宣言しません。

最小構成#

yaml
name: hello
steps:
  - id: only
    run: echo done

name は、データベースとインターフェースの中でワークフローを識別します。steps は ステップのリストで、各ステップは一意の id と run を持ちます。

description — 何のためのものか#

任意で、自由形式です。エンジンのどの部分からも読まれません。

yaml
name: daily-orders
description: >
  Pulls yesterday's orders from the vendor and lands them in bronze.
  Runs at 04:00 because the vendor closes its books at 03:30.
steps:
  - id: extract
    run: python fetch.py

ワークフローの画面の先頭、件数とスケジュールの上に表示されます。グラフはフローが 何をするかをすでに示しています。これは、それが何のために存在するかを示す唯一の場所で、 午前 3 時に初めてそのワークフローを開く人が本当に必要としているものです。

説明のないワークフローには、そこに何も表示されません。空のブロックは表示しません。 読み込みに失敗したように見えるからです。

順序: chain か dag か#

yaml
type: chain   # order is the file's order
type: dag     # order comes from depends_on

chain は糖衣構文です。パーサがその並びをエッジに変換し、エンジンが知っているのは DAG だけです。順序が直線的でない場合は dag を使います。

yaml
type: dag

steps:
  - id: prepare
    run: ./prepare.sh

  # Siblings: they depend on the same step, so they run in parallel.
  - id: extract
    run: ./extract.sh
    depends_on: [prepare]

  - id: validate
    run: ./validate.sh
    depends_on: [prepare]

  - id: publish
    run: ./publish.sh
    depends_on: [extract, validate]

ランナーはグラフをレベルごとに進みます。同じレベルのものはすべて並列に実行され、 次のレベルは前のレベルが完全に終わってから始まります。

失敗するとレベル全体が止まります

ランナーは、レベル内で最初の失敗が起きた時点で止まり、次のレベルを開始しません。 エラーの後で続行すると、完全に見えるのに実は部分的な結果が出てしまうからです。

スケジュール#

yaml
schedule: "0 5 * * *"   # five-field cron
concurrency: 1

schedule がなければ、そのワークフローは手動です。インターフェースからのトリガー、 brevis run、backfill によってのみ実行されます。

concurrency: 1 は、同じワークフローの同時実行数を制限します。1 回の run が 15 分を 超えたときに、*/15 のワークフローが自分自身と重なるのを防ぎます。

同じテーブルに書き込む異なる 2 つのワークフローには、グループが必要です。同じ dbt モデルを ビルドする日次のワークフローと */15 のワークフローは、それぞれ次のように宣言します。

yaml
concurrency:
  group: jaffle_models   # the shared resource, named the same in both files
  limit: 1               # optional; a group without one means 1

グループ内のすべてのワークフローの run は、起動のきっかけ(スケジュール、landing、backfill、 クリックのどれか)にかかわらず、1 つの上限に対してカウントされます。グループが満杯のときに 到着した run はキューで待機します。スキップも失敗もしません。同じテーブルに書き込む 3 つ目のワークフローも、グループ名を指定すれば参加できます。待機中は、その run のページに、 どのグループか、その上限、どの run がスロットを占有しているかが表示されます。

  • すべてのメンバーが同じ上限を宣言します。validate と publish は、あるファイルで 1、 別のファイルで 3 と宣言されたグループを、すでに公開済みのメンバーとの比較も含めて拒否します。
  • グループが直列化するのは Brevis の run です。誰かが自分のマシンで起動した dbt run はこのキューに 含まれず、同じように失敗します。

イメージとリソース#

yaml
image: us-central1-docker.pkg.dev/example/apps/dbt:1.10.3
resources:
  cpu: 200m
  memory: 1Gi
  limits: {memory: 2Gi}

トップレベルで宣言したものは、すべてのステップのデフォルトになります。各ステップは 自分の分を上書きできます。

yaml
steps:
  - id: bronze
    run: dbt build --select bronze+          # inherits the top-level image

  - id: notify
    image: ghcr.io/example/notify:0.3        # another runtime
    shell: false                             # distroless has no shell
    run: /notify --channel data
    resources: {cpu: 25m, memory: 32Mi, limits: {memory: 64Mi}}
    depends_on: [bronze]

これにより、Go 製のフェッチャーは、1.9 GB の dbt build の隣で 12 MB と 32Mi で済みます。 両者が大きいほうのサイズを負担することはありません。詳しくは ステップごとの pod を参照してください。

ステップのフィールド#

フィールド
id必須ワークフロー内で一意。グラフとログに表示される名前
runコマンド
imageステップのイメージ。省略するとトップレベルのものを継承します
hostエンジンが管理しないマシンにコマンドを送ります。image の代替であり、併用はしません。Kubernetes ガイドの host:を参照
shelltruefalse にするとシェルなしで実行します。distroless では必須です
depends_on先に終わっている必要がある id のリスト。要素は {step, label} でも構いません
markerfalseコマンドを持たないステップ。start や end 用です
resourcesそのステップの cpu、memory、limits
runtime, toolsステップの言語とツール — ステップのランタイムを参照
whenall_success依存先がどの状態のときにこのステップを実行するか — 後述
unless_emptyやるべきことがあるかどうかを決めるコンテキストのキー — 後述
for_eachリストを保持するコンテキストのキー。ステップは要素ごとに 1 回実行されます — 後述
groupこのステップを、名前付きで折りたためるボックスの中に描画します — 後述

on_errorこのステップの失敗を通知します — 後述

やるべきことがあるときだけステップを実行する#

python
# in extract
context.set(has_rows=len(rows) > 0)
yaml
  - id: transform
    run: ./transform.sh
    depends_on: [extract]
    unless_empty: extract.has_rows

unless_empty が指定するのは式ではなくキーです。ステップが判断して答えを公開し、 エンジンは 1 つのキーを読んで、それが空かどうかを問い合わせます。

空とみなされるもの存在するとみなされるもの
false、0、""、null、[]、{}それ以外のすべて

文字列の "false" は存在するとみなされます。その 5 文字を公開したステップは 何かを公開したのであり、それが真偽値を意味すると推測することは、ルールが作者に見えない 意見を持ち始める原因になります。本物の真偽値を公開してください。

なぜ式ではないのか#

魅力的な設計は when: "{{ context.extract.rows > 0 }}" です。しかし、小さな式言語は 大きな負担を伴います。パーサ、JSON の any に対して > が何を意味するかを定める型システム、 他の人が書いた YAML から式が出てくることによるセキュリティ上の問題、そして文字列の 内部を指すエラーメッセージです。式言語を持つオーケストレータは、どれもそれに関する バグトラッカーを抱えています。

ここでは、判断は作者がすでに書いている言語の中にあり、自分のテストフレームワークから 手が届きます。

キーがないのは空の値ではなく失敗#

キーがない場合、ステップは失敗し、メッセージには、公開側が実際に書いたものとともに そのキーの名前が出力されます。

step "transform" reads `extract.has_row`, and "extract" published "has_rows" but not "has_row"

代案として、存在しないキーを「空なのでスキップ」と読むと、タイプミスが、黙って永遠に 実行されなくなるステップに変わり、その理由を示すものはどこにもありません。これはこの機能にとって 最悪の結果です。

キーは常に、それを公開するステップで修飾され、そのステップはこのステップが依存しているものでなければ なりません。どちらも publish の時点で拒否されます。決して見えないキーで制御されたステップは 永遠にスキップされ、夜間ジョブが動かなくなったときにそれに気づくのでは遅すぎるからです。

要素ごとにステップを 1 回実行する#

python
# in extract
context.set(partitions=["2026-01", "2026-02", "2026-03"])
yaml
  - id: load
    run: ./load.sh "$BREVIS_MAP_VALUE"
    depends_on: [extract]
    for_each: extract.partitions

ステップは要素ごとに 1 回実行され、それぞれが自分の行、リトライ、終了コードを持ちます。 グラフには 3 つのノードではなく、[3] が付いた 1 つのノードが表示されます。

変数
BREVIS_MAP_INDEX0、1、2 …
BREVIS_MAP_VALUEその要素

JSON の文字列は引用符なしで渡されるため、["2026-01"] に対する for_each は シェルに "2026-01" ではなく 2026-01 を渡します。それ以外のもの(数値、オブジェクト、 リスト)は JSON のまま渡されます。

どちらの変数も、マップされていないステップには存在しません。常に存在して常に空の変数は、 環境変数を読む人にそれを無視するよう教えてしまうからです。

DAG の形は変わらない#

マップされたステップは、依然として 1 つのエッジの集合を持つ 1 つのノードです。変わるのは、 その下にある行の数だけです。したがってレイアウトはこれまでどおりで、[3] は読み取り時に それらの行から数えられます。何も保存されないので、同期を保つ必要もなく、誤った件数が 修正されたクエリより長く残ることもありません。

インスタンスがまだ実行中のあいだ、カードには [2/3] と表示されます。

1 つのインスタンスの失敗でステップが失敗する#

3 つのパーティションをロードして 1 つが失敗したなら、そのステップは仕事を果たしていませんし、 その下のステップはそれを知ることになります。大半がうまくいったからといって緑になるノードは、 嘘をつくバッジです。

リトライでやり直されるのは、失敗したインスタンスだけです。 成功した 18 のパーティションが、 2 つが壊れたからといって再ロードされることはありません。

空のリストは成功ではなく skipped#

やるべきことがなかったために何もしなかったステップは、それをやり遂げたわけではありません。 インスタンスがゼロなのに緑のノードというのは、まさに誰かがダッシュボードを作ってしまう類のものです。

リストではない値は失敗し、キーが存在しない場合も同様です。unless_empty: と同じ方針で、 理由も同じです。タイプミスが黙ってインスタンスをゼロにすると、ステップが永遠に無効になってしまうからです。

ファンアウトには上限があり、その上限は継承されたもの#

リストはコンテキストに載って運ばれ、コンテキストには kubelet に由来する 4096 バイトの 上限があります。ワークフローは、それを 4 キロバイトで表現する方法を見つけない限り、 1 万個の pod を要求できません。これは、回避するのではなく維持する価値のある制限です。

マップされたステップが公開するもの#

その出力は各インスタンスの行に記録され、下流のステップからは見えません。1 つのステップ名の もとで 4 つのインスタンスが公開すると、1 つのキーに 4 つの値があることになり、 context.String("load.bucket") に対する答えは推測以外にありません。ステップはそれを 黙って捨てるのではなく、ログで知らせます。

グラフ上でステップをグループ化する#

yaml
steps:
  - id: extract_orders
    group: sales_data_reporting
    run: ./extract.sh
  - id: load_orders
    group: sales_data_reporting
    depends_on: [extract_orders]
    run: ./load.sh

ステップは、名前の付いた折りたためるボックスの中に描画されます。DAG が大きくなって 読めなくなったときのための、Airflow の TaskGroup に相当するものです。

見た目だけです。 Airflow の TaskGroup は中の id に*プレフィックスも付ける*ため、 extract は sales.extract になります。ここではそうしません。プレフィックスを付けると、既存の ワークフローのすべての depends_on、コンテキストのキー、記録済みの行が変わってしまいます。 しかもこの機能の価値は、大きなグラフが読みやすくなる点にすべてがあります。名前空間は後から 追加できます。それはこの機能への厳密な追加になります。

グループはコンテナではなくラベルです。ステップはグローバルな id を保ち、グループは 複数のレベルにまたがることができ、実行については何も変わりません。

グループ名をクリックすると折りたたまれます。そのステップは消え、境界をまたいでいた矢印は ボックスを指すようになります。

別のワークフローを再利用する#

yaml
# nightly.yaml
steps:
  - id: prepare
    run: ./prepare.sh

  - id: mlops
    uses: ml_training       # another workflow in the same publish
    depends_on: [prepare]

  - id: report
    run: ./report.sh
    depends_on: [mlops]

publish の時点で、ml_training のステップがそのステップの代わりに入り、その id が プレフィックスとして付き、uses のノードは消えます。

prepare → mlops.train → mlops.evaluate → report

それらは折りたためる 1 つのグループとして届くので、グラフにはファイルに書かれたとおりのものが 表示されます。

publish 時に展開され、実行時に走るわけではありません。 子の*run* をトリガーして待つステップは、 Airflow をデッドロックさせた設計であり、このエンジンにも同じ要素があります。pod の上限は プロセスごとのセマフォなので、親がスロットを保持したまま、同じプールのスロットを必要とする 子を待つとハングします。しかもそれは負荷がかかったときだけ、つまり本番で起きます。run は 1 つ、 グラフは 1 つ、プールは 1 つです。

代償として、独自の id と独自の履歴を持つ子の run は得られません。

ルール#

子は同じ publish に含まれている必要があるすでに公開済みというだけでは不十分
矢印そのステップへの矢印は子の各ルートへの矢印になり、そのステップからの矢印は子の各リーフからの矢印になる
子の image、env、secrets、resources各ステップに具体化されるため、自分のファイルに書かれたもので実行される
子の unless_empty / for_each のキープレフィックスとともに移る
ネスト深さ優先でフラット化される
循環publish で拒否され、連鎖が示される

「すでに公開済み」ではなく「同じ publish」であることが重要です。 データベースを読む展開を 行うと、意図的にデータベースに触れない brevis validate が brevis publish とは別の問いに 答えることになり、CI を通ったファイルがデプロイで失敗するファイルになってしまいます。

子は単独でも publish できます。展開はコピーであり、消費ではありません。ステップが uses: と、run:、action:、marker: のいずれかを同時に宣言することはできません。それは ファイルが 2 つのことを言っているからです。

矢印の意味を伝える#

依存関係にはラベルを付けられ、グラフの矢印に表示されます。

yaml
steps:
  - id: determine_load_type
    run: ./decide.sh

  - id: load_full
    run: ./full.sh
    depends_on:
      - {step: determine_load_type, label: additional data}

  - id: load_delta
    run: ./delta.sh
    depends_on:
      - step: determine_load_type
        label: changed existing data

素の書き方である depends_on: [extract] も引き続き使え、通常の形のままです。ほとんどの 依存関係には言うべきことがなく、すべての矢印にラベルがあるとノイズになります。

ラベルが役に立つのは分岐です。同じステップから出る 2 本の矢印に何も書かれていない図は、 読むのにソースを開く必要があります。グラフはそれを避けるために存在するはずです。

何もしないステップ#

yaml
steps:
  - id: start
    marker: true

  - id: end
    marker: true
    depends_on: [load_full, load_delta, report]

marker: true はコマンドを持たないステップです。何も実行せず、即座に成功し、 グラフ上に表示されます。

飾りではありません。すべての分岐に依存する end があれば、全体が終わったか? という問いが、 6 本の矢印をたどる代わりに 1 つのノードで答えられます。しかも他のステップと同じように振る舞うので、 失敗した分岐の下にある end は緑ではなくスキップされます。

run: も marker: true もないステップは、引き続き拒否されます。 この 2 つのケースを 1 つにまとめてはなりません。空のコマンドはほとんどの場合ミスであり、marker: true は 意図したものだと表明する方法だからです。run: も宣言しているマーカーも同様に拒否されます。 それはファイルが 2 つのことを言っているからです。

何かが失敗したときだけステップを実行する#

デフォルトでは、ステップは、それより前のすべてが成功したときに実行されます。when: はこれを変更します。

yaml
steps:
  - id: extract
    run: python fetch.py

  - id: notify_failure
    run: ./notify.sh
    depends_on: [extract]
    when: any_failed          # runs precisely when extract did not make it

  - id: cleanup
    run: ./cleanup.sh
    depends_on: [extract, transform]
    when: all_done            # runs either way
ルール
all_successデフォルト。このステップが依存するものがすべて成功した — Airflow と同様に、そのステップ自身の依存関係が対象
any_failedこのステップが依存するステップのうち、少なくとも 1 つが失敗した
all_doneこのステップが依存するものがすべて、どのような終わり方であれ終了した

未知のルールは publish で拒否され、有効なものが示されます。そうする必要があります。 when: on_failure が「デフォルト」として読まれると成功時に実行されてしまい、書いてあることと 正反対のことが、重要な夜に初めて発覚するからです。

実行されないステップは skipped#

これは独自の状態であり、独自の色で描画され、理由が付きます。extract が failed だった、という ものです。これ以前は、失敗の下にあるステップには記録がまったくなく、画面ではいつまでも pending のままに見えていました。

skipped は失敗でも成功でもありません。上流が壊れたステップは失敗したのではなく、 機会を与えられなかっただけです。それを成功と呼ぶのは、run 自身のステータスにまで及ぶ嘘になります。

トリガールールが決めるのは、どのステップが実行されるかです。run の結果を決めるものではありません。 メッセージを届けた notify_failure があっても、パイプラインがうまくいったことにはならず、 その run は失敗のままです。

all_success は Airflow と同様にローカル#

このルールが問うのは、ステップ自身の依存関係だけです。無関係な分岐の失敗は、 このステップを止めません。

extract_orders ──✕                 (failed)
extract_users  ──✓── transform_users ──✓     keeps going

失敗の下流にある分岐は、やはり止まります。all_success がローカルであることは、 下流への影響がないという意味ではありません。

このエンジンはかつて、最初の失敗でグラフ全体を中止していました。それには理由がありました。 エラーの後で続行すると、完全に見える部分的な結果が生まれ、あるパイプラインは誰にも気づかれずに 28 日遅れで動いていたのです。

その保護に代わるものは、決して無ではありません。

  • run は同じエラーで引き続き失敗します。
  • グラフは失敗したステップを赤で、スキップされたステップをそれぞれ独自の色で表示し、 それぞれがどのステップに止められたかを示します。
  • run が諦めたときには、アラートが引き続き送信されます。

run が完全でないと自ら言うので、部分的な結果が完全に見えることはなくなります。

手放すものを率直に言えば、別の場所で失敗した run でも、無関係な分岐がデータを書き込むように なったことです。

リトライは失敗したものだけをやり直す#

run のリトライはグラフ全体をやり直しません。同じ run の以前の試行ですでに成功したステップは、 結果を保持し、再実行されません。Airflow でクリアした DAG run の動作と同じです。

attempt 1   extract ✓    load ✕    report (skipped)
attempt 2   extract –    load ✓    report ✓            extract is not re-run

そのステップは元の行を保持します。所要時間、ログ、公開したものは最初の試行のものです。 仕事が行われたのはそのときだからです。その下のステップは、公開されたものを引き続き読み取ります。 run のコンテキストは再構築されるのではなく、保存されているからです。

重要な区別があります。これはこの run の以前の試行についての話です。昨日の run で 成功したステップは、今日も通常どおり実行されます。(もう一方の問いも存在し、それが SDK にステップの初回かどうかを伝えます — BREVIS_RUN_FIRST を参照してください。)

スキップされたステップは確定していません。一度も実行されておらず、リトライは新しい試行の 結果をもとに、あらためてそれを判断します。

ステップの失敗を通知する#

すべての失敗はすでに通知されます。Webhook を設定していれば、諦めた run は 1 通のメッセージを 送り、どのファイルにもブロックを繰り返す必要はありません。on_error は、自分専用の通知が 必要なステップのためのものです。

yaml
steps:
  - id: fetch_observations
    run: python fetch.py
    on_error:
      type: SLACK
フィールド
type必須SLACK。未知の値は publish で拒否され、有効なものが示されます
whengive_upattempt は最後の試行だけでなく、失敗したすべての試行を通知します

メッセージが 1 通ではなく 2 通届きますが、それが狙いです。run レベルのアラートは *id_verification が失敗した*と伝え、それはパイプラインの担当者が必要とするものです。 ステップレベルのアラートは*fetch_observations が失敗した*と伝え、それはそのインテグレーションの 担当者が必要とするものです。

webhook や url のフィールドはなく、今後も追加されません。 宛先は認証情報です。それを 持つ人は、プラットフォームであるかのようにチャンネルへ投稿できます。そしてワークフローファイルを 書く人は、会社のアラートの送り先を選ぶ権限があるとは限りません。ファイルが決めるのはするかどうかと どのようにであり、どこへはインストール側が BREVIS_SLACK_WEBHOOK で決めます。

when: give_up がデフォルトなのは、誰の夜かを考えてのことです。 2 回失敗して 3 回目に通る ステップは、もう一方のデフォルトでは 2 通のメッセージを送り、2 通目は問題が解消した後に届きます。

失敗しなかったステップが通知されることはありません。 ある分岐が壊れたワークフローで、 別の分岐の担当者が起こされることはありません。

配信は brevis alert の仕事です。アラートは失敗と同じトランザクションで記録されるため、 Slack が止まっても失われず、遅れるだけです。

タグ#

yaml
tags: [analytics, dbt, daily]

インターフェースでの絞り込みに使われます。実行には影響しません。

検証#

検証にデータベースは要らないため、テストと並べて CI で実行できます。

bash
brevis validate workflows/
  ok    daily_analytics              dag  5 steps, 5 dependencias  (manual)
  ok    daily-report                 chain  3 steps, 2 dependencias  cron 0 2 * * *

ファイルまたはディレクトリを受け取ります。ディレクトリでは *.y*ml に一致するものをソートします。 2 回の実行で同じログになるので、2 回のデプロイの差分がノイズになることはありません。

公開#

bash
brevis publish workflows/
brevis publish workflows/ --project acme --prune

--prune は、公開リストにないワークフローをプロジェクトから削除し、その履歴は保持します。 実用上の理由から、これはデフォルトではありません。publish one-file.yaml が、 コマンドラインで名前を挙げなかっただけで、他の 48 個を削除してはならないからです。
