スケジューラとキュー

2 つの独立したループ — 誰が run を作り、誰が実行するのか、そしてなぜ分かれているのか。

brevis.sh は、run の作成と実行を分離しています。2 つのループが一緒に動きますが、 互いに依存しません。

scheduler                          queue
─────────                          ─────
reads the schedule
materialises the slot
creates the Run  ─────────────►  (pending in the database)
                                   claims it
                                   walks the graph
                                   executes each step
                                   records state and log

なぜ分けるのか#

スケジュールと実行の両方を行う 1 つのループには、困った性質があります。実行が詰まると、 スケジューリングも一緒に止まります。その後 12 時間分の slot はそもそも存在せず、 届かなかったデータを誰かが探すまで、誰も気づきません。

2 つを分けると、次のようになります。

  • スケジューラが止まっても、キューは作成済みのものを消化し続けます。
  • キューが止まっても、slot は具体化され続け、キューが戻ったときに実行されます。
  • 再処理は時計に依存しません — backfill は、cron が使うのと同じ経路で過去の run を作成します。

プロセス#

両方のループは同じコマンドの中にあります。

bash
brevis scheduler --interval 5s --concurrency 4 --max-pods 10
フラグデフォルト
--interval10sスケジューラのサイクルの間隔
--concurrency5同時に実行される run の数
--max-pods5同時に実行されるステップの合計数

--concurrency と --max-pods は意図的に別のものを数えます。上限が run にしかなければ、 並列ステップが 3 つずつある 5 つの run で、15 個の pod になってしまいます。

`serve` はスケジュールを具体化しません

API プロセスも同じスケジューラを起動しますが、ループなしです。インターフェースからの 手動トリガーに応えるためだけにあり、「スケジューラが run を作る」というルールの持ち主が 1 つに保たれます。スケジュールを発火させるには、brevis scheduler を並行して動かす必要があります。

定義のスナップショット#

スケジューラが run を作成するとき、ワークフローの定義を run の中に保存します。 実行はディスク上の YAML ではなく、このスナップショットを読みます。

理由は具体的です。トリガーから実行までの間に、誰かがファイルを編集してデプロイしているかもしれません。 スナップショットがなければ、05:00 にある定義で作成された run が 05:02 に別の定義で実行されることになり、 ログにはその違いを説明する手段がありません。

リトライ#

失敗した run は3 回試行され、遅延は倍々になります。デフォルトでは 0 秒、30 秒、1 分 30 秒に実行されます。

bash
brevis scheduler --max-attempts 3 --retry-backoff 30s --retry-backoff-max 1h
フラグデフォルト
--max-attempts3run あたりの試行回数(最初の試行を含む)
--retry-backoff30s最初の遅延。それ以降は試行のたびに倍になります
--retry-backoff-max1hその遅延の上限

プロセスは起動時にそのスケジュールを出力するので、2 つの数値から計算する必要はありません。

scheduler and dispatcher are up  max_attempts=3 retry_backoff=30s retry_at="0s, 30s, 1m30s"

ヒント

レート制限のあるベンダーには、もっと長い間隔が必要です。 これらのパイプラインが失敗する理由は、 何よりも一つに集約されます。一時的な上流の問題です。200 を返しながら「リクエスト上限に達しました」と 言う API や、ウェアハウスのクォータの一時的な乱れなどです。これが解消するには 1 分ほどかかり、 それより早く終わるリトライは、実質的に行われなかったリトライと同じです。 --retry-backoff 1m にすると、試行は 0 秒、1 分、3 分に配置されます。

リトライは run 単位で行われ、失敗したステップだけが再実行されます。失敗した dbt_build のために、 その上流で成功したフェッチが再実行されることはありません。

試行回数は永続化されており、プロセスの状態ではありません。ワーカーを再起動しても、 その run についてすでにわかっていたことは消えません。

run の試行番号は pod 名に入ります。これがないと、リトライは run を最初からやり直し、 同じ名前の前の試行の pod にぶつかって、Pending のまま永久にハングします。

Backfill#

公開済みのワークフローの過去の slot を具体化します。

bash
brevis backfill daily --from 2026-01-01 --to 2026-01-31
brevis backfill daily --from 2026-01-01 --to 2026-01-31 --param load_full=true
  31 backfill run(s) queued for daily (2026-01-01 to 2026-01-31)
  run `brevis scheduler` to execute them

キューに追加するだけで、実行はしません。 実行は scheduler の仕事です。ここでも同じ分離です。 --to はその日全体を含みます。

landing による起動#

ワークフローは、時計が示したからではなく、データが届いたから実行することができます。

yaml
trigger:
  on_landed:
    - bigquery://acme-prod/bronze/orders
    - bigquery://acme-prod/bronze/*
  debounce: 5m

すべてのステップは、フェーズを運ぶパイプ上で、自分が何を書いたかをすでに宣言しています。 それが /data を埋めるものです。ワークフローはそれらの名前のいずれかを購読し、 そこに何かが着地したときに起動します。

末尾の /* はデータセット全体を購読します。これは、ルートごとにテーブルを作る auto_table のために あります。誰も宣言していないテーブルに名前を付けられるのは、データセットだけだからです。 bronze/orders には一致しますが、bronze_raw/orders には一致しません。

ウィンドウと、10 件の landing が 1 つの run になる理由#

debounce は、短時間に集中した landing をまとめます。5 分以内に 10 個のテーブルが着地しても、 起動する run は 10 個ではなく1 つで、その run がどのテーブルかを伝えます。

BREVIS_AUTO_LANDED=bigquery://acme-prod/bronze/orders,bigquery://acme-prod/bronze/items

正確なリストは JSON として BREVIS_AUTO_PARAMS にも入っています。ターゲットにカンマが含まれうる場合は、 こちらを読んでください。

ウィンドウは、ステップが発生したと申告した時刻ではなく、エンジンが landing を記録した時刻から 区切られます。クエリが始まった瞬間を報告するステップは、正しいけれども古いことを報告しており、 時計が 1 つずれているだけで、集中した landing が 2 つの run に分割されかねません。

debounce を省略すると、すべての landing が run を起動します。

やらないこと#

ワークフローが自分自身の書き込みで起動されることは決してありません。 エンジンは、書き込み元が 購読しているワークフロー自身である landing を捨て、その理由をログに残します。これがなければ、 同じテーブルを読み書きするワークフローは、永久に自分自身をトリガーしてしまいます。

これは、ファイルが検査されるときではなく発火するときに拒否されます。これは見落としではなく 制限です。brevis validate はファイルを読むだけで、ステップが何を書くかを宣言するファイルは ありません。ウェアハウスのターゲットは YAML ではなく接続によって決まります。そのため validate は、 実行時に必ず拒否されるワークフローを通してしまい、その理由はログに残ります。

最初のサイクルでは何も起動しません。 トリガーは、スケジュールと同様、有効になった時点から カウントを始めます。そうでなければ、トリガーを publish した途端に、カタログの履歴にあるすべての landing に対して run が発火してしまいます。

アラート#

bash
export BREVIS_SLACK_WEBHOOK='https://hooks.slack.com/services/...'
export BREVIS_UI_URL='https://brevis.example.com'

Webhook がなければ、プロセスは起動時に、失敗が報告されないという警告を出します。黙って失敗する インストールは、チームではなく顧客に発見されがちです。

BREVIS_UI_URL はアラート内の run へのリンクを作ります。これがないと、アラートは何が失敗したかは 伝えますが、読み手が run を手作業で探すことになります。
