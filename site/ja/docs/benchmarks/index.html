ベンチマーク

gateway の測り方、数字が示すこと、そして一致していなければならない 3 つの証人。

1 つのコマンドで gateway 全体を計測します。

bash
BREVIS_BENCH_IMAGE=areteacademy/brevis-gateway:0.11.0 ./bench/run.sh

Postgres を起動し、gateway を起動し、[k6] で負荷をかけ、バッファが空になるのを待ち、gateway 自身の /metrics を取得して、bench/results/REPORT.md を書き出します。

3 つの証人、そして重要なのは 3 つ目#

k6 が知っているのは、プロデューサーが見たものです。gateway が知っているのは、自分がしたことです。 前者だけを持つ負荷テストでは、高速な gateway と、202 を返しながら受け付けたものを捨てている gateway を 区別できません。

そこでレポートは 2 つを並べ、さらに Postgres の行数を数えます。

証人イベント数
k6 が accepted と告げられた5,431,000
gateway が受信としてカウントした5,431,000
Postgres の行数5,431,000
dead letter のレコード数0

最初の 2 つはどちらも gateway 自身の算術です。1 つは書いたレスポンスから、もう 1 つは加算したカウンタから 来ており、イベントを失うバグがあっても、両者の間では整合を保てます。データベースだけが、 こちらの言い分を鵜呑みにしませんでした。

3 つが一致しない run は、パーセンタイルがどれだけ良くても失敗です。

上記の run#

bench/results/REPORT.md にある 2026-09-26 の run です。 areteacademy/brevis-gateway:0.11.0、Darwin arm64、11 CPU、同じカーネル上のコンテナ内の Postgres 17、 write: append の auto_table[columns]:

受け付けたイベント5,431,000(135,768/s)
送信したボディ40 秒で 1,156.7 MiB
503(バックプレッシャー)0
p50 / p95 / p995.9 ms / 16.0 ms / 22.7 ms
配信したバッチ1,087、葬られたものなし

しきい値こそが要点#

k6 はしきい値のどれかが破られるとゼロ以外で終了するので、これはグラフではなくゲートです。

しきい値理由
p95 < 500ms受け付けの経路は sink のレイテンシから離れていなければならない。COPY を待つリクエストは、非同期パイプが防ぐために存在する欠陥です。
http_req_failed < 1%503 は問題ない。タイムアウトや 5xx は問題。
events accepted > 1000しきい値のスイートは、何も応答しなかった gateway に対しても通ってしまう。

意図的に緩く設定されています。CI が割り当てたどんなマシンでも動くからです。検出するのは、パーセントではなく、 リグレッションの姿である桁違いの変化です。

503 は失敗ではありません。 置き場のないイベントを gateway が拒否したもので、リトライしても安全です。 ingestion_id はイベントの固定された関数なので、同じボディを再送すれば同じレコードだからです。 これをエラーとして数えると、バックプレッシャーがバグに見えてしまいます。

測らないもの#

  • BigQuery ではありません。 宛先はコンテナ内の Postgres です。ウェアハウスのロードジョブのクォータ、 コミットのレイテンシ、DDL の同時実行性はこれらの数字に含まれず、含めることもできません。
  • 耐久性ではありません。 durability: memory が唯一のティアなので、202 は *RAM に受け付けた*ことを意味します。測るのはそれがどれだけ速く起きるかであって、SIGKILL の後に 何が生き残るかではありません。
  • あなたのハードウェアではありません。 形と比率として読んでください。

ローカルクラウド、プロファイルごと#

bash
docker compose -f docker-compose.drivers.yml --profile gcp up -d
docker compose -f docker-compose.drivers.yml --profile all up -d

クラウドごとに 1 つではなく、プロファイル付きの 1 つのファイルです。2 つのファイルは 2 つのプロジェクト名 であり、両方にある postgres が、すでに一度エンジンの開発用データベースを置き換えてしまったからです。

floci がカバーする BigQuery は、見かけより少ない#

仮定ではなく計測した結果です。

データセットとテーブルの作成✅
timePartitioning と clustering が保持される✅ — 0.9.1 のバグの形
列の PATCH✅ — auto_table の進化
insertAll✅
クエリ✅、/var/run/docker.sock をマウントした場合のみ
ロードジョブ❌ Only QUERY jobs are supported by the floci BigQuery emulator

SDK が BigQuery に書き込むのは、ロードジョブだけを通じてです。そのため floci が検証するのは、 ペイロードを DDL に変える auto_table のすべての行であり、Brevis の書き込みは 1 つもありません。 それでもローカルテストがない半分であり、持っておく価値はあります。しかし floci に対してスイートが 緑だからといって、BigQuery が動くことにはなりません。

[k6]: https://k6.io
