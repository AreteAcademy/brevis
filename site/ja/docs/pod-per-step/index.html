ステップごとの pod

なぜ各ステップが専用の pod で動くのか、そしてそれがコストと分離にどう影響するのか。

Kubernetes では、ワークフローの各ステップが pod になり、そのステップで宣言された イメージを使います。仕事を待つ汎用ワーカーは存在せず、仕事が自分のランタイムを持ち込みます。

scheduler                          cluster
─────────                          ───────
walks the graph
  for each ready step:
    builds the Pod  ───────────►  Pod: the step's image, the step's command
    follows status      ◄───────  Pending → Running → Succeeded/Failed
    follows the log     ◄───────  container stdout
    reads the exit code ◄───────  containerStatuses[0].terminated
    deletes the pod ───────────►  (gone)

何が変わるか#

モノリシックなワーカーでは、どのステップが必要とするかもしれないものをすべて、イメージに 入れなければなりません。実際には次のようになります。

単一イメージステップごとの pod
dbt のステップ1.9 GB · 1Gi RAM1.9 GB · 1Gi RAM
その隣の Go フェッチャー1.9 GB · 1Gi12 MB · 32Mi
dbt のバージョンを上げるすべてを再ビルドそのワークフローの YAML の 1 行
メモリリークするステップワーカーと隣のステップごと落ちる単独で落ちる

3 行目は最もわかりにくく、日々のコストとしては最も高くつきます。単一イメージでは、 1 つのパイプラインで dbt を 1.10 から 1.11 に上げると、すべてのパイプラインで上げることに なります。

ロールごとのイメージ#

イメージは、プロジェクトごとではなくロールごとです。イメージに余分に残ったものは、 そのステップを実行するすべてのノードが取得します。

ロールサイズコールドスタート
Go5.8 MB0.18 s
Python118 MB0.54 s
dbt620 MB3.3 s

以前は、すべてに対して 1.87 GB の単一イメージでした。

dbt では、ビルド時に dbt parse が実行され、target/partial_parse.msgpack がイメージに 含まれます。これにより、呼び出しのたびに、pod あたり 2.68 秒短縮されます。

各ステップが動く場所#

この判断は起動時に一度だけ行われ、BREVIS_PODS とクラスタの有無によって決まります。

BREVIS_PODSクラスタありクラスタなし
auto(デフォルト)image: のあるステップは pod になるすべてローカルプロセス。ログに警告が出る
onimage: のあるステップは pod になる起動エラー
offすべてローカルプロセスすべてローカルプロセス

host: のあるステップは、このどれも通りません。 pod より先、プロセスより先に判定され、 すでに動いているマシンに送られます。BREVIS_PODS は適用されず、ローカルプロセスに フォールバックすることも決してありません。これは意図的です。image: が警告付きでローカル実行に 縮退するのは、コンテナとプロセスが、同じコマンドを 2 通りに包んだものだからです。ホストは違います。 ライセンスがあり、GPU があり、データがある場所です。

auto がデフォルトなのは、同じバイナリが両方の場所で動くからです。ノート PC ではサービスアカウントが マウントされておらずローカルプロセスにフォールバックし、クラスタではマウントされていて pod の作成を始めます。

on は、黙ってローカル実行になってはならないデプロイのためにあります。そこでは、 クラスタがないことは起動エラーでなければなりません。

`brevis run` は pod を作りません

run コマンドが組み立てるのはプロセスのエグゼキュータだけです。image: のあるステップは インスタンス自身で実行され、その旨が表示されます。黙っていると、宣言したイメージで ステップが動いたように見えてしまいます。それは、結果がすでに間違っているときにしか 表面化しない類のミスです。

ID と認証情報#

pod がどの ID で起動するかは、ワークフローではなくインストールの判断です。パイプラインが 自分の実行するサービスアカウントを選べてはなりません。そのため、環境から取得します。

bash
BREVIS_POD_NAMESPACE=data
BREVIS_POD_SERVICE_ACCOUNT=brevis-runner
BREVIS_POD_PULL_SECRETS=registry-cred
BREVIS_POD_ENV_FROM_SECRETS=bigquery-cred,api-tokens

pod モードでは、タスクの環境はクラスタの Secret から取得され、BREVIS_TASK_ENV からは 取得されません。

ノードセレクタと toleration#

bash
BREVIS_POD_NODE_SELECTOR='kubernetes.io/arch=arm64'
BREVIS_POD_TOLERATIONS='dedicated=data:NoSchedule'

toleration では Equal 演算子だけが受け付けられます。Exists はそのキーを持つあらゆる taint を許容してしまい、環境変数から来る判断としては広すぎます。

不正な形式の toleration は、起動エラーにはせず無視されます。pod は Pending のままになり、 それは目に見えます。一方、起動を拒否すると、そのプールを必要としないワークフローまで 止まってしまいます。

失敗のデバッグ#

bash
BREVIS_POD_KEEP_ON_FAILURE=true

失敗した pod を残し、kubectl logs と kubectl describe で調べられるようにします。 本番ではオフにしておいてください。停止した pod はクラスタのクォータを消費します。
