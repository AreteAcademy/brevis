オブザーバビリティ

両方のプロセスの Prometheus メトリクス、何を監視するか、そして意図的に存在しないもの。

Brevis は、両方のプロセスから、専用のポートで Prometheus メトリクスを公開します。

GET http://<pod>:9090/metrics

ポートは BREVIS_METRICS_ADDR で指定します。HTTP ポートとは意図的に分けています。メトリクスは インターフェースの認証を通らず、両方を同じ場所で提供すると、認証付きのスクレイプか、 開放されたダッシュボードかの二択を迫られるからです。

2 つのプロセス、2 つのエンドポイント#

ここは、多くの構成が API だけをスクレイプして間違える部分です。

提供するもの報告するもの
brevis serveUI と HTTP APIキューの深さ
brevis schedulerHTTP では何も提供しないキューの深さ、claim のレイテンシ、slot、孤立、run、ステップ

実行するのはスケジューラなので、ほとんどすべてがそこから得られます。API だけで作ったダッシュボードは、 キューが増えていることは示しても、それを消化しているものについては何も示しません。

ステップが公開するメトリクス#

エンジンが計測するものに加えて、ステップは独自のメトリクスを公開できます。何行が着地したか、 ベンダーが何行を拒否したか、などです。

python
from brevis import metrics
metrics.set("rows_loaded", 48213)

これらは同じスケジューラの /metrics に、エンジンによってプレフィックスとラベルが付けられて 現れます。

brevis_step_rows_loaded{workflow="daily_sales",step="load"} 48213

ステップはポートを開きません。stdout に 1 行書き、エンジンがそれを記録します。40 秒しか生きない pod はスクレイプできないからです。Python を参照してください。

何を監視するか#

シグナル理由
キューの深さが増え続けて減らないスケジューラが死んだか、負荷に対して --concurrency が低い
claim のレイテンシが増加しているデータベースの競合、またはインターバルに対してキューが大きすぎる
孤立 > 0終了前に死んだプロセスが claim した run
slot が具体化されていないスケジューラのループが止まり、スケジュールも一緒に止まる

最初の 2 つだけでは「高負荷」と「プロセスの停止」を区別できません。そのため slot が重要です。 キューが増え、かつ slot が作られているなら負荷です。キューが増え、slot が作られていないなら、 ループが止まっています。

Kubernetes#

yaml
env:
  - name: BREVIS_METRICS_ADDR
    value: ":9090"
ports:
  - name: metrics
    containerPort: 9090

Prometheus Operator では、ロールごとに 1 つの PodMonitor を使います。そして、ロールごとに 1 つで なければなりません。2 つの Deployment は異なるラベルを持ち、異なるセットを報告するからです。

意図的に存在しないもの#

トレース。 OpenTelemetry はまだありません。ステップは専用の pod として動き、その開始、終了、 試行、終了コード、ログといった重要な情報は、すでにデータベースと画面にあります。有用なトレースは ステップの内部にあるものであり、それはオーケストレータではなくステップのコードに属します。

これはステップが単位である限り成り立ちます。ステップが別のサービスを呼び出し、問いが「40 秒は どこに消えたのか」になる日から、トレースはそのコストに見合うものになり始めます。
