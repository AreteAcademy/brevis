取り込みの sink

6 つの宛先、各データベースがレコードを書き込む方法、そしてイメージが使うものだけを含む理由。

宛先は 6 つで、このリストは意図的に明示的にしています。*計画中*のコネクタと*動作する*コネクタは、 これを選ぶ人にとって別のものだからです。

sink状態書き込みとは検証先
pubsub動作するバッチごとに 1 回の publish。属性と ordering key はイベント自身のフィールドからエミュレータ
postgres動作するCOPY FROM STDIN、または 1 トランザクション内のステージング INSERT実際の Postgres
mysql動作するトランザクション内の複数行 INSERT、または INSERT IGNORE実際の MySQL
files動作するディレクトリ、gs://、s3:// への NDJSON オブジェクトファイルシステムと S3
bigquery動作する行のロード、または ingestion_id でのステージングと MERGE設定のみ — エミュレータが存在しない
redshift動作するバッチを S3 へ、次に COPY、次に MERGE設定のみ — エミュレータが存在しない

6 つのうち 2 つは、エンドツーエンドでは未検証です。表は、誰も確認していない主張を 「動作する」という言葉に担わせるのではなく、そう明記しています。BigQuery と Redshift にはローカルの エミュレータがないため、テストされているのは、設定、拒否、そしてその下のドライバです。ドライバは SDK 自身の テストスイートがすでにカバーしています。どちらかの最初の本番利用が本当の証明であり、リスクの低い ストリームで行うべきです。

未知の type: は起動時に拒否され、*このバイナリ*が持っているものが示されます。持っていない sink で 起動した gateway は、誰にも見えない理由でイベントを捨てる gateway だからです。

gs:// と s3:// は別のコネクタではありません。files が 3 種類のパスの形をすべて読むので、 dead letter はノート PC ではフォルダ、本番ではバケットになり、ここで何も変える必要はありません。

それぞれの書き込み方#

write は、テーブルに書き込む 4 つの宛先で必須であり、デフォルトはありません。2 つのモードは 本当に異なり、どちらかを知っているのはテーブルの所有者だけだからです。

appendmerge
postgresCOPY FROM STDININSERT … ON CONFLICT (ingestion_id) DO NOTHING
mysqlブロックごとの複数行 INSERTINSERT IGNORE
bigquery行のロード(インライン上限を超えると GCS 経由)MERGE … WHEN NOT MATCHED THEN INSERT
redshiftS3 からの COPYステージングテーブルへの COPY、その後 MERGE

merge は 4 つすべてで同じ意味です。冪等な挿入で、最初の配信が勝ちます。再配信は適用されず 無視されます。これは、一度だけ起き、変わらないイベントには正しく、可変な状態を持つ行には間違っています。

Postgres と MySQL は、merge に ingestion_id の UNIQUE インデックスを必要とし、なければ 黙って追加するのではなく拒否します。

sql
CREATE UNIQUE INDEX CONCURRENTLY ON landing.orders (ingestion_id);

インデックスがなければ、ON CONFLICT に照合する対象がなく、すべての再配信が、所有者が正反対を 求めたテーブルに重複してしまいます。拒否はバッチの喪失ではありません。リトライされ、その後、理由と CREATE INDEX をレコードに付けて dead letter に葬られます。誰かがインデックスを作成するあいだに イベントを失う人はいません。

upsert は名前を挙げて拒否されます。 *最後の*配信が勝つ ON CONFLICT DO UPDATE は実在するモードですが、 実装されていません。merge のように振る舞いながらその言葉を受け付けるのは、そのフィールドが防ぐために 存在する失敗そのものなので、設定はそう伝えます。

それぞれに固有の事実#

yaml
# Postgres: schema-qualified name, and the table has to exist.
sink: {type: postgres, dsn_from: BREVIS_DSN, table: landing.clicks, write: merge}

# MySQL: no COPY, so throughput is an order below Postgres on the same
# hardware. Flush wider here.
sink: {type: mysql, dsn_from: BREVIS_DSN, table: landing.clicks, write: merge}

# BigQuery: no dsn_from. It authenticates with the pod's own credentials, which
# is what a workload identity is for. The name has no dots — the project and
# the dataset are their own fields.
sink: {type: bigquery, project: acme-prod, dataset: landing, table: clicks, write: merge}

# Redshift: two hops, not one. It is columnar, a row-by-row INSERT pays the cost
# of a block, and the only workable load is COPY from S3. So every batch becomes
# an object in the staging prefix and then a COPY — a stream flushing every
# second writes 86,400 objects a day. Flush much wider here.
sink:
  type: redshift
  dsn_from: BREVIS_RS_DSN
  table: landing.clicks
  staging: s3://acme-staging/gateway/
  iam_role: arn:aws:iam::123456789012:role/redshift-copy
  write: merge

dsn_from は、接続文字列を保持する環境変数の名前であり、文字列そのものではありません。DSN には パスワードが含まれ、このファイルは git にあるからです。ワークフローの secrets: と同じ分け方です。

iam_role はロールであり、ドライバはキーを受け付けません。COPY の URL に入ったキーはクラスタの クエリログに残り、それを読む人は大勢いるからです。

列の宣言はない#

gateway は列のリストを送りません。パイプラインが自分で宣言するのは、その行が自分で制御できる 1 つの形を 持つからです。gateway のバッチは、1 回のフラッシュウィンドウで N 個のクライアントが POST したものが 何であれそれになり、形が異なることが許されています。

ドライバは、サーバーに触れる前に、テーブル自身から列のリストを取得し、バッチが持つものと 突き合わせて決定します。テーブルにないフィールドは、COPY の途中で column "x" of relation "y" does not exist と失敗するのではなく、修正方法を示すメッセージとともに 拒否されます。あるイベントが省略したフィールドは NULL として書き込まれます。

import のリストが選択になる#

sink はフックと同様にコンパイルして組み込まれ、バイナリは持っているものを登録します。

go
func main() {
    sinks := gateway.NewSinks()
    sinks.MustRegister(postgres.Sink, postgres.New)
    sinks.MustRegister(files.Sink, files.New)
    gateway.Main(nil, gateway.WithSinks(sinks))
}

Go のリンカは、何も参照していないものを刈り込むので、BigQuery ドライバを一度もインポートしないバイナリは、 BigQuery を持ちません。Arrow も Storage Write API も持ちません。database/sql が昔からそうして きたやり方です。

その価値は、聞こえるとおりです。

ビルドパッケージ数バイナリ
6 つすべての sink、両方のオブジェクトストア、両方のメタストア約 90055.0 MB
postgres + ローカルの files約 24010.2 MB

オブジェクトストアは2 つ目のレジストリです。スキームは宛先ではないからです。files は、ディレクトリ、 gs://、s3:// に書き込む 1 つの sink であり、ローカルにしか書き込まないビルドが、そのために AWS SDK を抱えるべきではありません。

公開されている 2 つのイメージ#

イメージ含むものpull サイズ(amd64)
areteacademy/brevis-gateway:0.32.06 つの sink、S3、GCS、Redis、memcached19.1 MB
areteacademy/brevis-gateway:0.32.0-slimpostgres、ローカルの files、auto_table5.2 MB

どちらも 1 つのツリーの 1 回のビルドから作られるため、2 つのタグは常に同じコミットです。 latest-slim はありません。latest はすでに、誰もデプロイすべきでないタグだからです。

別の組み合わせが欲しいですか? cmd/gateway-slim は 15 行で、import ブロックがその設定のすべてです。 コピーして import を変え、ビルドしてください。フックが欲しい人はすでに自分でバイナリをコンパイルして いるので、sink を選ぶことにそれ以上のコストはかかりません。

拒否は、どのビルドを持っているかを教える#

sink type "bigquery" is not one this binary carries (it has: files, postgres).
Sinks are compiled in, so this is a build that left it out rather than a
destination that does not exist.

固定のリストでは、その人は、自分がしていない設定ミスを探すことになります。オブジェクトストアも同じです。 S3 バックエンドのないバイナリでの s3:// の dead letter は、葬らなければならない最初のバッチではなく、 起動時にスキームを示して拒否されます。

1 つのルート、N 個のテーブル、宣言するものは何もない#

yaml
sink:
  type: auto_table
  shape: columns
  naming: {pattern: '^(app|svc)_[a-z0-9_]{2,40}$', allow: [app_, svc_], max_new_per_hour: 20}
  metastore: {type: redis, addr_from: BREVIS_METASTORE_ADDR, ttl: 60s}
  into: {type: bigquery, project: acme-prod, dataset: landing, write: merge}

auto_table はルーティングするだけで書き込みません。書き込むのは into で、table を持ちません。 テーブルは各イベントから決まります。table を持つ into は起動時に拒否されます。ルーターの下の固定テーブルが 黙って優先され、すべてのイベントがそこに着地してしまうからです。

エンベロープ#

ボディはエンベロープです。制御フィールドが最上位にあり、レコードは data の中にあります。

json
{
  "table_name": "app_orders",
  "description": "App orders",
  "operation": "INSERT",
  "unique_key": "id",
  "data": {
    "id": "A-1",
    "total": 150,
    "customer": {"id": 7, "uf": "SP"},
    "items": [{"sku": "X", "qty": 2}]
  }
}
フィールド内容
table_name必須これが着地する場所
data必須レコード、そしてレコードだけ
unique_keyデフォルトは iddata のどのフィールドがレコードを識別するか — merge では必須
operationデフォルトは INSERTINSERT、UPDATE、DELETE
description任意受け付けるが、まだ使われていない — 後述

total や customer の隣にある table_name は、トランスポートのフィールドがレコードの フィールドのふりをしていたものでした。両者を分けるのは、あらゆる CDC フォーマットの形であり、 プレフィックスを予約できるようにするものでもあります。プロデューサーだけが書く場所が、 1 つできたからです。

キーは merge のものであり、エンベロープのものではない#

unique_key は任意で、それが必須かどうかは書き込みモードで決まります。2 つのモードが 求めるものが異なるからです。

write: merge必須。 このモードはレコードごとに 1 行を保つために存在し、brevis_record_key が「レコードごと」の意味です。現行バージョンを解決する qualify はそれでパーティションを切ります。どのレコードも指さない行でいっぱいの merge テーブルは、誰にも解決できないテーブルです。
write: append任意。 append テーブルはログであり、ログのエントリは、レコードに*ついて*のものである必要はありません。監査ログ、Webhook、メトリクスのサンプルなどです。そこで id を要求すれば、プロデューサーに id をでっち上げさせることになり、本物らしく見える分、NULL より悪くなります。

append では、列は null 許容で作成され、キーのない行は NULL を持ちます。"" ではありません。それは別の事実だからです。 そして brevis_ingestion_id は引き続き存在します。キーがなければ内容がキーになるので、 同じドキュメントを 2 回送れば同じ id になります。

data にないフィールドを指定すると、どちらのモードでもエラーです。「言わなかった」と 「そこにないものを言った」は別の間違いで、通るのは前者だけです。

json
{"accepted":0,"rejected":["event 0: \"unique_key\" names \"pedido_id\" as this
 record's identity and \"data\".\"pedido_id\" is missing or empty. Drop
 \"unique_key\" to fall back to \"id\", or send the field"]}

description は読み取られますが、現時点ではどこにも行きません。 まだ書かれていない Console の 取り込みページのために、契約に含まれています。ここで明言するのは、黙って受け付けられたフィールドは、 保存されていると誰かが信じるフィールドだからです。

8 つの固定列と、レコードが持つもの#

列
brevis_ingestion_idSTRING識別子であり、merge のキー
brevis_record_keySTRINGdata[unique_key] — どのレコードについてのものか。append では NULL
brevis_operationSTRINGINSERT、UPDATE、DELETE
brevis_received_atTIMESTAMP到着時刻。こちら側の時計で。パーティション列
brevis_loaded_atTIMESTAMP書き込み時刻。宛先が刻印する
brevis_streamSTRINGどのルートが書いたか
brevis_gatewaySTRINGどのデプロイか
brevis_received_bytesINT64イベントがエンベロープを含めてどれだけの大きさで届いたか

この 8 つは、この sink のものではなく SDK のものです。sdk.LandingSchema がそれらを宣言し、 sdk.LandingID が識別子を生成するため、パイプラインは同じテーブルを同じ id で着地させられます。 定義は 1 つです。2 つあればずれていくからです。 SDK のランディングレイアウトを参照してください。

brevis_ は予約されています。 そのプレフィックスを持つキーが data にあると、イベントごとに 拒否されます。さもなければプロデューサーが制御フィールドを偽造でき、偽造された brevis_received_at は 本物らしく見える分、ないよりも悪いからです。

brevis_loaded_at は、データベースの DEFAULT であり、gateway が送る値ではありません。 gateway が知っているのは送出の時刻、宛先が知っているのは書き込みの時刻で、2 つの列の差が、 行ごとの本当のエンドツーエンドのレイテンシです。何も計装する必要はありません。

brevis_received_at はパーティション列であり、クライアントの時計では決してありません。 プロデューサーの時計は間違っているか、存在しないことがあり、クライアントが制御できるパーティション列は、 2035 年に書き込めるクライアントを意味します。パーティションのないランディングテーブルは、増える一方の クエリ料金です。クラスタリングは brevis_record_key で行います。このようなテーブルで誰もがすることは、 1 つのレコードの履歴を読むことだからです。

1 つの宣言がすべての宛先に使えるのは、SDK の DDL ジェネレータが各型を変換するからです。STRING は Postgres では TEXT、MySQL では LONGTEXT、BigQuery では STRING になり、JSON は JSONB、JSON、JSON になります。

ボリュームを測るインフラなしでボリュームを知る#

brevis_received_bytes は無料です。gateway は buffer.flush.size を駆動するために、デコード時に すでにこのバイト数を数えており、これまでその数字はそこで捨てられていました。レコードだけを測ろうとすると、 イベントごとに json.Marshal が必要になり、パースがすでに使う 3.1 µs に対して 2.0 µs、つまりホットパスで 67% 多くかかります。それも、傾向と帰属を知るための数字を洗練させるためだけに。

これは、メトリクスが構造的に答えられないことに答えます。すべての brevis_gateway_* 系列は *ストリーム*単位で、table ラベルを意図的に持ちません。auto_table では 1 つのルートが N 個のテーブルに なり、そのラベルを選ぶのはプロデューサーだからです。そのため、「どのテーブルが、いつから増えているか」には、 どこにも答えがありませんでした。

sql
select date(brevis_received_at) day,
       count(*) events,
       sum(brevis_received_bytes)/1e9 gb
from app_orders
group by 1 order by 1 desc

この列がなければ、同じ問いのたびに JSON 列全体のスキャン、つまり sum(length(to_json_string(data))) が必要で、スキャンされるバイト数は約50 倍です。この列は、 最初のクエリで元が取れます。

これはストレージではなくイングレスです。 宛先は行を型付けして圧縮して保持するため、 400 バイトの JSON がディスク上では 80 バイトのこともあります。これを合計して得られるのは、*届いた*量であって、 保持に対して課金される量ではありません。

そしてプロデューサーはこれを書き込めません。gateway はフックの後に値を刻印し、エンベロープが 持っていたものを上書きします。このフィールドを送ってきたクライアントは自分のボリュームを報告する ことになり、その合計は何も意味しなくなるからです。

ボリューム系列はオプトイン#

bash
BREVIS_INGESTION_METRICS=true
brevis_gateway_ingested_bytes_total{stream,table}
brevis_gateway_ingested_events_total{stream,table}

デフォルトではオフであり、デフォルトであることが要点です。table は*プロデューサー*が選ぶラベルです。 このファイルの他のすべては、オペレータが YAML に書いたものでラベル付けされるため、系列の数はプロセスの 起動前にわかります。アップグレードしたからといって、誰もメトリクスの請求書を見つけるべきではありません。

パースできない値は、失敗ではなくオフとして読まれます。これはオブザーバビリティであり、ここでの タイプミスが取り込みエンドポイントが起動しない理由になってはならないからです。

列はどちらの場合もあります。メトリクスは*今*を買い、列は*いつから*と*誰によって*を買います。

2 つの形、1 つの契約#

shape は、レコードが行に何を寄与するかを決めます。プロデューサーの契約はどちらでも同じで、 エンベロープは変わりません。変わるのはテーブルの見た目で、それはプロデューサーではなく オペレータの判断です。

yaml
shape: document   # the default
shape: columns

document では、data が丸ごと 1 つの JSON 列に入ります。

 brevis_ingestion_id | brevis_record_key | … | data
 d7179bfe-…          | A-1               |   | {"id": "A-1", "total": 150, "customer": {…}}

作成後に DDL が発生することはありません。新しいフィールドは新しいキーです。スキーマ変更のクォータも、 書き込みストリームの再オープンも、レプリカ間の競合もなく、届いたその日からクエリできます。 市場がたどり着いた形でもあります。Fivetran、Airbyte、Snowpipe はいずれも、失敗し得ない raw 層に 着地させ、モデリングは下流で行います。

columns では、レコードの各フィールドが独自の列を持ちます。

 id   | total | customer              | items
 A-1  | 150   | {"id": 7, "uf": "SP"} | [{"qty": 2, "sku": "X"}]

スカラーは STRING、オブジェクトと配列は JSON になり、どこにも推論はありません。 150 は数値として 届いて、文字列 150 になりました。これは制限ではなく選択です。今日は整数で届き、明日は小数で届く フィールドは、誰も何も書いていないのに列の型を変えてしまい、もう合わなくなった行は dead letter に行きます。 型を付けるのは昇格の経路で、YAML に書かれ、差分でレビューされます。

null は、列をまったく作りません。 形がないので読み取るものがなく、フィールドは、値を持つ最初のイベントから、 その値の形でテーブルに現れます。null を送ったイベントも、それが意味したとおり NULL として着地します。 そして、宣言したか別のイベントが作ったかで列がすでに存在する場合は、null は省かれるのではなく、 その列に書き込まれます。

そして JSON 列は JSON の値を受け取り、決してその文字列ではありません。 細かいことに聞こえますが、 クエリできるテーブルと、正しく見えるだけのテーブルの違いです。

sql
SELECT JSON_TYPE(customer) FROM bronze.orders;     -- object
SELECT JSON_VALUE(customer, '$.uf') ...;           -- SP

JSON_TYPE が string を返し、JSON_VALUE が NULL を返すなら、オブジェクトが二重にエンコードされています。 列はオブジェクトではなく、オブジェクトの TEXT を保持しています。0.15.0 以前の gateway バージョンは、 BigQuery で両方の形についてそうなっていました。1 行で確認する方法と修復は gateway の changelogを参照して ください。Postgres と MySQL は影響を受けていません。サーバーがテキストをパースするからです。

フィールド名は、4 つの中で最も狭い BigQuery のルールに合致する必要があります。Postgres は引用符を付ければ ほとんど何でも受け付けますが、それが罠です。そこではテーブルが作成され、誰かがストリームを BigQuery に 向けた日に壊れます。

どちらの形にも SDK に相当するものがあり、それは一致するコードではなく同じコードです。 sdk.Landing(table, sdk.LandingKey("id")) は document を着地させ、 sdk.LandingColumns()を加えると columns を着地させます。列も、値も、brevis_ingestion_id も同じなので、ストリームはマイグレーションなしで gateway とパイプラインの間を移動でき、両者を 1 つのテーブルとして読めます。

パイプラインも、同じ列を同じ方法で増やせます。宛先に Evolve: sdk.EvolveAdditiveFromPayloadを 設定すると、バッチが持つフィールドが、このルール、このコードによって列になります。

プレフィックスは設定可能で、プロセス全体での 1 つの判断です。 BREVIS_LANDING_PREFIX=acme にすると acme_ingestion_id などになります。この gateway のすべての ストリームに及ぶので、両方が書き込むかもしれないテーブルについて 2 つの sink が食い違うことはありません。 上の予約ルールもそれに合わせて移ります。acme_ の下では、acme_region を送るプロデューサーは拒否され、 brevis_region は普通のフィールドです。

最初のテーブルを作る前に選んでください。 後から変更すると、8 つの列が追加されて 8 つが放棄されます。 列を削除するものはないため、あるプレフィックスでレイアウトをすでに持つテーブルは、別のプレフィックスを 宣言したロードを拒否します。正規化と回避方法は SDK のページを参照してください。

ネストされたオブジェクトのフィールドに、独自の列を持たせることができます。 gateway のプロセスで BREVIS_NORMALIZE_DATA=true にすると 1 階層がフラット化され、 {"name": {"first": "x"}} は name_first として着地します。すべてのストリームがこれを共有するため、 両方が書き込むかもしれないテーブルについて 2 つの sink が食い違うことはありません。何がリネームされるかは SDK のページを参照してください。有効にする前に読むべきなのは そちらの半分です。

BigQuery では、nationalID と nationalId は 1 つの列です。 BigQuery は列の大文字小文字を畳み込む ため、DELETE で一方の綴り、INSERT で他方の綴りを持つフラッシュは、CREATE を失敗させるのではなく、 ソート順で最初の1 つの列を作成します。1 つのイベントが両方を持つ場合は、両方のフィールドを示して 拒否されます。Postgres と MySQL では 2 つの列のまま保持され、それらにとっては正しい動作です。 どちらの綴りが勝つか、何がマイグレーションされないかはSDK のページを参照してください。

UPDATE と DELETE は、適用されず記録される#

brevis_operation は列です。ランディングテーブルは履歴です。その場で適用された UPDATE は以前の バージョンを失い、そのバージョンが欲しくなる日は、何かが壊れた日です。「各レコードの現行バージョン」の 解決は、下流のモデルの仕事です。

sql
qualify row_number() over (partition by brevis_record_key
                           order by brevis_received_at desc) = 1
   and brevis_operation <> 'DELETE'

これは Debezium、Fivetran、Airbyte がしていることで、CDC が書き込み経路で何もコストを払わないことを 意味します。upsert モードも、ロックも、削除もありません。

識別子に時計は入っていない#

brevis_ingestion_id = uuid5(auto_table | table | data[unique_key] | sha256(canonical(data)))

計算式に occurred_at はなく、これは意図的です。到着はこちら側の責任になり、こちらの時計は time.Now() で、配信のたびに異なります。それを含んだ識別子では、すべての再配信が新しいイベントになり、 merge は何も吸収しなくなります。

same record, same content, twice  →  same id, merge absorbs
same record, content changed      →  a different id, both versions land

注意点は文書化されているとおりです。バイト単位で同一の data を持つ、本当に別の 2 つのイベントは 1 つにまとまります。CDC ではそれが正しい動作です。同じ値での、1 つのレコードに対する同一の 2 回の更新は、 同じ事実だからです。

フィンガープリントは、正規形のドキュメントに対して計算されます。すべての階層でキーをソートし、 配列は順序を保ち、すべてを引用符で囲みます。Go はマップの反復順序をランダム化するので、素朴なハッシュは 同じイベントの 2 回の配信で異なってしまい、それがハッシュの防ぐべき唯一のことだからです。

テーブルは自分で列を増やす#

テーブルにないフィールドを持つ data は、列を出現させます。追加のみで、追加だけです。 何も削除されず、何も狭められません。

BigQuery でこれが成り立つようになったのは 0.13.0 からです。それ以前は、auto_table は すべての宛先に Evolve: additive を宣言していましたが、その宣言を読んだのは Postgres と MySQL の ドライバだけでした。そのため、BigQuery では形が作成時に固定されたままで、そのことを伝えるものは ありませんでした。

0.11.0 または 0.12.0 から移行する場合、0.11.0 より前に作成されたテーブルには、1 回限りの マイグレーションが必要です。8 番目の固定列が宣言に追加され、テーブルには追加されなかったからです。 ``sql ALTER TABLE <dataset>.<table> ADD COLUMN IF NOT EXISTS brevis_received_bytes INT64 `` Postgres と MySQL は影響を受けませんでした。

ALTER の競合に負けたバッチは失敗し、パイプの通常のリトライがそれを解決します。DDL を待つバッチと ワーカーを待つバッチは同じものなので、2 つ目のバッファはありません。複数のレプリカにまたがっては、 メタストアがテーブルごと、形ごとに 1 秒の*デバウンス*を保持します。同じ新しいフィールドを見た 10 個の レプリカが、BigQuery のテーブルあたり 10 秒に 5 回のメタデータ操作というクォータに対して、10 回の ALTER にならないようにするためです。

ロックではなくデバウンスです。何も解放されず、リースも更新されません。負けた側は ブロックされるのではなく*リトライされ*、保持したまま死んだレプリカのコストは、他のレプリカに とっての 1 秒です。市場がしていることと同じです。Delta Lake と Iceberg は楽観的にコミットしてリトライし、 Kafka Connect はパーティションの順序から直列化を得て、Fivetran はテーブルごとに 1 つのライターを保ちます。

名前は攻撃対象領域#

auto_table はペイロード内の文字列を DDL に変えるので、naming 配下のすべてのフィールドが拒否の ルールになります。

  • pattern のデフォルトは ^[a-z][a-z0-9_]{2,48}$ で、Postgres、MySQL、BigQuery、Redshift が 引用符なしで受け付けるものの共通部分です。これを通る名前はどこでも引用符が不要で、インジェクションを 含みえません。
  • allow は、プレフィックスでさらに絞り込みます。
  • max_new_per_hour(デフォルト 20)は、ローリング 1 時間における作成の上限であり、書き込みの 上限ではありません。すでに存在するテーブルがレート制限されることは決してありません。 metastore: memory では予算はプロセス内にあり、4 つのレプリカはこの 4 倍を許します。redis または memcached では、1 つのカウンタを共有します。

ルール外の名前はイベントごとに、レスポンスで拒否され、同じリクエスト内の正しい形式のイベントは すべて着地します。

json
{"accepted": 0, "rejected": ["event 0: the table name \"orders\" does not match ^(app|svc)_[a-z0-9_]{2,40}$"]}

バッチごとではなくイベントごとなのは意図的です。書き込み時に拒否すると、バッチ全体が失敗し、 1 人のプロデューサーの不正なイベント 1 つが、同じフラッシュウィンドウにある他のすべてのプロデューサーの イベントを葬り、誰にも通知されません。

auto_table は listen.auth のないエンドポイントでは拒否されます。 BREVIS_ENV=local でも 同様です。テーブルに名前を付けられるプロデューサーはそれを作成できるので、通常のストリームでは 不要な場合でも認証が必要です。NetworkPolicy ではカバーできません。それはポートに到達できる人を 制限するもので、彼らが要求するテーブル名を制限するものではないからです。

メタストアはキャッシュ#

イベントごとの書き込みがイベントごとの検索にならないようにするために存在し、3 つのものを保持します。 どのテーブルが存在するか、DDL の*デバウンス*、そして max_new_per_hour を支えるカウンタです。

これはキャッシュであり、信頼できる情報源ではありません。テーブルが存在するかどうかは宛先が決め、 N 個のレプリカが競ってテーブルを作成するのは通常のケースです。AlreadyExists は成功であり、 これは競合を減らすだけです。TTL は、それが間違っていてよい期間です。

バックエンド使う場面
memoryデフォルト。何も要らない。レプリカが1 つならそれが正解
redisaddr_from が必須。SETNX が claim、INCR がカウンタ
memcachedaddr_from が必須。Add が claim で、有効期限は秒単位

ルーティングキーを持つストリームでは Redis のほうが高速で、その差は形容詞ではなく数字で語る価値があります。 トリガーがテーブルごとの場合、ウィンドウはテーブルごとに 1 回の claim を要求します。Redis は 94 件を パイプライン化した 1 回の往復で答え、他のすべてのバックエンドは、32 を上限として並列に答えます。 25 ms 離れたバックエンドに対して計測した結果は、94 件の claim で次のとおりです。

バックエンド1 件ずつ出荷時の動作
redis2.589 s29.8 ms
memcached2.577 s89.4 ms

1 回の往復に対して 3 ウェーブです。どちらも claim に与えられる 500 ms の内側なので、memcached は 遅い選択ですが、拒否される選択ではありません。

複数のレプリカでは、memory は各レプリカに独自のものを与えます。デバウンスは何もデバウンスせず、 max_new_per_hour はプロセスを制限するだけです。他の 2 つが存在する唯一の理由がそれです。

ダウンしているメタストアが、書き込みをダウンさせてはなりません。 エラーになる Get はミス、 エラーになる claim は獲得したものとして振る舞い、エラーになるカウンタは制限を緩めます。取り込みを 止められるキャッシュは、キャッシュがないよりも悪いからです。

そして「ダウン」には「遅い」も含まれます。 claim はバッファのロックを保持している間に実行されるため、 応答に 2 秒かかるバックエンドは、そのストリームが 2 秒間何も受け付けないことを意味します。すべての 呼び出しは 500 ms で制限され、それを超えるとフェイルオープンします。Redis は呼び出し側のコンテキスト としてそれに従い、gomemcache はコンテキストをまったく取らないため、memcached はソケットの デッドラインとしてそれに従います。2 つのクライアントの一方には停止を指示できないため、同じ制限に 2 通りの方法で到達しています。

ttl: 0 は「無期限」を意味し、何も指定しなければ 1 分のデフォルトが適用されます。2 状態ではなく 3 状態です。

間違ったエントリから回復するのは時計ではありません。宛先が拒否した書き込みは invalidate を呼び、 エントリを即座に落とし、パイプ自身のリトライが冷えたキャッシュに対して戻ってきます。手動で削除された テーブルのコストは、1 分ではなく1 回の失敗した試行です。

有効期限には代償があります。sinkFor は、テーブルを把握していないとき naming.max_new_per_hour を 消費します。そのため、数週間存在し続けているテーブルでもミスは課金され、テーブルの最後のイベントの 1 分後に再起動する pod は、料金を払っている共有バックエンドから何も得られません。長寿命のテーブルが あるなら、ttl: 0 が答えです。

0.12.0 と 0.13.1 では、その書き方はパースされません。YAML は裸のゼロを整数として読み、 両方を受け付ける最初のバージョンは 0.13.2 です。それらのバージョンでは ttl: 0s と書いてください。

addr_from は、アドレスを保持する環境変数の名前であり、アドレスそのものではありません。 パスワードを含んでいることがよくあるからです。

BigQuery にはフラッシュの下限がある#

BigQuery は、テーブルあたり 1 日 1,500 回のロードジョブを許可します。 デフォルトの 1 秒ウィンドウでは 86,400 回で、クォータの 57 倍、約 25 分で使い切ります。Pub/Sub では問題にならず、この数字は Pub/Sub の設定から*持ち込まれる*ものです。

そのため、BigQuery に直接またはルーター経由で書き込むストリームは、ウィンドウが 60 秒未満だと ロード時に拒否されます。本当の答えは Storage Write API ですが、まだ書かれていません。それができるまで、 設定は守れないウィンドウを拒否します。最初のデプロイでそれが発覚するよりは良いからです。

auto_table は Redshift にはルーティングできません。そのドライバはテーブルを作成しないため、 新しい名前はすべてロードで失敗するからです。名前を挙げて、起動時に拒否されます。

まだ存在しないもの#

sqlite、dynamodb、kinesis、sqs、sns、kafka、rabbitmq は計画中で、何も書かれていません。 (redis と memcached はメタストアとして存在しますが、それは別のもので、テーブルについて わかっていることのキャッシュであり、宛先では決してありません。)このページの冒頭の表が、それぞれの 状態を示しており、状態が変わったときに更新されます。その前ではありません。
