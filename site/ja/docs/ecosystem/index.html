エコシステム

brevis.sh の 4 つの構成要素と、それぞれの役割、そしてデータが通る場所。

Core はスケジューリング、キューイング、監視を担い、データには一切触れません。データに触れるのは、取得する SDK、受け取る Gateway、そしてデータが着地した後にモデリングする SQL です。

4 つの構成要素#

構成要素役割入手方法ガイド
Coreスケジュールし、キューに積み、ステップごとに 1 つの pod を起動します。データには一切触れません。areteacademy/brevisCore
SDKステップの中で抽出、整形、ロードを行う Go ライブラリです。go get github.com/AreteAcademy/brevis/sdkGo SDK
GatewayHTTP POST を受け取り、202 を返し、バッチで書き込みます。専用のデータベースは持ちません。areteacademy/brevis-gateway取り込み
SQL通常の .sql ファイルを、依存関係の順にテーブルとビューへ変換します。areteacademy/brevis-sqlSQL

コントロールプレーンとデータプレーン#

コントロールプレーンは Core です。各ステップをいつ実行するかを決め、 キューと状態を Postgres に保持し、ステップごとに 1 つの pod を起動します。 データがここを通ることはありません。

データプレーンは残りの 3 つの構成要素です。データは API、データベース、 ファイルから届き、2 通りのどちらかで宛先に到達します。1 つは、あなたのステップの中で SDK が取得する方法、もう 1 つは Webhook やアプリから HTTP で Gateway にプッシュされる方法です。宛先はテーブル、トピック、 またはバケット内のファイルです。データが着地した後は、SQL が着地先の データベース内でそのままテーブルをモデリングします。

周辺の構成要素#

補助的な 3 つの構成要素があります。

  • Console — Core の上に載る Web インターフェース
  • agent — 既存のクラスタでステップを実行します
  • Python 用の brevis — Python ステップ向けの実行コンテキスト

1 つの構成要素だけを使う#

使えます。各構成要素は独自のモジュール、バージョン、イメージを持っています。SDK は任意のプログラムで動く Go ライブラリで、Gateway は YAML ファイルだけでデータベースなしに単独で起動し、brevis-sql はコンテナとして動きます。Core は必要なときに他の構成要素をオーケストレーションしますが、どれの前提条件でもありません。

同じ行#

SDK が取得した注文と Gateway に届いた注文は、同じ brevis_ingestion_id を持つ同じテーブルに着地します。両者の選択はデプロイの判断であり、スキーマの判断ではなくなります。

SDK では sdk.Landing を使います(詳細はランディングレイアウト):

go
sdk.Execute(ctx, &sdk.Pipeline{
	Source:    sdk.Source{From: from.Files{Path: "order.json"}},
	Transform: []sdk.Transformer{sdk.Landing("app_orders", sdk.LandingKey("id"))},
	Target: sdk.Target{
		To:     postgres.Table{DSN: dsn, Name: "app_orders"},
		Schema: sdk.LandingSchema(sdk.LandingOptions{}),
	},
}, nil)

Gateway では /v1/tables への POST を使います(詳細は1 つのルート、N 個のテーブル):

bash
curl -X POST localhost:8080/v1/tables -H 'Authorization: Bearer dev-key' \
    -d '{"table_name":"app_orders","unique_key":"id",
         "data":{"id":"A-1","customer":"acme.example.com","total":150}}'

レスポンス:

text
{"accepted":1,"rejected":null}  202
