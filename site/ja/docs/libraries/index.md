# クライアントライブラリ

> どの言語のステップでも、コンテキストと run の時計を読み取る方法、そしてすでにライブラリがある言語。

*https://brevis.sh/ja/docs/libraries/ · brevis.sh docs (ja)*

---

ステップがオーケストレータから必要とするものは 2 つです。**前のステップが公開したもの**と、
**この run が読むべき時計**です。クライアントライブラリが渡すのはこの 2 つだけで、それ以外は何も
渡しません。

## ライブラリより先に契約がある

エンジンが定義するのは、**2 つの環境変数と 1 つのファイル**です。

| | |
|---|---|
| `BREVIS_INPUT` | `{"<step id>": {…}}` — このステップの依存先が公開したもの |
| `BREVIS_OUTPUT` | JSON オブジェクトを**1 つ**書き込むパス |

これに加えて、run の変数と自動パラメータがあり、すべて読み取り専用です。`BREVIS_RUN_*` と
`BREVIS_AUTO_*` です。Kubernetes では `BREVIS_OUTPUT` は `/dev/termination-log` で、
エンジンは終了コードを得るためにすでにこれを読んでいます。

したがって、**API 呼び出しも、トークンも、ポートも不要**です。どの言語のステップでも、
JSON のパースとファイルの書き込みだけで参加できます。

```bash
window=$(jq -r '.extract.watermark' <<< "$BREVIS_INPUT")
./publish --until "$window"
jq -n --arg n "$(date -Is)" '{published_at: $n}' > "$BREVIS_OUTPUT"
```

ここでのライブラリは新しい機能を開くものではなく、書き直さないほうがよい検証、値が存在しない場合の
処理、エラーメッセージを肩代わりしてくれるものです。

## 存在するもの

| 言語 | | |
|---|---|---|
| **Python** | `pip install brevis` | [利用可能](/ja/docs/python/index.md) — PyPI で `0.2.1` |
| **Go** | `brevis/sdk/context` | 利用可能。SDK モジュールの中にあります |
| **Node.js** | — | 計画中 |
| **Rust** | — | 計画中 |
| その他 | 上記の変数 | 現時点ではこれ |

:::note Go は `lib/` にありません
Go のコンテキスト対応は、プロジェクトがすでに公開している `sdk/` モジュールの中にあり、
インポートしない人にとっては何にもならないサブパッケージです。`lib/go-context` を作ると、
1 つのパッケージのために 2 つ目の Go モジュールを作ることになります。

ルールは、**公開済みの成果物をまだ持たない言語ごとに 1 つのディレクトリ**です。
:::

各ライブラリは、独自のバージョンとタグを持つ別々の成果物です。Python クライアントの修正で
エンジンのリリースが必要になることはありません。

## 何であり、何ではないか

これらは契約の上に載る**薄いクライアント**であり、Go SDK の移植ではありません。

SDK の ETL の仕組み、つまりドライバ、ページネーション、チェックポイント、ingestion id の移植は
ここには属しませんし、おそらくどこにも属しません。対象となるどの言語にも、そのためのより良い
ツールがすでにあり、Brevis の仕事はそれらを実行することだからです。Python ライブラリが存在するのは、
チームが pandas、Polars、dbt を使いながら、オーケストレータの存在意義であるものを得られるように
するためです。

## メトリクス

ライブラリはメトリクスを**出力**し、公開するのはエンジンです。

```python
from brevis import metrics

metrics.set("rows_loaded", 48213)      # a gauge: the last value wins
metrics.inc("vendor_rejected_total")   # a counter: it adds up
```

メトリクスは、スケジューラのポートにある**エンジンの** `/metrics` から、ワークフローとステップの
ラベル付きで出力されます。[オブザーバビリティ](/ja/docs/observability/index.md)を参照してください。

**これはポートを開きませんし、開けません。** ステップは専用の pod で 40 秒動いて終了します。
開いたポートがスクレイプされることは決してないか、運よく一度あるだけです。そのため、その行は
stdout に出力されます。エンジンがパイプラインのフェーズを描くためにすでに読んでいるのと同じ
パイプで、エンジンがそれを記録します。インストールするものも、運用するものもなく、ラベルが
エンジンのものになるのは、ステップが自分のワークフローの slug を知り得ないからです。

API の詳細は [Python](/ja/docs/python/#metrics-only-your-pipeline-knows) にあります。

## 別の言語のクライアントを書く

私たちより先に Node.js や Rust に取り組む場合のために、クライアントが正しく実装すべきことと、
Python 実装がすでに苦労して学んだことを挙げます。

1. **ステップで修飾されたキー。** ステップなしの `get("bucket")` は拒否しなければなりません。
   2 つのステップが `bucket` を公開することがあり、検索して片方を選ぶのは偶然による優先順位だからです。
2. **書き込みをマージする。** 異なるキーでの 2 回の呼び出しは両方を保持し、同じキーの 2 回は最後を保持します。
3. **プロセス終了時にだけフラッシュする。** 強制終了したステップは何も公開しません。これは正しい動作で、
   クラッシュしたステップの出力は、終わっていない仕事を記述しているからです。
4. **4096 バイトを超えたら拒否する。** プラットフォームは拒否せず**切り詰め**、半分に切られた
   オブジェクトは、次のステップに不正な JSON として届きます。
5. **Brevis の外でも動く。** `BREVIS_INPUT` がなければ、`get()` はデフォルト値を返し、`set()` は
   例外を出さずに受け取って破棄します。手動で実行できないスクリプトは開発できないからです。
