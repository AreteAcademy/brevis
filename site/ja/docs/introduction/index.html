ドキュメント

はじめに

brevis.sh とは何か、何を解決するのか、そしてどんなときに最適な選択ではないのか。

brevis.sh は Go で書かれたデータオーケストレーションランタイムです。単一のバイナリが、 通常は 4 つのツールが担う役割をまとめて提供します。宣言的な変換、 ワークフローのオーケストレーション、永続キュー、スケジューラ、 そしてそれらすべてを操作するインターフェースです。

MIT ライセンスのオープンソースで、プロジェクトは Aretê Academy から生まれました。

課題#

一般的なデータスタックは、変換ツール、オーケストレータ、キュー、 インターフェースを組み合わせて作られます。どの部品もそれぞれの役割には優れていますが、 それらの統合は恒久的な作業になります。バージョニングの方式が 4 つ、設定の方法が 4 つ、 障害時に見る場所が 4 つです。

このコストはアーキテクチャ図には現れません。現れるのは、チームが自分たちしか知らない ドメインの仕事ではなく、つなぎ込みの保守に費やす時間です。

提案#

1 つの成果物に、役割に応じたサブコマンドを持たせます。

bash
brevis serve        # API + interface
brevis scheduler    # materialises schedules and drains the queue
brevis run wf.yaml  # runs now, no database

ワークフローはバージョン管理された YAML ファイルです。パイプラインのレビューは、 クリック操作のセッションではなく、差分のレビューになります。

yaml
name: ingest
schedule: "0 5 * * *"

steps:
  - id: bronze
    image: registry.example/dbt:1.10.3
    run: dbt build --select bronze+

  - id: notify
    image: ghcr.io/example/notify:0.3
    run: /notify --channel data
    depends_on: [bronze]

何が違うのか#

すべてのステップは、専用のイメージを使って専用の pod で実行されます。 仕事が来るのを 待つ汎用ワーカーは存在せず、仕事が自分のランタイムを持ち込みます。dbt のステップは dbt のイメージで起動します。その隣の Go 製フェッチャーは、最大の隣人のサイズを 引き継ぐことなく、5.8 MB と 32Mi のメモリで起動します。

スケジューラは run を作り、キューがそれを実行します。 2 つの独立したループであり、 この分離は意図的です。片方が止まってももう片方は中断されず、 過去 1 か月分を再処理するのに時計は関係ありません。

検証にデータベースは要りません。 brevis validate はテストと並べて CI で実行できるため、 YAML のエラーはクラスタではなくプルリクエストの段階で失敗します。

意図的に分けた 3 つの構成要素#

構成要素内容バージョン
enginebrevis。このページの主題となるバイナリで、オーケストレーション、スケジューリング、実行、運用を行います0.15
SDK抽出とロードを行うステップを書くための Go モジュール0.66
gatewayデータを取りに行く代わりに、*届いた*データを着地させる HTTP エンドポイント0.8

バージョンが独立しているのは、成熟度が独立しているからです。engine がそこにあるからといって gateway を 0.15.3 と採番すれば、持っていない成熟度を主張することになり、 公開したバージョンは取り消せません。

3 つをつなぐのは 1 つの数値、ingestion_id です。これは provider|entity|source_key|record_ts に対する固定の UUID v5 です。 gateway が着地させた行と、SDK のフェッチャーが 同じレコードについて着地させた行は*同じ 1 行*になり、両者の間で突き合わせは不要です。

brevis.sh が選択肢にならない場合#

ツールができることを書くより、できないことを書くほうが時間の節約になります。

  • すでに Airflow や Dagster を運用していて満足している。 移行にかかるコストは、 バイナリが 1 つ減る運用上の節約を上回ります。
  • ワークフローがデータに関するものではない。 brevis.sh は変換とロードの DAG を 前提にしています。汎用のオーケストレータのほうが向いています。
  • 既製のオペレータのカタログが必要。 ここではステップはイメージとコマンドです。 シンプルですが限定的で、取り込める何百ものインテグレーションはありません。
  • チームが Kubernetes を使っておらず、使う予定もない。 ローカルモードは動作しますが、 設計は pod を前提としています。

オープンなコード。関わり方は選べます。#

brevis.sh は 100% オープンソースです。独自ライセンスも、機能限定版も、あなたが作るものへの制約もありません。

名前について

Brevis はラテン語で「短い、簡潔な」を意味し、brevity(簡潔さ)の語源です。 セネカの De Brevitate Vitae(人生の短さについて)に由来します。私たちに時間が 少ないのではなく、多くを失っているのだ、という考えです。
