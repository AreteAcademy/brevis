the pieces

Each piece, the way you will use it.

Four independent pieces, each with its own version. Use one, or all four.

Core areteacademy/brevis

One YAML file, one pod per step.

The whole workflow is one versioned file: reviewing a pipeline becomes reviewing a diff. The Core schedules, queues and starts each step with its own image — and never touches the data.

hello.yaml
name: hello
type: dag
tags: [example]

steps:
  - id: prepare
    run: sh -c 'echo preparing; sleep 1'

  # The next two depend on the same step, so they run IN PARALLEL.
  - id: extract
    run: sh -c 'sleep 2; echo 42 extracted'
    depends_on: [prepare]

  - id: validate
    run: sh -c 'sleep 1; echo validated'
    depends_on: [prepare]

  - id: publish
    run: echo published
    depends_on: [extract, validate]
shell
$ docker run --rm -v ./hello.yaml:/w/hello.yaml -w /w \
  areteacademy/brevis:0.17.1-worker run hello.yaml

  ▶ validate

  ▶ publish

SDK brevis/sdk

A whole fetcher in three calls.

Extract reads, Transform reshapes, Load writes. Each takes and returns a sequence — nothing is materialised in memory all at once.

shell
$ go get github.com/AreteAcademy/brevis/sdk@latest
main.go
rows, err := sdk.Extract(ctx, sdk.Source{
	From: from.HTTP{URL: "https://api.example.com/v1/events"},
})

rows = sdk.Transform(rows, sdk.Accept("id", "created_at", "amount"))

res, err := sdk.Load(ctx, rows, sdk.Target{
	To:      bigquery.Table{Dataset: "bronze", Name: "events"},
	Columns: []string{"id", "created_at", "amount"},
})

Requires Go 1.23 or newer.

Gateway areteacademy/brevis-gateway

An endpoint that lands the data that arrives.

The client POSTs and gets a 202 straight away; the batch goes to the destination later, on a worker. No database of its own, and configured entirely in YAML.

gateway.yaml
name: events_gateway

listen:
  addr: :8080
  auth:
    type: bearer
    keys_from: BREVIS_INGEST_KEYS

streams:
  - name: clicks
    path: /v1/clicks
    format: json
    identity:
      provider: web
      entity: click
      source_key: event_id
      record_ts: occurred_at
    sink:
      type: files
      path: /var/landed/
    dead_letter:
      type: files
      path: /var/landed/dead-letter/
shell
$ docker run -p 8080:8080 -e BREVIS_INGEST_KEYS=dev-key \
  -v ./gateway.yaml:/etc/brevis/gateway.yaml:ro -v ./landed:/var/landed \
  areteacademy/brevis-gateway:0.26.1-slim

$ curl -X POST localhost:8080/v1/clicks -H 'Authorization: Bearer dev-key' \
  -d '{"event_id":"e-1","occurred_at":"2026-10-08T12:00:00Z","page":"/pricing"}'
{"accepted":1,"rejected":null}  202

The real answer, from the published image. Without the key, 401.

SQL areteacademy/brevis-sql new · 0.1

Plain .sql files, built in the right order.

No templating: a model is a file that stays valid SQL, and the order comes from reading the SQL itself. Postgres and BigQuery, under the same conformance suite.

models/staging/stg_orders.sql
/* brevis
materialized: view
*/
select order_id, customer_id, amount, ordered_at
from raw.orders
where amount is not null
models/marts/orders.sql
/* brevis
materialized: table
tests:
  - not_null: [customer_id]
  - unique: [customer_id]
*/
select customer_id, count(*) as orders, sum(amount) as revenue
from staging.stg_orders
group by customer_id

the same row

Fetch it or receive it: the row is the same.

An order the SDK fetches and an order that arrives at the Gateway land in the same table, with the same brevis_ingestion_id. Choosing between the two becomes a deployment decision, not a schema one.

through the SDKmain.go
sdk.Execute(ctx, &sdk.Pipeline{
	Source:    sdk.Source{From: from.Files{Path: "order.json"}},
	Transform: []sdk.Transformer{sdk.Landing("app_orders", sdk.LandingKey("id"))},
	Target: sdk.Target{
		To:     postgres.Table{DSN: dsn, Name: "app_orders"},
		Schema: sdk.LandingSchema(sdk.LandingOptions{}),
	},
}, nil)

how it executes

One pod per step. Each with its own image.

The Core reads the workflow and starts one pod per step. Extract in Go, prepare in Python, transform in dbt — each step with the image, the limits and the runtime it declared. No step inherits its neighbour's weight.

The Core never touches your data: it schedules and starts pods, and the data goes from source to destination inside the step. The Gateway has no database: what arrives goes straight to the destination you declared.

01

The work brings the runtime

A step is an image and a command. Bumping dbt is one line in that workflow's YAML, not a rebuild of everything.

02

Context between steps

A step publishes a watermark or a path; the next one reads it. Two environment variables, no API and no port.

03

Failure with a boundary

A step that leaks memory dies alone. With no generic worker, there is no neighbour to take down.

de brevitate vitae

It is not that we have little time, but that we lose much of it.

Seneca's maxim guides the question behind brevis.sh: which complexities truly deserve a team's time? Every workflow runs in isolated pods so that failures, versions and dependencies have clear boundaries.

01

image per step

Each step declares the runtime it needs. Bumping one version doesn't force you to touch the others.

02

logs per run

Output belongs to the run that produced it. Investigating a failure isn't rebuilding a lost context.

03

persistent retries

The attempt outlives the process. A restart doesn't erase what was already known about the work.

04

dependency isolation

What one step carries doesn't leak into its neighbours. A clear boundary is what makes a failure legible.

frequently asked

Start with the essentials.

Is brevis.sh really 100% open source?

Yes. The complete runtime is open to read, use, adapt and contribute to.

What does the reference to Seneca mean for the project?

De Brevitate Vitae inspires more intentional engineering: reduce the complexity that consumes time, and preserve room for work with purpose.

How does pod isolation work?

Each workflow step runs as its own pod with its own image, keeping dependencies and execution context separate.

What is the relationship with Aretê Academy?

brevis.sh is a project of Aretê Academy, which brings great ideas from philosophy closer to the real challenges of building software.

Can I use only one of the pieces?

Yes. Each piece has its own module, version and image: the SDK is a Go library that runs in any program, the Gateway starts on its own with a YAML file and no database, and brevis-sql runs as a container. The Core orchestrates the others when you want it to — it is a prerequisite for none of them.
