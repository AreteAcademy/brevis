문서

brevis.sh를 설치하고, 이해하고, 운영하는 데 필요한 모든 것 — 첫 workflow부터 Kubernetes 배포까지.

시작하기

에코시스템

brevis.sh의 네 가지 구성 요소가 각각 하는 일과 데이터가 지나가는 경로입니다.

통합

무엇이 무엇과 연결되는지: 데이터가 어디서 오고, 어디에 도착하고, 어디서 모델링되고, 전체가 어디서 실행되는지 정리합니다.

소개

brevis.sh가 무엇이고 어떤 문제를 해결하는지, 그리고 어떤 경우에 맞지 않는 선택인지 설명합니다.

설치

바이너리를 받는 방법, 필요한 요구 사항, 설치가 올바른지 확인하는 방법입니다.

빠른 시작

아무것도 없는 상태에서 인터페이스의 실시간 DAG까지, 네 단계로 진행합니다.

개념

Core

오케스트레이터입니다. run을 스케줄링하고, Postgres에 큐를 보관하고, step마다 pod 하나를 시작하며, 데이터는 절대 만지지 않습니다.

Workflows

전체 YAML 형식입니다. step, 의존성, 이미지, 리소스, 스케줄을 다룹니다.

스케줄러와 큐

서로 독립된 두 루프입니다. 누가 run을 만들고, 누가 실행하는지, 그리고 왜 분리되어 있는지 설명합니다.

step당 pod 하나

각 step이 자기만의 pod에서 실행되는 이유와, 그것이 비용과 격리에 가져오는 변화입니다.

step 간 컨텍스트

한 step이 다음 step에 전달하는 것으로, 환경 변수 두 개와 파일 하나입니다.

레퍼런스

CLI

엔진의 하위 명령 열두 개와 각각의 플래그, 인자, 요구 사항입니다.

매개변수

파일을 수정하지 않고도 같은 workflow의 두 run 사이에 달라지는 것입니다.

구성

모든 환경 변수의 기본값, 형식, 누락되었을 때의 동작입니다.

step 런타임

step이 다루는 언어와 도구에 대해 선언하는 것과, 대부분은 선언할 필요가 없는 이유입니다.

SDK와 라이브러리

Go SDK

fetcher를 작성하는 방법으로, 소스에서 추출하고 변환한 뒤 목적지에 적재합니다.

클라이언트 라이브러리

어떤 언어의 step이든 컨텍스트와 run의 시계를 읽는 방법과, 이미 라이브러리가 있는 언어입니다.

Python

pip install brevis — step 간 컨텍스트, run의 시계, 파이프라인 고유의 메트릭을 의존성 없이 제공합니다.

운영

Console

Core의 웹 인터페이스입니다. 무엇이 실행 중이고, 무엇이 실행될 예정이며, 각 run에 어떤 일이 있었는지 보여 줍니다.

Kubernetes

엔진을 배포하는 방법, 필요한 권한, 배포 후 확인할 사항입니다.

관측성

두 프로세스의 Prometheus 메트릭, 무엇을 지켜봐야 하는지, 그리고 의도적으로 없는 것입니다.

화이트 라벨

YAML 파일 하나로 인터페이스의 제목, 모토, 로고, 팔레트를 바꿉니다.

수집

수집

데이터를 적재하는 HTTP 엔드포인트입니다. 검증하고, 식별하고, 배치로 묶고, 전달합니다. 자체 이미지와 자체 버전을 가집니다.

수집 sink

여섯 가지 목적지, 각 데이터베이스가 레코드를 쓰는 방식, 그리고 이미지에 사용하는 것만 담기는 이유입니다.

벤치마크

게이트웨이를 측정하는 방법, 숫자가 말하는 것, 그리고 서로 일치해야 하는 세 증인입니다.

SQL 모델링

SQL

일반 .sql 파일이 의존성 순서대로 테이블과 뷰가 됩니다. workflow step으로도, 단독으로도 사용할 수 있습니다.
