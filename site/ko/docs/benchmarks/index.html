문서

벤치마크

게이트웨이를 측정하는 방법, 숫자가 말하는 것, 그리고 서로 일치해야 하는 세 증인입니다.

명령 하나로 게이트웨이 전체를 측정합니다.

bash
BREVIS_BENCH_IMAGE=brevissh/brevis-gateway:0.11.0 ./bench/run.sh

Postgres를 띄우고, 게이트웨이를 시작하고, [k6]로 부하를 걸고, 버퍼가 비워질 때까지 기다린 뒤 게이트웨이 자신의 /metrics를 수집해 bench/results/REPORT.md를 작성합니다.

증인 셋, 그리고 중요한 것은 세 번째#

k6는 프로듀서가 본 것을 압니다. 게이트웨이는 자기가 한 일을 압니다. 첫 번째만 가진 부하 테스트는 빠른 게이트웨이와 202로 응답하고 받아들인 것을 버리는 게이트웨이를 구별할 수 없습니다.

그래서 리포트는 둘을 나란히 놓고, Postgres의 행도 셉니다.

증인이벤트
k6가 accepted라고 통보받음5,431,000
게이트웨이가 수신으로 집계함5,431,000
Postgres의 행5,431,000
dead letter의 레코드0

앞의 둘은 모두 게이트웨이 자신의 산술입니다. 하나는 작성한 응답에서, 하나는 증가시킨 카운터에서 나온 것이며, 이벤트를 잃는 버그가 있어도 둘은 서로 일치할 수 있습니다. 우리 말을 믿지 않은 것은 데이터베이스뿐입니다.

셋이 일치하지 않는 run은 실패한 것입니다. 백분위수가 아무리 좋아도 마찬가지입니다.

위의 run#

bench/results/REPORT.md의 2026-09-26 run입니다. brevissh/brevis-gateway:0.11.0, Darwin arm64, CPU 11개, 같은 커널의 컨테이너에서 실행한 Postgres 17, write: append인 auto_table[columns]입니다.

수락된 이벤트5,431,000 (135,768/s)
전송한 본문40초 동안 1,156.7 MiB
503 (백프레셔)0
p50 / p95 / p995.9 ms / 16.0 ms / 22.7 ms
전달된 배치1,087개, 묻힌 것 없음

임계값이 핵심입니다#

임계값 중 하나라도 실패하면 k6가 0이 아닌 코드로 종료하므로, 이것은 차트가 아니라 게이트입니다.

임계값이유
p95 < 500ms수락 경로는 sink의 지연과 무관해야 합니다. COPY를 기다리는 요청은 비동기 파이프가 막으려는 결함입니다.
http_req_failed < 1%503은 괜찮지만 타임아웃이나 5xx는 그렇지 않습니다.
events accepted > 1000임계값 스위트는 아무것도 응답하지 않은 게이트웨이에 대해서도 통과합니다.

의도적으로 느슨하게 잡았습니다. CI가 준 어떤 머신에서든 실행되기 때문입니다. 이 임계값은 퍼센트 단위가 아니라 회귀의 모습인 자릿수 차이를 잡아냅니다.

503은 실패가 아닙니다. 게이트웨이가 둘 곳이 없는 이벤트를 거부하는 것이며 재시도해도 안전합니다. ingestion_id는 이벤트의 고정된 함수이므로 같은 본문을 다시 보내면 같은 레코드입니다. 이를 오류로 집계하면 백프레셔가 버그처럼 보입니다.

측정하지 않는 것#

  • BigQuery는 아닙니다. 목적지는 컨테이너 안의 Postgres입니다. 웨어하우스의 load job 쿼터, 커밋 지연, DDL 동시성은 이 숫자에 들어 있지 않으며 들어갈 수도 없습니다.
  • 내구성은 아닙니다. durability: memory가 유일한 티어이므로 202는 *RAM에 수락됨*을 뜻합니다. 이 벤치마크는 그것이 얼마나 빨리 일어나는지를 측정할 뿐, SIGKILL 이후 무엇이 살아남는지는 측정하지 않습니다.
  • 여러분의 하드웨어는 아닙니다. 형태와 비율로 읽으세요.

프로파일별 로컬 클라우드#

bash
docker compose -f docker-compose.drivers.yml --profile gcp up -d
docker compose -f docker-compose.drivers.yml --profile all up -d

클라우드마다 파일 하나가 아니라 프로파일이 있는 파일 하나입니다. 파일이 둘이면 프로젝트 이름이 둘인데, 양쪽의 postgres가 이미 한 번 엔진의 개발 데이터베이스를 대체한 적이 있습니다.

floci가 지원하는 BigQuery는 보기보다 적습니다#

가정이 아니라 측정한 결과입니다.

데이터셋과 테이블 생성✅
timePartitioning과 clustering 보존✅ — 0.9.1 버그의 형태
컬럼 PATCH✅ — auto_table의 진화
insertAll✅
쿼리✅, /var/run/docker.sock을 마운트한 경우에만
load job❌ Only QUERY jobs are supported by the floci BigQuery emulator

SDK는 BigQuery에 load job으로만 씁니다. 따라서 floci는 페이로드를 DDL로 바꾸는 auto_table의 모든 줄을 검증하지만 Brevis의 쓰기는 하나도 검증하지 않습니다. 오늘날 로컬 테스트가 없는 쪽이 여전히 그 절반이며, 갖출 가치가 있습니다. 하지만 floci에 대한 스위트가 통과했다고 BigQuery가 동작한다는 뜻은 아닙니다.
