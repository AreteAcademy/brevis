has nowhere to put, which is the honest answer and safe to retry: the

## The three have to agree

| witness | events |
|---|---:|
| k6 was told `accepted` | 5431000 |
| the gateway counted received | 5431000 |
| rows in Postgres | 5431000 |
| records in the dead letter | 0 |

**They agree.** Every event that was answered `202` is a row, and
nothing was buried. This is the only number on the page that cannot
be traded for speed: a gateway can always be made faster by
accepting more than it delivers.

The third witness matters. The first two are both the gateway's own
arithmetic -- one from the response it wrote, one from the counter it
incremented -- and a bug that lost events could keep them consistent
with each other. The database is the only one that did not take our
word for it.

## What this does not measure

- **Not BigQuery.** The destination is a Postgres in a container on the
  same kernel. A warehouse's load-job quota, its commit latency and its
  concurrency are not in these numbers and cannot be.
- **Not durability.** `durability: memory` is the only tier there is, so
  a `202` means accepted into RAM. This measures how fast that happens,
  never what survives a `SIGKILL`.
- **Not your hardware.** It ran on whatever machine produced the header
  above. Read it as a shape and a ratio, not as a capacity plan.
