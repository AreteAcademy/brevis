### §3 is half done, and the written half is the harder one

The note asks two things, and only the first is open.

> *"como podemos fazer com que esse sdk aqui se comunique com a API?"* and
> *"o contexto precisa estar salvo no banco de dados, e toda execucao precisa
> ter um ID"*

**That half shipped.** The library does not talk to an API — deliberately, and
the design is in [`docs/CONTEXT.md`](../CONTEXT.md): the engine hands a step
`BREVIS_INPUT` and reads back `BREVIS_OUTPUT`, which under Kubernetes is the
termination message the kubelet already carries. The context lands in
`task_runs.saida` (JSONB), keyed by `(run_id, node_id, attempt, map_index)`,
every run carries a UUID, and a resumed run seeds from those rows. No token, no
port, no socket in the step's process.

What is left of §3 is the **npm package itself**, and its plan is written.

## §7 — official task images

> `brevis/etl-go:1.4`, `brevis/etl-python-analytics-pandas:1.4`,
> `brevis/etl-python-analytics-polars:1.4`, `brevis/etl-python:1.4`,
> `brevis/etl-node:1.4`

### Why this is worth more than it looks

Today a consumer writing a Python step brings their own image and installs
`brevis` into it. That works, and it is also the reason the Python library's
audience is smaller than it should be: the step author has to build an image
before they can write a step.

An official image is not a convenience. It is the difference between "install
our package into your image" and "point `image:` at ours and write the step".

### What it costs, honestly

Not the Dockerfiles. Those are short. The cost is what an image commits you to:

| | |
|---|---|
| a **security surface** | a published image with pandas in it is a CVE feed you now own. `brevis/etl-go` is distroless and near zero; `brevis/etl-python-analytics-pandas` is not |
| a **rebuild cadence** | an image nobody rebuilds is worse than no image. Weekly, on a schedule, or the base's patches never reach it |
| a **version matrix** | five images times two architectures times the SDK versions they embed |
| a **size claim to keep honest** | "ultra leve" has to be measured, the way `engine-weight.sh` measures the engine, or it stops being true one dependency at a time |

### The shape that keeps it cheap

- **One `Dockerfile` per image**, one `deployments/images/` directory, and one
  matrix job — not five workflows.
- **A gate on size**, in the shape this repository already uses: a ceiling per
  image with the number measured and a comment saying what bought the last
  raise. Without it, "ultra leve" is marketing.
- **The SDK is embedded, and the image says which version.** `brevis version`
  inside the engine's image already sets this precedent, and it is what makes
  an incident traceable.
- **The tag is the SDK's version, not an invented one.** `etl-go:0.56.0`
  carries `sdk/v0.56.0`. A separate `1.4` is a second number to keep in step,
  and this repository has been bitten by that four times.

### What has to be decided before starting

Whether Polars and pandas are **separate images** or one image with both. The
note asks for separate, and separate is right: they are two different
dependency trees, and a team that uses one should not carry the other's CVEs.

## §8 — orchestrating beyond Kubernetes

> EKS (pod), GKE (pod), Cloud Run, AWS Lambda, ECS, EC2, GCP machines. Validate
> the whole ecosystem on floci.io.

### The good news, and it is real

`internal/execution/Executor` is already the right interface, and it is small:

```go
Name() string
Execute(ctx, TaskExec) (<-chan Event, error)
Cancel(ctx, execID) error
```

Two implementations exist (`local`, `kubernetes`) and the runner chooses
between them. **EKS and GKE need nothing at all** — they are Kubernetes, and
the existing executor already runs there. The note lists seven targets; two of
them are already done.

### The bad news, and it is the whole design problem

Three things the Kubernetes executor gets from the platform have **no
equivalent** on Lambda, Cloud Run or ECS:

| | how Kubernetes does it | elsewhere |
|---|---|---|
| the **return path** | `terminationMessagePath` — the kubelet carries up to 4 KB back with the exit code | nothing equivalent. Lambda has a response payload; Cloud Run Jobs have none; ECS has none |
| **live logs** | `Logs(pod, follow=true)`, which is what makes `@brevis:` phases appear while a step runs | CloudWatch and Cloud Logging are pull-based, with lag and their own quotas |
| **cancellation** | delete the pod | Lambda cannot be cancelled at all once invoked |

So this is not "write four more executors". It is **a decision about what the
contract requires**, and there are only two honest answers:

**(a) Narrow the contract.** An executor that cannot return context declares
so, and a workflow using `context.set()` on such a step fails at *validation*,
not at runtime. Cheap, honest, and it makes half the targets second-class in a
way that is visible in the YAML.

**(b) Add a return path that does not depend on the platform.** The step POSTs
its context to the engine before exiting. That is the API the
[deferred-by-design](2026-09-07-deferred-by-design.md) §3 decision priced out:
per-run tokens, scoping, expiry, injection into every execution. It makes every
target first-class and it is a genuinely large piece of work.

**This decision comes first, before any executor is written.** Writing a Cloud
Run executor and discovering the return path at the end is how this gets built
twice.

### floci.io

The note names it as the simulation environment. Worth being clear about what
that buys: it can exercise the **executors**, and it cannot replace the `kind`
job from [`2026-09-07-proofs-that-need-infrastructure.md`](2026-09-07-proofs-that-need-infrastructure.md)
— that one exists to prove the *Kubernetes* path, which is the one running in
production today.

## §10 — schema evolution on load

> *"quando um cliente/consumidor usar a nossa solucao, ele precisa ter esse
> mecanismo"*, mirroring what the market does.

### What exists today

`sdk.Schema` is a **declaration**: name, type, nullability, in DDL order. The
SDK deliberately does **not** infer types, and the reason is written into
`schema.go` and is still right:

> *a field that arrived whole today and fractional tomorrow changes the
> column's type with nobody writing anything.*

`CreateSQL` exists for the destination that needs real DDL. What does **not**
exist is any answer to the source growing a column tomorrow.

### What the market actually does

The convergent answer across Fivetran, Airbyte, Delta Lake and Iceberg is
narrower than "evolve the schema", and the narrowness is the point:

| change | the market's default |
|---|---|
| a **new** column appears | add it, nullable. Safe: nothing that read the old schema breaks |
| a column **disappears** | keep it, stop writing it. Dropping loses history |
| a type **widens** (int → bigint, int → float) | allow |
| a type **narrows** or changes kind | **refuse**, and say so loudly |
| a column is **renamed** | indistinguishable from a drop plus an add without a declaration. Refuse to guess |

That is `additive-only` as the default, with an explicit opt-in for anything
lossy. It maps cleanly onto what already exists here: `Schema` is the
declaration, and evolution is the diff between the declaration and the
destination.

### The shape

- A **policy** on the target, defaulting to additive-only, named in the YAML
  and in `sdk.Target`.
- The diff computed **before** the load, not during — a load that half-evolves
  and then fails is the worst outcome.
- Every change **recorded**, so "when did this column appear" has an answer.
  This is the piece consumers actually ask for after the fact.
- A refusal that names the column, both types, and the flag that would allow
  it. A refusal that says "schema mismatch" is a refusal somebody works around
  by deleting the table.

### Weight

Real, and self-contained: one SDK feature, one policy, per-destination DDL.
Bigger than §7, smaller than §8, and it is the one on this list that a running
consumer hits **today**, silently, whenever a vendor adds a field.

## §11 — the database and data diagnostic

> *"boa parte do sistema de ingestao tem problemas de carregamento,
> dimencionamento dos dados, datasets grandes, carregamento lento"*

This note deserves to be split, because it is two features wearing one name and
they have very different costs.

### (a) What the SDK already knows and does not surface

Every load already produces rows, bytes, extract time, load time, pages,
attempts, ignored records — that is `sdk/meter.go` and the `LoadResult` the
runner logs. `sdk.Meter` already routes them.

So the first half of this ask is not a new measurement. It is **keeping the
numbers over time and showing the trend**: which pipeline's rows-per-second is
degrading, which one's bytes are growing faster than its rows, which one's
extract time has doubled since March. That is a query, a screen and a retention
policy, over data the engine is already producing and discarding.

**This is the cheap half, and it answers most of the note.** "Carregamento
lento" is a trend question, and a trend needs history, not a scan.

### (b) A genuine profile of the destination

Null rates, cardinality, distinct counts, min/max, table and partition sizes,
skew. This is a different product: it means reading the destination's own
statistics (`pg_stats`, `INFORMATION_SCHEMA.TABLE_STORAGE` in BigQuery,
`information_schema.columns`), which is per-destination work, and it means
deciding whether Brevis is allowed to run queries against a consumer's
warehouse on a schedule — with the cost that implies on a metered engine.

### The order inside §11

(a) first, and it may well be enough. It uses what exists, costs a table and a
screen, and the note's own examples — slow loading, growing datasets — are all
trend questions. (b) only if (a) leaves something unanswered, and with the
billing question answered before a single query is written.

## The order worth attacking, and why

```
  now        1. the scheduler's retry policy        a consumer is waiting. ~1h
             2. the Python-skip line in CI          one line, and a proof stops being optional

  next       3. §10 schema evolution                the only item a running consumer hits TODAY
             4. §7 official images                  cheap, and it is what makes every language library adoptable
             5. §3 Node.js (TASK #4)                plan written, contract proven, unblocked by #4 above

  then       6. §11(a) the trend screen             uses what already exists
             7. kind in CI                          the only production path with no proof
             8. §8 beyond Kubernetes                decide the return path FIRST

  background   the website's three items, and a plan for datasets
```

**Why §10 before §7.** Images are adoption; schema drift is correctness. A
vendor adding a column breaks a consumer today, quietly, and no image fixes
that.

**Why §7 before §3.** Shipping a Node.js library with no image to run it in
delivers half a feature: the step author still has to build an image before
writing a step. `brevis/etl-node` is what makes the npm package worth
publishing.

**Why §8 is last, and should stay last.** It is the largest item here and its
first deliverable is not code — it is the decision in §8 above about the return
path. EKS and GKE, which is what most of its value is, already work.

**What is deliberately not on this list.** The GCP integration credentials, and
the Spanish translation. The first is not a code change; the second is a
translation, and correcting `CONTRIBUTING.md`'s sentence is the honest one-line
answer until there is a Spanish-speaking reader to serve.
